## 二、Agent 平台架构与多租户隔离（约 04:30—08:00）

### 面试官问题（根据回答还原）

Agent 平台如何实现多用户/多租户隔离？Agent 服务、用户环境和数据分别如何部署？

### 候选人回答

- Agent 本身设计为无状态应用，多个用户共享一组 Agent 服务副本；候选人举例为约 5 个副本。
- 每个用户拥有独立的沙箱环境，Agent 与沙箱之间通过网络连接。
- 沙箱运行在云端的另一套平台上，与 Agent 服务解耦。
- 公共能力（例如公共 Skills、MCP 等）存放在云端对象存储/文件存储中；用户私有能力和工作空间单独隔离。
- 每个员工有独立工作空间，用于保存技术文档、私有 Skill 等内容。
- 用户登录后，系统会：
  1. 启动该用户对应的沙箱；
  2. 从对象存储中拉取用户工作空间内容；
  3. 将文档、Skill 等注入到对应沙箱中。
- 用户通过企业统一身份认证（音频中疑似 BOC/企业统一认证）获得沙箱授权。

### 面试官追问与澄清

- 面试官表示对“Agent 与沙箱的关系”理解不够清晰，请候选人重新解释。
- 候选人进一步明确：Agent 服务是共享的无状态服务，用户之间真正独立的是沙箱环境；用户请求由共享 Agent 处理，再通过网络访问对应沙箱。

### 关键评价点

- 有无状态服务与有状态/隔离执行环境的拆分意识。
- 能从计算环境、用户数据、公共能力、身份认证几个维度解释多租户隔离。
- 需要进一步补充的工程细节：沙箱生命周期、网络隔离、权限边界、资源配额、逃逸防护、密钥管理、故障恢复及审计机制。

## 三、Agent 在 SRE 运维中的实际价值（约 08:20—11:35）

### 面试官问题（根据回答还原）

Agent 具体解决了哪些运维问题？当前落地效果如何？

### 候选人回答

候选人将运维流程拆成四个环节：

1. **感知**：发现水位异常、网络异常、故障等事件；
2. **信息收集**：从调用链、变更事件等上下文中收集相关信息；
3. **故障定位**：基于收集的信息分析异常原因；
4. **修复**：执行变更或恢复操作。

当前 Agent 主要覆盖前三步，自动修复暂未开放，原因是生产环境风险较高。

### 效果举例

- 项目从 4 月开始建设。
- 在一次涉及多个团队的故障中，传统流程需要拉会、跨团队沟通和定位，整体处理约 30 分钟左右。
- 通过 Agent 辅助，内部基础业务场景的故障处理目标可压缩到约 10 分钟左右。
- 候选人强调的目标口径为“1 分钟感知、5 分钟定位、10 分钟由人工配合完成修复”。

### 可能的追问

- 这些时间指标是平均值、P95 还是单个案例？
- Agent 定位结果的准确率、误报率和人工采纳率如何衡量？
- 自动修复何时可以开放？如何设置审批、回滚和熔断？

## 四、Agent 效果指标与输出质量（约 12:08—15:00）

### 面试官问题（根据回答还原）

如何衡量 Agent 的效果？除了响应时间，还会关注哪些指标？

### 候选人回答

候选人提到的指标包括：

- 资源消耗：Token消耗等；
- 响应时间；
- SRE 特定任务的完成率；
- 工具调用有效率：调用的工具是否真正提供了有效信息，是否存在无效调用；
- API 调用情况：调用次数、调用耗时和相关成本；
- 回复友好性/可读性：输出是否过长、是否能快速给出结论。
- 一致性：同一任务/问题，同一Agent多次执行结果的一致性。

### 输出格式优化（友好型的判定）

- 与运维团队沟通，明确用户真正需要的回复形式。
- 将模型的自然语言输出结构化，优先使用表格。
- 回复采用“总—分—总”结构：先给结论/结构，中间给详细依据，最后给总结和建议。
- 对故障场景，结果中补充：
  - 问题结论；
  - 修复建议；
  - 推荐的后续排查问题。

### 关键评价点

- 不只关注模型效果，也考虑工具调用、资源成本和运维人员使用体验。
- 对“友好性”指标的衡量较主观，候选人的解决办法是通过一线用户反馈迭代输出模板和结构。

## 五、eBPF 监控系统项目（约 16:20—18:20）

### 面试官问题（根据回答还原）

请介绍一下 eBPF 监控项目：为什么做、如何实现、难点是什么？

### 候选人回答

- 项目针对微服务/业务系统的异常监控需求，实验室团队中有成员负责 eBPF 和 C 语言部分。
- 监控体系使用 Prometheus。
- 基于现有 eBPF 相关 exporter，增加针对业务的自定义指标，并将 exporter 接入 Prometheus，采集底层数据。
- 采集过的指标包括底层 I/O 效率、Flash 相关效率等（具体指标名称需复核）。

### 技术难点

- 监控体系本身搭建相对成熟，难点主要在自定义 eBPF 监控脚本/插件的开发。
- eBPF 需要从 Linux 底层采集数据，对 Linux 内核、底层机制和 C 语言编程要求较高。

### 面试官可能关注的问题

- eBPF 程序如何保证安全性和稳定性？
- exporter 如何避免高基数指标和自身性能开销？
- 指标从内核态到用户态再到 Prometheus 的数据链路如何设计？

## 六、监控组件性能开销验证（约 18:40—20:00）

### 面试官问题（根据回答还原）

如何评估监控组件对业务系统的性能影响？

### 候选人回答

- 使用 Locust 进行压力测试。
- 对微服务持续施加约 1000 QPS 的请求压力。
- 监控组件与被测微服务运行在同一集群中。
- 观察监控组件与主要业务组件的 CPU、内存占用，并进行对比。
- 测得监控组件的资源占用约为主要微服务组件占用的 9.66%。

### 结果解读

- 候选人将 9.66% 作为监控组件相对于主要业务组件的资源占用比例。
- 需要注意：该数据更像“相对资源占用”，不一定等同于业务请求延迟增加 9.66%；若继续追问，应区分 CPU/内存开销、吞吐下降和延迟变化。

## 九、候选人反问与团队方向（约 22:24—29:55）

### 候选人问题

想了解团队在 AI SRE / AIOps 方向的现状、投入重点和发展状态。

### 对话要点

- 候选人认为，运维平台需要连接大量业务和基础设施平台。
- 不同业务可能有不同的数据平台、监控平台和权限边界，平台之间的互通是落地难点。
- 候选人结合阿里实习经历说明：在单一事业部内，团队通常能掌握本部门的业务数据和基础指标；但跨部门、跨业务线时，数据和权限往往无法直接打通。
- 当前思路之一是让不同部门分别建设自己的业务 Agent，再通过 A2A（Agent-to-Agent）方式进行协同，减少人工提单和跨团队流转，让 Agent 按流程完成协作。

### 候选人关注点

- 跨团队数据访问与权限治理；
- 多平台信息串联；
- Agent 之间的协作协议与流程编排；
- 从单点智能助手走向企业级智能运维体系。

## 十、面试整体印象与复盘建议

### 展现出的优势

- Kubernetes、调度器、监控、异常检测和 Agent 运维方向经历较集中。
- 能从实际运维流程拆解 Agent 的价值，而非只描述模型能力。
- 有多租户隔离、沙箱、对象存储、统一认证等系统设计思考。
- 能使用压力测试、混沌工程和基线算法做效果验证。
- 对自动修复保持谨慎，具备生产风险意识。

### 需要加强的表达

- 量化结果需明确统计口径：平均值/P95、样本量、基线、实验时长和线上数据来源。
- 多租户方案应补充安全边界：网络策略、资源配额、沙箱逃逸防护、权限最小化、审计与回滚。
- eBPF 项目需准备更具体的内核机制、程序生命周期、数据采集链路和开销分析。
- 调度器项目需明确重构前后的架构差异和性能收益。
- 面试中出现了一些较多的口语重复和模糊术语；正式面试时可以采用“背景—目标—方案—结果—复盘”的结构回答。

### 一句话总结

候选人具备云原生和 Kubernetes 基础，项目经历覆盖调度、监控、异常检测及 AI 运维，能结合实际业务讨论 Agent 落地；后续重点应进一步夯实生产级安全、可靠性和量化指标表达。
