## 二、SRE-Benchmark 测评平台深挖（约 05:39—08:31）

### 面试官问题（根据回答还原）

这份实习里最难的部分是什么？这个测评平台你是怎么设计的？

### 候选人回答

- **为什么不做"全虚拟环境"**：主流 Agent 评测平台/框架的设计逻辑，是先构建一个完全虚拟的实验环境，再让 Agent 在里面跑不同 case。但他们的业务需求不满足这个前提——Agent 依赖的 MCP 数据是**跨部门、跨业务**的，做数据快照/冻结需要跨部门协同，平台上也很难支持数据快照或冻结，人力和时间成本都过高。
- **改用动态基准**：参考了网上已发表论文中被验证过的方法。线上 SRE Agent 使用的是 Claude Code 模型，它给出的回复已经过业务运维和团队成员验证、确认能满足需求，于是把这些回复作为每个 SRE case 的**实际标准答案**，并做结构化。
- **两部分评分**：
  1. **回复质量**：针对不同任务类型设定不同评分标准，用 LLM-as-a-Judge 让大模型评测，评测提示词可根据人工打标持续优化。
  2. **工具调用链路**：记录 Agent 执行任务时调用了什么工具、顺序如何、传入参数是什么，把被测模型的链路与参考答案链路做**编辑距离的序列匹配**。
- **权重**：回复占 0.7、链路占 0.3，这样对同一批 case 上不同模型能有比较好的区分度。
- 当时评出性能最好的模型是 Qwen3.8-Max。

### 关键评价点

- 「为什么不用虚拟环境」这段是本场的**最高光回答**：他没有背框架，而是给出了真实工程约束（数据跨部门、快照成本、平台能力不足），再说明如何退而求其次用动态基准——"约束 → 取舍 → 验证"的叙述比复述论文方法有说服力得多。
- 需要补一层防守：动态基准的标准答案来自 Claude Code，**存在"以强模型答案为准"的乐观偏置**。如果被追问"这套基准会不会偏向 Claude 系模型"，要能说出缓解手段（人工复核、多模型交叉标注、按任务类型分层）。
- 简历里写了"覆盖 6 个维度的模型测评"，本场没有展开具体是哪六个维度——建议提前固定一版，被问到时直接报出来。

## 三、编程语言与 Go 基础（约 08:31—22:38）

### 面试官问题（部分引用）

「你平时写代码主要用什么语言？」

### 候选人回答

- 自己写代码主要用 Golang；做 Agent、协同相关的会用到 Python。

### 面试官追问与澄清

（以下问题多为语义反推，个别片段有录音依据）

**make 和 new 的区别**

- `new`：为类型分配空间并返回**指针**，指向该类型的零值；
- `make`：只用于 slice、map、channel，负责提前开辟空间并完成初始化；
- 日常用 `make` 更多，主要是给自定义结构体、slice、map 做初始化。

**goroutine 与线程的区别**

- goroutine 的粒度比线程小，利用的是 Go 的 GMP 调度模型；
- 线程是系统层面的执行单元，goroutine 更像一个更轻量的、执行任务的单元；
- 对应到 GMP：G 是 goroutine，M 是线程（真正干活的工人），P 是处理器（工作台）——线程必须先拿到一个 P 才能执行任务。

**无缓冲 channel 与有缓冲 channel**

- 有缓冲 channel 中间有缓冲空间；无缓冲 channel 的写入会被阻塞，必须等读取端同时就绪，否则两端相互阻塞。
- 候选人补充：有缓冲 channel 关闭后仍能把缓冲里的存量数据读出来，无缓冲 channel 关闭后读到的基本是零值。

> 需要修正：channel 关闭后再读取，**有无缓冲都会返回零值**，区别只在于有缓冲的能把缓冲区中尚未取走的数据读完。这一点在面试里答反了。

**数组和切片**

- 数组是静态的、固定长度；切片更像动态数组，可动态扩容——一开始可能只开很小的空间，填充过程中按两倍扩容，扩容时会搬到另一片新的底层空间；
- 从 `sliceA` 取一段赋给 `sliceB`，修改 `sliceB` 会同时改到 `sliceA`（共享底层数组）；数组则相当于整体 copy 一份。

**Go 中如何处理异常**

- 用 `error` 返回值判断，而不是 try/catch；panic/recover 用得少。

**map 是不是线程安全的**（面试官追问片段）

- 原生 map 不是并发安全的；`sync.Map` 才是并发安全的。
- `sync.Map` 是两层 map：一层读、一层写，中间有计数与同步机制；当读命中率下降时，会把写层的数据同步到读层。

**Go 接口有什么特点**（面试官原话引用）

- 空接口 `interface{}` 可以作为通用参数接收任意类型，取用前需要做类型断言转换；
- 接口是**隐式实现**：只要实现了接口里的所有方法就算实现了该接口，不需要显式引入接口类型名。

**值接收者与指针接收者的区别**

- 读操作两者一样；
- 用值接收者写，改的是副本，影响不到原变量；用指针接收者才能改到原本那片空间，形成链式修改；
- 涉及内存逃逸：函数内定义的局部变量如果通过指针返回，会逃逸到堆上；值接收者接收临时变量则不会发生逃逸。

**select**

- 主要用于 channel 的多路复用：一个 select 里有多个 case，每个 case 是一个可触发条件（通常是 channel 收发）；
- 可以同时监听多个管道，哪个就绪就执行对应 case 下的逻辑；也可以像 switch 一样针对不同条件做多分支。

**context**

- 主要作用是管控 goroutine：一个函数里起多个 goroutine 做数据处理与写回时，用 context 控制它们的生命周期，并传递背景参数；
- 两种常见形式：`context.WithCancel`（调用 cancel 即关闭）与 `context.WithTimeout`（超时即关闭），传入同一 context 的 goroutine 会一并收到取消信号。

**goroutine 泄露**

- 两种情况：一是创建后没有正常结束，goroutine 不断累积；二是 goroutine 还在运行，但它的父函数/父协程已经退出、没人再接收它；
- 排查方式：从代码上看有没有合法的关闭逻辑——父函数是否用 context 对它的生命周期做了合理管理。

### 关键评价点

- 覆盖面够（make/new、GMP、channel、slice、map/sync.Map、接口、接收者、内存逃逸、select、context、泄露都答到了），但**表达效率偏低**：每题平均要三四轮自我修正（"可能""我觉得""大概是这样"），面试官很难快速抓到结论。
- **channel 关闭语义答反了一处**：关闭后读取返回零值是无缓冲/有缓冲共同的语义，区别只在于缓冲里还有没有剩数据。这类基础题答错比答不出更扣分。
- 更好的节奏是"结论先行 + 一句机制 + 一个自己项目里的例子"：讲 select 时直接接"调度插件 / Agent 的工具循环里就用了 select 做超时与取消"，回答立刻从八股变成工程经验。
- `sync.Map` 的定位要补准：它适合**读多写少、键集合相对稳定**的场景，并不是 map 的并发版替代品；被追问"什么时候该用互斥锁而不是 sync.Map"时必须答得出来。

## 四、中间件与 Linux 基础（约 22:38—25:27）

### 面试官问题（根据回答还原）

中间件你熟悉哪些？Linux 上常用的排查命令说说看。

### 候选人回答

- 中间件这块用得比较少，直接说明经验有限。
- **日志**：程序的标准输出或 info/error 日志一般落到指定的 `.log` 文件；排查时直接查日志文件，搜关键字用管道配合 grep 匹配。
- **进程**：查看正在运行的进程用 `ps aux`，能列出所有进程及其 PID。
- **端口占用**：用 `netstat -tulnp` 查看端口对应哪个应用在占用，包括进程 ID、启动命令。
- **权限**：`chmod`，既可以用 `chmod +x` 给文件加可执行权限，也可以用数字形式（如 `chmod 777`）修改权限。
- **软链接与硬链接**：软链接类似快捷方式，删掉指向的文件后软链接本身还在但已不可用；硬链接则相当于删掉原文件时硬链接也会同步消失。

### 关键评价点

- **硬链接这一问答错了**。硬链接与原文件指向**同一个 inode**，删掉原文件名（一个目录项）后，只要还有其他硬链接，数据依然可以正常访问；只有当 inode 的链接计数归零，数据才会被回收。这类错误比"不会"更伤，必须立刻修正记忆。
- `netstat` 在新发行版上已逐步被 `ss` 取代（`ss -tulnp`），可以顺带提一句。
- 中间件"用得少"是实话，但后端岗问中间件通常想听 **Redis / 消息队列 / 缓存** 的基本模型，完全放空会直接失分；建议至少准备 Redis 常用数据结构与缓存穿透/击穿/雪崩的口径。

## 五、容器与运行时（约 25:27—27:10）

### 面试官问题（部分引用）

「Docker 和 ContainerD 有什么区别？」「镜像和容器的区别呢？」「Docker 容器中的数据如何持久化？」

### 候选人回答

- **Docker vs ContainerD**：Docker 提供两部分能力——一是容器运行时，让容器能在 Linux 上跑起来；二是一整套容器操作（build、run、`exec` 进容器执行命令、镜像管理），既能构建镜像又能把镜像在本机运行起来。ContainerD 只提供底层运行时，**不能构建镜像**。
- **镜像与容器**：类似"程序与进程"的关系。镜像是静态的、打包完成的文件（程序 + 运行环境 + 依赖包）；容器是把镜像加载到实际运行时里跑起来的动态实例。
- **数据持久化**：给容器挂载对应的主机目录或 NFS 目录——要么经网络通过 NFS 存到云对象存储上，要么挂载 Linux 本机指定目录；容器把数据写进本机目录，重启时挂载同一目录即可把之前的数据重新加载进来。

### 关键评价点

- 这一节相对稳：**Docker / ContainerD 的拆分讲得清楚**（运行时 vs 工具链），镜像/容器的类比也准确。
- 持久化只答了 bind mount 与网络存储，**漏掉了 Docker volume**（由 Docker 管理的卷，位于 `/var/lib/docker/volumes`，生产上更常用），也没提 K8s 侧的 PV / PVC——而这恰好是他简历里的强项，是一次白白丢掉的加分机会。
- 更好的收尾：把"容器持久化"直接接到 K8s 的 Volume / PV / PVC / StorageClass，用项目里部署过的真实例子说。

## 八、AI Agent 相关（约 30:25—36:33）

### 面试官问题（部分引用）

「AI 智能体你是怎么理解的？」「工具调用是怎么实现的？」「如何保证智能体调用工具的安全性？」

### 候选人回答

- **Agent 是什么**：把大模型与可执行的操作环境结合起来。原本只能对话的模型，通过 Function Calling、MCP 或 CLI 这类统一协议，去获取环境中真实存在的数据，并且能够操作环境。
- **组成**：模型（大脑）、Function Calling / Tools（手脚）、上下文与消息管理、记忆管理、RAG 知识库。
- **工具调用链路**：提问时把当前可用工具的描述（作用、参数、参数含义与用法）注入给模型 → 模型结合训练过的 Function Calling 格式输出调用 JSON → 智能体解析 JSON 并转成对应的 MCP 调用 → 拿到模型本身拿不到的环境数据 → 回填给模型生成最终回复。
- **怎么保证调用准确性**：模型侧要选**原生 Function Calling 格式**匹配的模型（OpenAI 格式 / Anthropic 格式）；工具侧描述要清晰精确，又不能占用太多上下文窗口。
- **ReAct 模式**：模型自主判断的循环——提问 → 思考 → 输出一段 Function Calling / Tools 调用 → 拿到结果再判断下一步，边执行边思考，每步取的是当前环境下的局部最优，执行链路长度由模型自行判断，中间也可以做人工介入。
- **安全性**：MCP 方式可以把工具按粒度拆分，对敏感参数/操作做权限限制；危险操作必须有人工授权，或保证权限可回滚；另一侧在模型要调用工具时做人工审查——先判断调用与参数是否合法，合法才放行，形成人工审批闭环。

### 关键评价点

- 这是候选人的主场，**概念链条完整、术语准确**，也是整场最流畅的一段（印证面试官是在按"简历上写了 Agent"做验真）。
- 可以更"上强度"：讲工具调用安全时直接给项目事实——SRE-Benchmark 的 6 个维度里有没有安全性维度、Agent 平台里用沙箱与多租户做了什么隔离。用项目证据替代通用方法论，说服力高一档。
- ReAct 的"局部最优"表述略有偏差：ReAct 是"推理—行动—观察"的交替循环，其核心限制是**缺乏全局规划**（这正是后来 Plan-and-Solve、Reflection 等范式要解决的问题）；被追问"ReAct 有什么不足"时，要能顺势讲到这些范式。

## 九、手撕代码：判断链表是否有环（约 36:33—42:47）

### 面试官问题（根据回答还原）

在线编程题：给定一个链表，判断其中是否有环。

### 候选人回答

- 读题后指出：题目给的代码只有一个核心逻辑（判断是否有环），输入需要自己构建有环 / 无环的链表。
- 实现思路为**快慢指针**：快指针每次走两步、慢指针每次走一步，相遇即有环。
- 自测若干用例（含无环链表返回 `false` 的情形），确认全部通过。

### 关键评价点

- 这是**最基础的一道链表题**，识别与思路都没问题，但从读题到跑通花了约 6 分钟，时间主要耗在"自己构造输入"上——说明是**在线判题环境（核心代码模式的输入输出处理）不熟练**，而不是算法不熟。
- 面试前过一遍常见题型的核心代码模式写法：链表、二叉树、数组的手动构造与多组用例自测。
- 写完可以主动补一句复杂度与边界（O(n) 时间、O(1) 空间；空链表、单节点），把"写完了"变成"写对了"。

## 十、反问环节（约 42:47—44:15）

### 候选人问题

- 咱们这边的主要业务都涉及哪些方面？更偏后端开发是吗？
- 咱们（团队）是所有的语言都会用到吗？
- 这些应用似乎也会以 Docker / 容器的方式部署在云平台上，是吗？

### 关键评价点

- 三个问题都问在"确认岗位与团队形态"上，方向没错，但**没有问任何能体现判断力的问题**（业务的技术挑战、团队正在做的事与自己的项目如何衔接）。
- 建议固定准备两个"反向价值"问题：一是"这个岗位最看重候选人哪项能力"，二是"团队目前在技术上最头疼的是什么"——既显得认真，也能用来判断要不要去。

## 十一、面试整体复盘建议

### 展现出的优势

- AI Agent / SRE 项目链条完整，能讲出工程取舍（动态基准那一段尤其好），Agent 概念题答得准确流畅。
- Go 语言基础覆盖面广，make/new、GMP、sync.Map、context、goroutine 泄露这些点都接住了。
- 诚实划线（中间件、数据库、跨域都直接说接触少），没有硬编，可信度守住了。

### 需要加强的表达

1. **后端岗位底座必须补齐**：数据库（索引、事务、隔离级别、锁、连接池）与中间件（Redis、消息队列）是本场的空白区，也是后端岗的必问项，优先级最高。
2. **基础概念不能答反**：硬链接语义、channel 关闭后的读取语义这两处答错，比答不出更伤——把 Go 与 Linux 的基础题过一遍并做自我复述。
3. **结论先行、少自我修正**：本场大量"可能""我觉得""大概是"，把答案稀释了。练习方式：每题先用一句话给结论，再补一句机制，再（可选）接一个项目里的例子。
4. **量化口径跨场次统一**：冗余工具调用下降的 30% / 33% 已出现不一致，按 33% 固定下来，并把 50% / 18% / 57% 一起写进口播稿。
5. **手撕环节练核心代码模式**：不是算法不会，而是输入构造与自测流程不熟，白花了几分钟。

### 一句话总结

项目与 Agent 部分撑住了场子，但这是一场**按后端开发底座出题的面试**，数据库、中间件与基础概念上的空白被完整暴露——下一场之前，把数据库与中间件的最小知识集补齐，是性价比最高的动作。
