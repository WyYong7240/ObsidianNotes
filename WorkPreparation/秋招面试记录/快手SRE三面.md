## 一、项目经历分类梳理（约 00:56—06:11）

### 面试官问题（引用）

「你现在还在阿里实习是吗？」「你的项目经历比较多，这些项目大概齐能说一下背景，比如说有的是你自己花时间做的，还是说有的是那种实验室的、或者实习的类似这样的分类，简述一下是吧？」

### 候选人回答

- 开场确认已从阿里巴巴离职、现在在学校。
- **项目一（云边异构调度优化）**：实验室产出的论文，刚入学时交给他；他读完后发现论文有缺陷（包括算法上的缺陷），做了优化重构，并用 Scheduling Framework 重写，最终目的是更好地传给下一届。背景是微服务网格应用的访问延迟问题与四种资源的负载均衡，做的是均衡性调度机制，利用 K8s 原生调度框架的机制实现。
- **项目二（微服务异常检测，团队 3 人、本人任组长）**：与同门、师兄组队参赛。他负责从监控平台、压力测试到混沌工程的整个平台搭建，以及异常检测算法设计并落到平台上；师兄负责基于 eBPF 的非侵入式监控体系；同门负责文档、PPT 与比赛流程控制。背景是微服务网格应用做异常检测比较麻烦，因此要搭建一个业务性能损耗低于 10% 的监控体系，能对微服务网格应用做异常检测与根因分析，要求根因定位准确率至少高于开源的 Eadro 算法。结果拿了国家一等奖，所有指标都满足赛题要求。
- **项目三（LangGraph 运维 Agent）**：今年年初手搓，基于 LangGraph 架构、采用 ReAct 架构；通过自然语言指令感知和收集集群的过程信息与指标数据，对故障原因进行分析并给出可行的操作建议，但最终的恢复/快恢手段仍由人工执行。
- **实习（阿里巴巴千问事业部）**：分两部分——
  1. 协助团队构建运维智能体（SRE Agent）：负责沙箱的质量稳定性监控与保障，以及设计 SRE Agent 的子代理编排功能；
  2. 因 SRE Agent 迭代速度较快，需要评测框架对所选用的模型做评测、并验证 Hermes 框架的迭代是否逐步更优、会不会出现退化，于是自己设计了 SRE-Benchmark。产出是 System Prompt 优化：实验环境可削减每个案例 50% 的 token 消耗，实际生产削减 18% 的输入 token、57% 的输出 token、30% 的冗余工具调用；7 月评测 14 个模型、8 月评测 8 个模型，最终上线 Qwen3.8-Max、DeepSeek-V4-Flash-0731、Kimi-K3，把 7 月一开始用的 Claude 跟 GPT 这类国外模型下线。
- 补充：2024 年从太原理工大学考入西安电子科技大学。

### 关键评价点

- 面试官用「哪些是你的、哪些是团队的」开场，是在为后面所有追问建立参照系；本次比一面、二面更主动地交了分工边界（师兄 eBPF、同门文档），可信度好。
- 项目二有现成的硬数字没投放：业务性能损耗 9.66%、准确率较 Eadro 提升 1–2%。本场只说「损耗低于 10%」（赛题要求口径），少了实测值。
- 实习那段把「沙箱保障」放在最前，直接引出了后面第十一节关于"主要工作到底是哪条"的整段质疑——**简历条目的排序会决定面试官的追问起点**。

## 二、LangGraph 选型追问（约 07:24—09:24）

### 面试官问题（引用）

「先从今年 2 月到 4 月你手搓 AI 这个事——为什么当时选择用 LangGraph 来做这样一个运维 Agent？选型的可选范围还是比较广的，为什么选它呢？」

### 候选人回答

- 2 月刚开始对 Agent 的理解还比较模糊，当时主要了解两种构建 Agent 的框架：LangChain 和 LangGraph。
- 他的理解：LangChain 还是链式结构（把 Agent 的处理逻辑变成一个链式结构），LangGraph 可以做成图的结构，更能应对 K8s 与实验室的运维场景。

### 面试官追问与澄清

- 「用 LangChain 你会想到 LangGraph 吗？」→ 候选人：当时想的是 LangChain 比较早期，LangGraph 相对新一点，就直接用了相对新的框架，并且主要就是想做成图的结构。
- 「其实图的结构你这块的逻辑也是比较简单的对吧？」→ 候选人承认「对，比较简单」（4 个智能体：一个中枢 + 三个子智能体）。
- 「这个事情似乎你之前也没有太多了解……什么情况下适合用 LangGraph、适合用 LangChain？」→ 候选人承认原来并不是做 AI 这一块的，AI 兴起之后尝试在对应场景用一下、简单学一下，当时比较急，所以可能比较草率。
- 面试官收束：「就是说至少看起来是刚开始尝试对吧？」候选人：「对对对。」

### 关键评价点

- 这一问的实质是**框架选型是否有技术依据**。候选人的回答停留在「新的 vs 旧的」「链式 vs 图结构」的印象层面，没有回答"为什么这个场景必须是图"。
- 更好的答法：给出图结构的不可替代性——多智能体之间有状态共享、条件分支与回边（一个节点可能被多次进入）、失败可回退重规划，这些用链式编排表达会很别扭。本场实际上在第四节被迫补上了这个论证，但已经是在被质疑之后。
- 「当时比较急、比较草率」是诚实但减分的表述；换成「当时的目标是把闭环先跑通，框架选型是次要变量，事后回看确实应该先做对比」更稳。

## 三、提问-分析-执行-总结闭环的质疑（约 09:24—10:44）

### 面试官问题（引用）

「当时设计考虑的时候是用『提问-分析-执行-总结』这样的一个闭环排障？」「这个闭环实际上是（一个）比较通用的过程」「那你这儿的具体问题是，是面对什么样的问题需要这样的过程来处理？」

### 候选人回答

- 设计目的是辅助实验室的 K8s 集群做运维管理。实验室集群里的一些 Pod 会莫名其妙宕掉，或者因为负载问题宕掉，针对这类集群应用问题就走这个流程：发现集群里某些应用不健康，就让 Agent 去提问、分析、总结。
- 面试官归纳：「就是把原本人工诊断的过程变成 Agent 的诊断。」

### 关键评价点

- 面试官在这里已经把「闭环」定性为**通用套路**，含义是：这个流程换成任何一个领域都成立，所以它本身不构成技术贡献。
- 应对方向有两个：一是给出**领域特异性**证据（K8s 故障的哪些状态量必须拿到、哪一步最容易错、哪一步是人工经验的沉淀点）；二是给出**闭环的收口指标**（定位准确率、平均定位耗时下降多少、建议被采纳率）。本场两者都没给，于是质疑在第四节升级。

## 四、LangGraph 与「自然语言翻译」的正面交锋（约 10:44—14:49）

### 面试官问题（引用）

「其实想要做的这个事情，最主要就是从自然语言到执行命令的一个转换？」「如果是这样的话，用 LangGraph——而且你又做了一个提问到四步的排障闭环——似乎看起来跟这个对应不上。」「如果只是自然语言的翻译过程，其实在今年年初的时候，你只用大模型、比如说其他 Agent，本身就可以完成命令了。」「那 LangGraph 在你从自然语言到命令行的翻译过程当中，它能起什么作用？」

### 候选人回答

这是一段辩护，候选人用 CrashLoopBackOff 实例把数据流讲开了：

- 举例：集群里有个 Pod 出现 CrashLoopBackOff 故障，他向 Agent 提问「检查一下当前集群里有哪些故障，并对故障做分析」，分析完成后给出可行的操作建议。
- 运行逻辑：中枢 Agent 接到指令后先分析，把任务派给 Ops Agent，由它获取集群里的故障信息（日志、Pod 状态、description、YAML），通过集群 MCP 或子 Agent 把信息收集并整合，再交回中枢 Agent。
- 另外还做了 RAG：把 K8s 官方运维文档和 GitHub 上一些开源运维文档做成向量存储，分析过程中会调用 RAG Agent，与 Ops Agent 收集到的故障信息一起做综合分析。
- 中枢 Agent 判断当前分析结果是否满足用户要求，满足就把最终结果与操作建议输出到对话框。
- 结论：所以整个流程还是有一个图的控制结构在，链路过程由 Agent 自己判定执行，一个节点可能运行多次、也可能只运行一次，跟"把自然语言简单翻译成 CLI 命令"不是一回事，中间还要做综合性的问题分析和诊断。

### 关键评价点

- 这是全场最关键的一次交锋：面试官的核心判断是「你想做的事 = NL→命令翻译，那用大模型 + 工具调用就够了，不需要 LangGraph」，候选人的回答只在**最后一句话**才触到要点（节点可多次进入、由 Agent 判定走向），前面的数据流复述对反驳这个问题帮助不大。
- 更有效的顺序：先一句话定义边界（「我要的不是翻译，而是带状态的多步排查：收集→假设→验证→再收集」），再拿 CrashLoopBackOff 举例说明"同一个节点会被反复进入"。这样面试官会把它听成设计论证，而不是辩解。
- 面试官那句「你说做相同的事情、选择更便宜的大模型」式的追问（见第九节）说明他关心的是**成本与效果的权衡点在哪里**——这正好是 LangGraph 式编排能回答的问题（哪些步骤必须强模型、哪些可以用便宜模型）。

## 五、执行环节与能力边界（约 14:49—18:47）

### 面试官问题（引用）

「全部都是提问到分析的过程？执行呢？」「我听起来其实是把状态提上来，然后有一些分析就完事了。」「具体的组件出问题了，或者是代码……做到什么样的力度？」

### 候选人回答

- 执行其实当时并没有做比较好的管理。他对它的限制要求是：从感知、定位到分析、给出操作建议就可以。
- 理由：如果让它真去执行，可能对这个集群的管理反而不方便，甚至产生一些破坏。**当时它其实是有这个权限的，但没让它这么做**，因为觉得还是比较危险。它当时确实也能实现简单的资源管理。
- 能力力度：只做到 K8s 平台层面——Ops Agent 和它的 RAG 能拿到的信息就在集群层面（每个节点的记录信息、每个 Pod 的记录信息、Pod 部署的 YAML），但 Pod 里面实际应用的代码拿不到，所以只能在集群层面做分析，力度比较浅。
- 效果判断标准：给出根因分析和可行操作建议之后，他照着建议去执行能够真的恢复问题；或者至少定位与分析过程能加快他人工定位的过程。当时差不多就到这个阶段。

### 关键评价点

- 「有权限但主动不做」是**加分表述**，但要把它讲成安全边界设计（变更类操作需要人工审批、写操作与读操作分级），而不是"我怕出事所以没做"。
- 力度只到集群层这个答案是诚实的，但依然缺"如何下探"：接 eBPF、应用侧指标、火焰图/pprof 都可行，而候选人项目二里正好有 eBPF 积累却没用在这里。
- 效果标准停留在「能加快我人工定位」这种主观表述。可量化版本：平均定位耗时、需要人工补充的信息条数、建议一次命中率。

## 六、部门职责范围的定义之争（约 18:47—21:56）

### 面试官问题（引用）

「这个基础设施部门是什么……认为的范围？」「我解释一下：如果不清晰你所在这个部门的职责范围，那你所做的这个运维的事情，它的边界范围其实就不太清晰。所以我想了解的是，你在这个部门，它所希望你运维的这个范围包括哪些——比如说是硬件层面的、物理机的、系统资源的、网络的，这些东西某种程度上叫基础设施；也有的把基础架构的一些东西，比如中间件、操作系统等等也叫做基础设施；还有的认为除了我应用之外都叫基础设施。因为每个公司它的叫法不一样。」

### 候选人回答

- 第一遍回答时明显紧张（原话有「因为可能公司有这个保密需求，不知道能不能说」「我感觉有点紧张」），面试官回「不用紧张」。
- 第二遍回答：运维部门只针对千问事业部会用到的业务应用的底层运维。运维团队分了很多小组，他所在的质量小组主要对中间件和 GPU 的模型水位、GPU 与推理服务的指标、包括 RPS 这类指标做水位控制与质量保障。
- 整个 SRE Agent 的设计平台，按面试官提到的口径，覆盖从操作系统、K8s 到中间件、再到业务应用的水位，业务面挺广。
- 但不涉及底层硬件管理——硬件管理还是由对应的云平台下面的团队负责。

### 关键评价点

- 面试官问这个不是为了刁难，而是在**教候选人一件事**：说不清部门职责边界，就说不清自己的运维 scope，也就无法判断 Agent 的价值边界。这个提示可以直接搬到输出话术里。
- 紧张点出在"保密"上：正确做法是**给粒度而非给细节**——「我所在的质量小组负责千问事业部业务应用的中间件与 GPU 相关指标的水位控制与质量保障，不涉及底层硬件」，既回答清楚又零风险。
- 这段还暴露一个信息：候选人自评"对实际运维流程欠缺"是真实情况，但也说明团队分工细，他拿到的是评测/平台这类横向任务。

## 七、Hermes 二开与选型背景（约 21:56—24:07）

### 面试官问题（引用）

「这个 Agent 当时……」「这个项目是开源 Agent 二开的？」「你大概了解为什么当初选了爱马仕（Hermes）？」

### 候选人回答

- 他到的时候项目还在构建过程中，属于在使用中迭代。
- 项目是基于开源 Agent 二开的，改的是 Hermes Agent。
- 选型他不太了解：项目 4 月启动，他到的时候已经是 6 月、他们已经迭代到第六个版本了，这个决策他没有参加。
- 他侧面了解到当时还有另外两个方案：一是 Hermes，二是公司内部（或开源）的另一个 Agent 平台。评估后认为后者的方式不太适合当时"尽快上线"的业务需求；而完全自主搭建 Agent 的工作量比较大——整个团队参与 SRE Agent 构建的也就十个人左右，这十个人各自还有业务运营与质量保障的任务，没有那么多时间专门投入。所以选择比较重型的 Hermes Agent 做二开。

### 关键评价点

- 「选型我没参加」是实话，但面试官真正想听的是**你有没有自己去搞清技术决策的来龙去脉**。可以补一句自己事后的判断（例如：Hermes 自带持久化记忆与规划器，二开改造成本低于自研，这在"十人、半年、要上线"的约束下是合理选择）。
- 反过来看，这也是一次机会：面试官本人对 Agent 框架很熟（见第十四节），这类"框架为什么选它"的问题在后面的轮次还会出现，至少要把 Hermes 相对于自研方案的取舍讲清楚。

## 八、沙箱质量保障与高可用（约 24:07—29:50）

### 面试官问题（引用）

「这个的话主要就是那个沙箱的保障和构建？」「我听下来有点懵……你这样做就能保证它能高可用？」「切换的过程里面说应该复制一些数据或者一些信息过去？」「所以你做的工作就是在需要切的时候，在那边新创建一个，新沙箱的时候在那个新的地方能找到，对不对？」

### 候选人回答

- **部署形态**：Hermes（团队内部叫 SRE Agent）被做成一个**无状态应用**，附属在一个 Agent 运行平台上，在平台上有多个副本，供运维团队内部使用；每个员工一个账号登录。
- **个人工作空间**：每个员工在云对象存储上有自己的工作空间，存放自定义 Skills、自定义 MCP 配置、工作文件与手册。
- **沙箱**：每个员工一个沙箱，落在集团统一的沙箱平台上。创建流程是——员工登录运维平台后，在该平台创建对应沙箱，并把员工在云对象存储上的配置（MCP、Skills、个人文件）全部注入沙箱。
- **跨部门授权**：如果沙箱要用到别的部门、或需要授权的 CLI，Agent 会通过推送机制推到员工的个人客户端上完成授权，授权通过后 Agent 才能拿到 token 去调用被授权应用。
- **生命周期**：沙箱的整个生命周期是 7 天，不管是否在使用，7 天都会销毁重建，这是沙箱平台的要求，没办法。
- **他的保障手段**：Agent 到沙箱之间有一个"连接桥"机制。他先在沙箱平台里，利用平台原有的告警机制挂上对应的沙箱告警；当沙箱出故障（比如集群 DNS 故障、CPU 或内存 OOM）时，通过告警机制推送到他的客户端账号，他据此判断沙箱是不是挂了，挂了的去沙箱平台手动处理。
- **高可用**：本质还是要靠平台侧做高可用部署。他做的举措是：该平台当时有两个沙箱集群（一南一北两地），相当于在两个集群做部署；一开始用其中一个，出现故障就直接切到另一个集群。他做的主要是沙箱这一块的使用质量保证——因为平台的可用性不由他们保证，他们只是让沙箱在 Agent 里出问题时能够快恢、尽量不影响大家使用。
- **切换的数据一致性**：沙箱里所有数据都会同步到云对象存储，所以切的时候只要把沙箱重新创建即可，不需要额外复制数据。

### 关键评价点

- 这段被面试官连续追问了五轮，最终被收成一句「你做的主要是这块工作，对不对？」——说明**表述方式把一件有内容的事讲成了运维杂活**。数据其实都在（无状态 + 多副本、配置注入、7 天重建、告警接入、双集群切换、状态外置到云对象存储），缺的是主线：一句话说清"我保证的是沙箱的可用性与状态可恢复性"，再分点支撑。
- 面试官那句「我听下来有点懵」是明确信号：回答太碎。**遇到系统性问题要先给结论再给细节**。
- 双集群切换这段其实很值钱（故障切换、状态外置、重建式恢复），但因为没有先说清"状态外置到云对象存储、沙箱本身无状态化"这个前提，听起来就像"手动重开一下"。

## 九、Benchmark 设计与模型评测原理（约 29:50—40:24）

### 面试官问题（引用）

「因为刚才你也强调做了这样的 benchmark，然后评测之后去省 token 看出了……那省 token 的原理是说，主要是针对大模型还是 Agent 的？」「那你说如果这个做相同的事情，选择更便宜的大模型？」「这块是你的工作吗？你是怎么考虑的？」「听起来你这选的其实是 Agent 的，并非单纯选大模型？」「假如说现在的问题是让你去判断大模型本身的差异？」

### 候选人回答

- **评测任务分类**：他按业务侧在 SRE Agent 上的真实对话 session 分成三类——① 多轮对话型（不受限制的多轮，可能长到几十条 message）；② 巡检型（定时触发的任务，对指定指标做检查）；③ 告警触发型（由触发器触发的任务）。三类的主要内容都是水位或故障的根因分析、定位与检查，检查结果会推送到对应业务运维的账号上。
- **评测对象**：测的时候保持 Agent 框架不变——测试环境与线上 Agent 使用同一套框架（把线上框架复制一份到测试环境），所以本质上是在测"同一套 harness 下不同模型的表现"。
- **需求背景**：SRE Agent 会有很多子 Agent，但子 Agent 未必需要主 Agent 那么高级的模型，一些针对性的模型就够用——这是模型评测的核心需求。
- **动态基准的做法**：他发现现有的一些 benchmark（如 SWE-bench 这类）大多是搭完全虚拟的环境，Agent 通过 MCP 或 CLI 拿到的数据是固定的；但在他们环境里做不到——MCP 由各业务部门提供，无法把取到的数据做快照固定，而且跨部门协同对实习生来说很困难（每次都要经过主管）。加上平台要尽快在团队内用起来，所以采用了**动态基准**的方式：线上 Agent 用的是 Claude 系的顶级模型（Fable / Opus），实际使用中这些模型产出的答案能够满足运维人员要求，于是把这些答案作为被测模型的参考答案。
- **评分设计**：分两部分——① Agent 执行任务时给用户的实际回复；② Agent 执行任务过程中的工具调用链路（调用了什么工具、顺序、每个工具的调用参数）。因为线上与测试环境 harness 一致，这两部分参考答案在评测里都可用。
  - 第一部分按任务类型设有不同评分标准，用的是 LLM-as-a-Judge；不设约束时评分不稳定。评分标准的提示词还可以通过人工打标不断迭代提升。
  - 第二部分（工具链路）用的是编辑距离算法，规则固定。
  - 两部分加权：实际回复权重 0.7、工具链路权重 0.3。
- **评测指标**：① 任务完成率（即上面 0.7/0.3 的分数）；② 一致性（同一任务执行两三次，回复是否稳定）；③ 工具调用效率（一次任务可能调用二三十个工具，但不是每个都对任务产出有效）；④ 回复的用户友好性（偏主观）。所有案例都是真实运维人员用的 SRE 案例。

### 关键评价点

- 这段是全场信息密度最高的部分，设计是完整的（任务分类 → 动态参考答案 → 双通道评分 → 加权 → 四指标），但**全程没有一句"为什么这样设计"**，因此面试官随即在第十节发起攻击。
- 自觉补强方向：把"动态基准"讲成一个取舍故事——因为拿不到跨部门的数据快照，所以改用线上强模型的输出作参考答案，代价是参考答案本身带模型偏好，收益是能立刻在真实 case 上评测。这样面试官会认为你知道方法论的边界。
- 权重 0.7/0.3 是最容易被追问的点（为什么不是 0.5/0.5？两个通道是否会互相污染？），要准备依据。

## 十、评测指标的 SRE 相关性之争（约 40:24—43:39）

### 面试官问题（引用）

「你刚才讲的这些还是跟 benchmark 做的，跟 SRE 有关系——一定是 SRE 本身它自己稳定性，这个事儿很通用。比如说做别的工作，它也需要这个输出稳定性，比如开发，他每次写代码不能第一次写十行、第二次写两百行，有非常大的偏差。」「从评测的角度来说，你认为什么对于 SRE 的工作、或者 SRE 的 Agent 是最重要的？」「如果这个事儿放在我们这个团队来做，首先我问的问题就是：评测的覆盖度有没有我们日常所运维的日常工作？比如说 SRE 运维它跟别的地方有什么不一样的、它日常干的都是什么？你有做过这种接触吗？你了解 SRE 每周或每天都在干什么？」

### 候选人回答

- 他认为 SRE 任务最重要的是**任务完成率和响应速度**（就是得快）。
- 面试官立即指出"别的也需要，开发测试也需要"，要求针对 SRE 特有的部分。
- 候选人进一步给出 SRE 特色：从**感知 → 定位 → 快恢**这个链路，相对人工走这个流程，用 Agent 是否有比较大的提升——这才是评测的重点。
- 并给出评测点的改造建议：需要重新组织案例，把细粒度的对话 session 总结成「从感知到定位到快恢」这样一条链路作为一个 case，然后评测整个流程的准确性以及链路执行完成的效率。

### 关键评价点

- 前半段被问住了（"完成率和响应速度"确实任何岗位都适用），后半段自救得不错——「感知→定位→快恢」这条链路确实是 SRE 独有，且直接对应评测设计。
- 把这段提前到第九节开头会更主动：先说明"我的评测指标里哪一项是 SRE 特有、为什么"，再讲评分架构，就不会被打成通用套路。
- 面试官暗示的框架是对的：**评测指标必须来自岗位的日常工作**（日常保障 = 监控覆盖/告警频率/水位正常；故障态 = 定位、快恢、拉通、演练、赔付、复盘），这条可以直接固化成话术。

## 十一、SRE 日常与故障处理流程（约 43:39—46:46）

### 面试官问题（引用）

「假如说现在让你描述，当没有故障的时候，他们所做的就是日常的保障——」「当有故障的时候……」

### 候选人回答

- 先说明：当时给他安排的任务并没有让他实际参与到团队的业务运维里，但他能看到他们每天在做什么。
- **无故障时（日常保障）**：看监控大屏上的平台是不是全的、每个故障/告警的频率是否正常、每个水位点在当前资源供给下是否正常。
- **有故障时**：首先对故障做快恢（因为有些故障并不发生在他们这里）；如果确实发生在他们这里，先定位故障在哪里，再做快恢；快恢完成后拉通会议沟通各方，确认故障的爆炸范围与影响范围有多大、对各方的影响点在哪里；收集完之后对故障做演练，包括压力测试——在一些重大节点之前会有拉通的压力测试与资源对齐；主要还是质量稳定性保障；确定爆炸范围和影响范围之后，对影响做总结并走赔付整个流程。
- **对 Agent 的定位**：当前 SRE Agent 没法覆盖整条链路，更多集中在**定位和快恢**这一段，用来加快从感知到定位到快恢的过程。

### 关键评价点

- 这段与二面、讯飞那场的口径一致（快恢、爆炸半径、拉通、演练、赔付、复盘），是候选人最稳的表达，面试官也没有再质疑。
- 可以再往前一步：主动说明「Agent 现在只能覆盖感知→定位→快恢，因为赔付与复盘涉及跨团队信息，Agent 拿不到也不需要拿到」——把边界讲成设计决策。
- 「日常保障」那部分说得略碎（大屏、告警频率、水位），可以归纳成三条可量化的巡检项，直接对上第九节的评测任务类型。

## 十二、省 token 的评估方式（约 46:46—50:20）

### 面试官问题（引用）

「省 token 做的这个事，你们怎么评估出来的？」「按你这个判断说法，是不是你会认为小米比较省 token、GPT 比较费 token？」「你评价这个模型是否省 token，它应该怎么评呢？……比如说小米省了多少 token，这个结论就不太 solid。」

### 候选人回答

- 评测在实验平台上做，参与测试的典型模型主要是 GPT 系与两款国产模型（通义千问、小米）。
- 案例数量是 107 个 case；评测完成后统计平均每个 case 消耗多少 token，并保留所有测试 case 的完整流程（模型回复 + 工具调用链路）。
- 针对 107 个 case 分析这几个模型，发现两类典型行为：
  - GPT 系：在执行任务或工具调用之前会做**环境预先检查**，会调用很多工具（主要是 terminal 类工具）去预先确认环境是否满足任务要求；
  - 小米的模型：没有做重试限制，一个工具调用失败可能会重试七八次甚至十几次，比较浪费 token。
- 于是针对这些模型的特性设计 session parameter 做限定：对 GPT 系，明确不需要预先检查（既然环境是我们提供的，就能保证任务可执行完成）；对重试型模型，最多执行两三次就不要再重试，去考虑别的方案。
- 对面试官"是不是认为小米省 token、GPT 费 token"的反问，候选人的回答是"也不能"，因为两者在这个测试里是**不同的费 token 的方式**。

### 关键评价点

- 这一段里候选人手里其实有**最有说服力的发现**（不同模型浪费 token 的模式不同：一类浪费在过度前置检查、一类浪费在无意义重试），但结论没有收口，反而在"哪个模型更省 token"上被问住。
- 正确收口：把结论从"某模型省 token"改成"**token 消耗与模型行为模式强相关，因此优化点是给 harness 加约束（session parameter），而不是单纯换模型**"——这恰好也是面试官在第十四节给的建议。
- 数字方面，107 个 case 与"平均每 case token"这两个统计量是硬资产，可以再补一个分布口径（P50/P95）以回应"结论不 solid"。

## 十三、运维基础知识拷问（约 50:20—55:27）

### 面试官问题（引用）

「前面我也提到了一些关于你的一些东西……你这儿接触过关于运维的一些基础知识？大概有没有想到——像网络，比如说 K8s 集群的 Pod 之间跨集群链接如果无法访问，它的整个链路应该怎么去综合定位；还有它的 QoS 是怎么样的；比较经典的问题就是这个 CPU 的 load 跟利用率不一样，它应该怎么去定位；像 Linux 网络出现问题，在 Linux 上面、或者操作系统层面应该怎么去定位。」「组件本身 Redis、数据库？」「消息队列这些？」「监控系统本身，我看你是 Prometheus 对吧？」「假如说采集量比较大……假如说现在有上万台机器的样子，会有什么问题？」

### 候选人回答

- 表示这些在平常会用到一些。
- Redis：用得比较少，没怎么用过。消息队列：没怎么了解过。
- 监控：确认用的是 Prometheus。
- Trace 采集：当时用的是 SkyWalking 采集，后面可能会用一个叫 DeepFlow 的东西采集，包括 Jaeger 这些。
- 上万台机器的采集量问题：这个没怎么接触过。他的大概想法是**分层统计收集**——比如分片区或分层，以 1000 台为一个采集的基础粒度，再逐级向上收集。

### 关键评价点

- 这一节是**暴露面最大的一段**：Redis、消息队列、大规规模监控采集全部答"没接触过"，只对 Prometheus 与分层采集有概念。SRE 岗位的基础设施三件套（中间件缓存、消息队列、监控）里有两件是空的，必须提前补课。
- 面试官问"上万台会有什么问题"，其实是在考**规模意识**：标准答案方向是采集端压力与聚合层扩展（Prometheus 单机时序基数上限 → 联邦/分片/远程写入、标签基数爆炸、抓取周期与拉取压力、告警风暴抑制），候选人的"分层采集"方向是对的但太笼统，补一句"分片 + 联邦 + 远程存储"就扎实了。
- 可以主动交底 + 给计划：「中间件这两块我确实是空白，我的补法是 X」——比单纯答"没接触"强。

## 十四、候选人反问与面试官点评（约 55:33—60:59）

### 候选人问题

「我在面试过程中感觉您对模型评测和 Agent 这一块非常了解，想问一下：咱们团队在这一块——比如模型评测——它是一个什么样的现状，或者说是怎么去做这种事情的呢？」

### 面试官回答（引用 + 归纳）

- 承接前面的讨论，面试官给了一个"应该怎么想"的框架：假如现在是在告警的情况下，我需要快速定位、缩小范围、加速出结果——那这种情况下用哪个模型对我来说就是当前的问题；我需要的是它能快速给我答案、且答案准确。
- 然后指出：「但是我听你刚才聊的很多，更多的还是在换模型，似乎别的地方的优化提供很少。我不知道是否实际在做、只是你没有聊到而已，还是说确实你做的所有的工作就是在不停地换模型，然后在跑用例，然后跑完之后出一个报告，大概就这么个事。」
- 进一步：「你还没有聊一个话题，就是什么情况下应该（把它限流/约束）——这个本身也跟执行效率有关系。所以这是一个很泛的话题……这个事情是我听下来最重要的点」。
- 定调：「这个侧重点可能确实是这样，这个没关系，每个团队可能从分工、或者刚开始有一个起点的角度来说。但是你要做你自己做这个事儿本身的时候，你要思考这个问题：我做这个我仅仅只是做换模型这件事儿是否充分、考虑的是否充分。」
- 用监控打比方：「你做监控的话，现在只是让你监控数台机器，跟你监控数万台机器，虽然说可能你当前的工作不涉及，但是你会考虑这件事情，至少说我大概知道遇到这种情况我该怎么办。毕竟咱们做技术的。」

### 候选人回应

- 承认工作流程确实是自己构建平台、让它能出看板，包括发现团队 harness 存在的问题；但实际优化在他离开时团队还没做。
- 补充后期的反思：一开始平台只做到给团队提供参考，很难参与到实际的 Agent 迭代中；到 8 月初（他 8 月底离职，8 月中那会儿）他发现问题并想通了一条路——让平台去发现当前 harness 框架存在的问题，对这些问题做具体分析、给出 harness 框架的优化建议，团队采纳之后形成"评测 → 发现问题 → 给优化建议 → 采纳迭代"的闭环，这是他最后认为能够真正参与到生产里的方式。

### 关键评价点

- 面试官的点评是这一场最有价值的收获，等于直接给出了**下一轮的答题主线**：不要把自己讲成"换模型的人"，要讲成"发现瓶颈并给出优化路径的人"。手上现成的素材就是这两条：① harness 约束（session parameter）能省 token；② 后期设计的"评测→分析 harness 问题→给优化建议→迭代"闭环。
- 候选人最后那段补充说明他**自己已经意识到了**这个问题，只是没有在面试前半段讲出来——这类"事后想通了"的内容应当在被问到时立刻前置，而不是等到收尾。
- 反问本身问得不错（问团队现状），但面试官没有直接介绍团队，而是把话题变成了对候选人的建议——这说明面试已经进入"给反馈"的阶段，也侧面说明这一轮并不乐观。

## 十五、面试整体复盘建议

### 展现出的优势

- **三场快手口径基本自洽**：项目分类、实习分工、故障处理流程（快恢/爆炸半径/赔付/复盘）都与一面、二面保持一致，说明叙事是稳定的。
- **诚信度依旧在线**：主动交底"选型我没参加""实际优化我走的时候还没做""Redis 与消息队列没接触过"，在连环追问下没有硬编。
- **评测设计有真东西**：动态基准、双通道评分（0.7 文本 + 0.3 工具链路）、四类指标、107 个 case、按模型行为模式加 session parameter，这些都是能被追问的实质内容。
- **有自我修正能力**：最后那段"评测→发现 harness 问题→给优化建议→迭代"的反思，说明能从被质疑中提炼结论。

### 需要加强的表达

- **把"做了什么"换成"解决了什么瓶颈"**。面试官整场的核心不满就是"你做的所有工作就是不停换模型、跑用例、出报告"。今后讲实习要先给瓶颈判断，再讲手段。
- **系统性问题先给结论再给细节**。沙箱那一节把面试官听到"有点懵"，是因为按时间流叙述而不是按结构叙述。
- **框架选型要能讲不可替代性**。LangGraph 那一问只答到"新的 vs 旧的"，没能一句话说明图结构相对于链式/纯工具调用的必要性。
- **补齐 SRE 基础设施短板**：Redis、消息队列、大规模监控采集（分片/联邦/远程写、标签基数）这三块是本场被问空的区域，且都是一面的同一薄弱面。
- **评测指标要突出 SRE 特异性**：完成率、一致性、效率、友好性都是通用指标，应主动补上"感知→定位→快恢链路的端到端效率与准确性"这类岗位特有指标。
- **别在收尾才交出最好的想法**：8 月那套 harness 优化闭环的思路应当早些抛出来。

### 一句话总结

这一场面试官从"框架选型"一路追到"你做的事到底有没有价值"，三面聚焦的不再是会不会做事，而是**有没有判断力**；候选人素材足够（动态基准、双通道评分、session parameter、harness 闭环），但叙述顺序让面试官始终听到"换模型 + 跑用例 + 出报告"，下一次要在开口第一分钟就把瓶颈、手段、收益的因果讲出来。
