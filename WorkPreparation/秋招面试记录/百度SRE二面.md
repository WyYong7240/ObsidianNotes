## 二、Agent 多租户隔离与沙箱授权链路（约 05:17—10:17）

### 面试官问题（录音中可辨识）

- “**多个租户之间网络的安全隔离**”
- “（框架）对开源二开的其实是 **HermesAgent**”

### 候选人回答

**Agent 服务形态与用户空间**

- Agent 本质上是一个**公用的无状态服务**，以 **5 个 Pod** 的形式部署在云上。
- 每个员工的工作文件不同，因此每人有独立**工作空间**，工作空间存放在**云对象存储**上。
- 多租户通过**沙箱**隔离实现；沙箱与 Agent 平台**不在同一个云平台**上，而是部署在另一个平台。

**首次使用的授权与沙箱创建**

1. 用户首次使用时先授权：Agent 给出授权链接，或利用自身 Skill / MCP 能力把授权链接推送到员工的**客户端**；
2. 员工在客户端完成授权后，Agent 才拿到授权，并在另一个平台创建该员工的沙箱；
3. 创建沙箱过程中，把该员工云存储个人空间中的 **Skills、MCP 配置、工作文件**注入沙箱；
4. 沙箱有**生命周期限制：最长保留 7 天**，到期后无论是否在用都要销毁重建。

**CLI 的二次授权**

- 因为会用到不同业务部门的 **CLI**，而这些 CLI 需要以员工身份授权，所以采用同样的机制：
  - Agent 执行任务时若需要授权某个 CLI，会提示用户授权，并把该 CLI 对应的授权链接推送到客户端、邮箱或其他信息渠道；
  - 员工在对应渠道授权后，Agent 才能拿到授权信息并正常使用该 CLI。

**沙箱网络隔离（面试官追问）**

- 沙箱可以理解为一个应用 Pod，但与 HermesAgent / SRE Agent **不在同一个集群**部署。
- 就 SRE 团队而言，沙箱是部署在**另一个业务部门为整个集团提供的基础平台**上；
- 本团队只能通过平台链接访问对应沙箱，**具体的网络隔离方式与沙箱创建流程并不由本团队实现**，属于集团公共沙箱环境的能力。

### 关键评价点

- 能清楚区分“共享无状态 Agent 服务”与“用户独立沙箱”的边界，与快手一面答述一致。
- 授权链路讲得完整（客户端授权 → 沙箱创建 → 云存储内容注入 → CLI 二次授权），细节比前几场更充分。
- **风险点**：被问“租户间网络安全隔离”时只回答“这块不是我们团队做的，是集团公共平台”——如实但**没有体现出对该平台隔离机制的了解**。建议补一句“我了解到的实现方式大致是……（Namespace / VPC 隔离、NetworkPolicy、权限最小化、逃逸防护）”。
- 沙箱 7 天重建是一个很具体的工程细节，值得继续准备“为什么是 7 天”“重建时状态如何迁移”。

## 三、评测数据来源与 System Prompt 优化的线上效果（约 10:17—14:06）

### 面试官问题（根据回答还原）

SRE-Benchmark 的评测 case 从哪里来？优化在生产环境中的实际效果如何？

### 候选人回答

**评测 case 的来源**

- 所有 case 都是从**业务运维人员以及参与 Agent 构建 / 使用的所有对话**中摘出来的；
- 所有人使用 Agent 的对话（session）都会在云上被记录；
- 因此最终选用的 case 都来自这些**真实 session**。

**初期基线数据**

- 7 月初进行了一轮测试，涉及 **14 个模型**；
- 当时每个 case 的平均 Token 消耗约 **114 万**；
- 原因是当时整个 harness 构建得比较随意，Skill 有自进化效果，**共堆积了 303 个 Skill**；
- 导致初期 Token 消耗极高，也伴随较多冗余工具调用。

**问题定位与优化**

- 测试后发现部分 case 的 Token 消耗显著高于其他 case，工具调用出现**死循环**；
- 针对这些情况做具体分析，产出**针对 Token 消耗与工具调用的 System Prompt 优化**；
- 优化后每个 case 的平均 Token 消耗**降至约 63 万**。

**实验室平台 vs 生产环境的差异**

- 平台测试结果：减少 **50%** Token 消耗、**30%** 冗余工具调用；
- 但把优化后的 Prompt 上线到**生产环境**后，效果有所降低：
  - 线上统计口径：所有 session 的 Token 分为**输入 Token** 与**输出 Token**；
  - 一天约有 **3000 多个 session**，统计总消耗（几亿 Token）、平均每个 session 的 Token 消耗与工具调用次数；
  - 引入优化后：**输入 Token 降低 18%**、**输出 Token 降低 57%**、**工具调用降低 30%**；
- 候选人向团队的业务运维人员求证，使用体验**没有明显打折或明显影响**；
- 因此判断这次 Prompt 优化是有效的。

### 关键评价点

- 这是本场最有价值的一段：**主动披露“实验室 50% 与线上 18% / 57% 的口径差异”**，说明有实测意识，不容易被追问击穿。
- 需要提前准备：
  - 为什么输入 Token 只降 18% 而输出 Token 降 57%（是否为工具返回内容压缩 vs 模型输出精简）；
  - “3000 个 session / 几亿 Token”的统计时间范围与样本量；
  - “使用体验没有明显打折”的依据（主观反馈还是有人工评分样本）；
  - 114 万 → 63 万是单轮平均还是全流程平均。

## 四、Benchmark 构建难点与“动态基准”方案（约 14:06—20:28）

### 面试官问题（根据回答还原）

构建这个 Benchmark 的难点是什么？怎么解决的？

### 候选人回答

**两个约束**

- 主管和 manager 的要求：**尽快上线**为业务所用（迭代频繁）；
- 同时评测要**准**，这是 Benchmark 的最基本要求。

**难点：行业主流做法是构建完全虚拟的实验环境**

- 调研发现市面与开源方法多为构建一个**完全虚拟的 Benchmark 实验环境**；
- 例如已有的 SRE 领域 Benchmark，给 Agent 搭一个“虚拟世界”，让 Agent 对这个世界做修改，再验证修改是否正确；
- 但对当时的业务部门而言实现难度大：还需要提供 MCP 的业务部门给出对应**快照**，沟通协调与平台开发成本都非常高。

**方案：动态基准（Dynamic Baseline）**

- 用线上 SRE Agent 实际使用的模型 **Claude Fable 5** 作为基准；
- 该模型经过验证，性能与实际回复质量均满足业务运维要求；
- 于是把该模型**对同一个 case 的官方回复**作为评测基准；
- 基准被拆成**两部分**：

  1. **实际回复内容** → 结构化后交给 **LLM 裁判打分**
     - 实际运维任务分为三类：
       1. **多人对话**：对话轮次不限制，包括让 Agent 做修改、查询、过程分析等；
       2. **定时任务（定时巡检）**：通常一到两轮回复；
       3. **触发器**：基本是故障定位或过程分析类；
     - 每类任务评价标准不同。以**故障定位**为例，要求回复分三段：
       1. 总结性结论——故障原因到底是什么；
       2. 数据支撑——获取了哪些数据、凭什么据此定位到该原因；
       3. 可操作建议与注意事项；
     - 被测模型的回复同样结构化后，与参考答案一起交给 LLM 评分；
  2. **工具调用序列** → 用**编辑距离算法**做相似性匹配
     - 允许同一任务的工具调用序列不完全一致；
     - 但要求**关键工具调用必须出现**，且传入参数要大致相同；
     - 相似度越高得分越高。

- 综合两部分给出该模型回复的质量评分，最终形成排名；
- 验证结果：该方法能够**把不同性能的模型有效区分开**。

**最终排名（8 月 13 日那轮）**

- 排名最高的是 **Qwen3.8** 与 **Kimi K3**；
- **DeepSeek V4 Flash 0731** 速度偏快，但整体 SRE 性能略低于前两者。

**面试官追问：纵向对比**

- 面试官问：也可以纵向比较同一模型在不同 harness 框架下的性能是否有明显提升或保持稳定？
- 候选人答：这个功能也有，但平时用得比较少。

### 关键评价点

- **动态基准是本场最亮的设计**：明确对比了“虚拟环境派”的成本问题，并给出可落地的替代方案，取舍逻辑清晰。
- 同一套方案在百度一面也讲过，本场补充了**评分细节**（三段式结构、编辑距离匹配、LLM 裁判），回答质量明显更高。
- 需要准备的追问：
  - LLM 裁判用哪个模型、多轮打分一致性如何保证、是否做过人工校验；
  - 编辑距离的**阈值**如何设定、“关键工具”如何定义；
  - 基准模型自身出错时，错误是否会被固化；
  - “纵向对比用得少”是明显减分点——harness 迭代验证恰恰是平台的两大目标之一，建议准备一次具体案例。

## 五、实习分工与子 Agent 编排（约 21:21—24:41）

### 面试官问题（根据回答还原）

你在 Agent 运维这块具体负责什么？子 Agent 编排是怎么设计的？

### 候选人回答

**个人职责**

- 主要工作是辅助 SRE Agent 的构建，自述“内容相对较少”：
  - **沙箱方向**：负责质量与稳定性的保证；
  - **子 Agent 编排方向**：设计方案并推动实现，讨论方案是否可行。

**子 Agent 编排方案**

- 使用了**预构建的 Agent**：Agent 默认带有 **4 个团队预构建 Agent**；
- 主 Agent 通常**不会新建 Agent**，而是优先复用已有的预构建 Agent；
- 每个用户还可以根据自身情况**自行创建** Agent；
- 因此每个用户大致是“默认 4 个预构建 Agent + 自己构建的 Agent”。

**任务分派机制（HermesAgent 原生能力）**

1. **DelegateTask**：把不同任务派发下去，等待各 Agent 返回；若某 Agent 未按时返回，会提示用户该 Agent 出错或延迟返回，由用户决定是否重试；实际使用中很少出现；
2. **看板方式**。

- 若子 Agent 处理不了任务，会直接向主 Agent 反馈“能力缺陷”或“需要授权”，主 Agent 再把信息返回给用户。

### 关键评价点

- 如实说明个人职责范围，没有夸大，可信度好。
- “主 Agent 优先复用预构建 Agent”是个好设计点，可以进一步说明**为什么这么设计**（成本、可控性、评测一致性）。
- 需要准备：4 个预构建 Agent 分别是什么、看板方式与 DelegateTask 的取舍、子 Agent 失败后的兜底与超时策略。

## 六、Kubernetes 控制面组件与资源变更流程（约 24:41—29:13）

### 面试官问题（录音中可辨识：“**本来是做 K8s 基础组件**”“**为什么这么做**”）

### 候选人回答

**控制面组件**

- **API Server**；
- **etcd**；
- 网络组件，候选人表述为“类似 kube-proxy 这种网络组件”；
- **kube-controller-manager**：资源控制组件，内部包含 K8s 各种默认资源的控制器；
- **kubelet**：每个节点上各有一个；
- **CoreDNS** 或容器运行时等基础组件。

**创建 Deployment 的完整流程（候选人自述）**

1. 以 `apply YAML` 的方式向 **API Server** 发起请求；
2. API Server 先对请求来源做**认证**，再做**准入控制**；
3. 通过后写入 **etcd**；
4. 写入的同时，把变更事件推送给对应资源的 **Informer** 机制；
5. Controller 通过 **List-Watch** 监听到事件变更；
6. Controller 调用对应的 **Reconciler**（调谐器，含自定义 CRD 的 Reconciler）；
7. 资源变更最终落到对应节点；各节点的 **kubelet** 内也有对应的 Informer / Controller 组件。

**面试官追问：“为什么这么做？”**

- etcd 本身具备分布式一致性共识；
- 如果组件（尤其是数量众多的 kubelet）**直接访问 etcd**：
  - 会有一致性问题；
  - 访问量会非常大；
- 直接访问 API Server 有时访问量也很大；
- 更重要的是**合法性校验**：直接访问 etcd 无法验证
  - 创建者是否合法；
  - 创建者是否具备对应 **RBAC** 权限；
  - 即使有权限，所创建资源的**字段是否合法**；
- 因此必须在写入数据库前通过 API Server 做**准入性验证**，例如 **Mutating / Validating Admission Webhook**，验证通过后才能进入 etcd 完成变更。

### 关键评价点

- 这一段比百度一面的同题回答**明显进步**：不再把 kube-proxy 说成 DNS，并补上了 List-Watch、Reconciler、RBAC 与准入链路。
- 仍需注意：
  - kube-proxy 的作用应表述为“**Service 的转发规则（iptables / IPVS）**”，而不是笼统的“网络组件”；
  - “写入 etcd 后把事件推送给 Informer”这个说法不准确：API Server 写 etcd 成功后是通过 **watch cache** 把事件下发给各组件，而 Informer 是 **client-go 侧的本地缓存 + 事件分发机制**；
  - “为什么要走 API Server”这段答得很好（RBAC、字段合法性、削峰），是可以直接复用的加分回答。
- 建议补上 **kube-scheduler 在流程中的位置**（Pod 创建后由调度器绑定节点）——这是本题最常见的追问点，而候选人本人写过调度插件，这里应该拿分。

## 七、设计题：给工作负载注入 sidecar 的两种实现（约 29:13—32:34）

### 面试官问题（录音中可辨识：“**那个微服务网关框架是吗**”）

（结合上下文，面试官问的是：如果要给指定工作负载注入 sidecar / 网关代理，你会怎么设计？）

### 候选人回答

候选人给出两种思路：

**方式一：自定义 CRD 资源**

- 把 sidecar 与 Pod 的对应关系，或 **Istio** 服务网格对应的组件 / 程序，做成一个**独立的 CRD 资源**；
- 为该 CRD 编写自己的 **Controller 与 Reconciler**；
- 在 Reconciler 中创建对应 Pod 时修改其 YAML 配置。

**方式二：MutatingWebhook 自动注入**

- 创建对应的 **Webhook**：在服务创建过程中自动注入对应标签；
- Webhook 首先检测 Pod 创建时携带的标签；
- 若存在对应标签，则通过 **MutatingWebhook** 机制，在写入 etcd **之前**修改该 Pod 的配置，为其**添加一个 sidecar 容器**；
- 修改完成后再进入 etcd，走后续的 Pod 创建流程；
- 最终这个 Pod 启动时会默认带一个 sidecar。

- 候选人自评：“**第一种方式比较重**。”

### 关键评价点

- 两条路径都说到了，且抓住了关键点——**注入要发生在写入 etcd 之前**，这正是 MutatingWebhook 的定位（与上一节“为什么要走 API Server”的回答形成呼应）。
- 这也正是 Istio 的做法（`istio-injection=enabled` 标签 + sidecar-injector MutatingWebhook），方向正确。
- 可以继续补强：
  - 明确对应 **MutatingAdmissionWebhook** 的准入阶段（Istio 侧就是 `istio-sidecar-injector`）；
  - 注入的**幂等性**（已注入的 Pod 不重复注入）与失败策略（`failurePolicy: Fail / Ignore`）；
  - CRD 方案更接近 Operator 模式，适合“声明式声明需要代理”的场景，但要自己维护 Reconciler 的调谐逻辑；
  - 补一句“生产上通常选 Webhook，因为它对业务 YAML 零侵入”——这是面试官想听的取舍结论。

## 八、候选人反问与 AI 工具使用（约 32:57—38:34）

### 候选人问题

- 询问对方团队 SRE 的工作内容主要涉及哪些方向，以及 AI 相关的情况。

### 对话要点

- 候选人讲述了自己在 AI 工具上的使用习惯：
  - 在学校主要使用**开源方案**：
    1. **Codex**，用于较复杂的任务；
    2. **Reasonix** 搭配 **DeepSeek** 模型，处理轻量任务；
  - 在公司：正式员工使用经过合规审查的 Claude 与 Codex，但大部分员工实际使用的是阿里自建的 AI coding 平台 **Qoder / Qoder Work**。
- 面试官追问评测相关问题，候选人回应：
  - 最初构建 Benchmark 平台时也遇到过同类问题——让模型按平台标准去评 case 时，**标准本身可能不太合适**；
  - 这种情况仍需要**人工打标与人工评分**机制，并给出不同评分理由，让模型学习；
  - 但**成本太大**，所以后续使用得比较少。

### 关键评价点

- 关于“LLM 评分标准不靠谱 → 需要人工打分校准”的回答很实在，正好补上了第四节“LLM 裁判”方案的已知短板，是加分点。
- 反问可以更具体：团队 SRE 的职责边界、Agent 是否已上生产、on-call 强度、岗位日常更偏“运维”还是“AI 平台建设”。

## 九、面试整体复盘建议

### 展现出的优势

- **同一套项目，这场讲得比百度一面深一个层次**：动态基准给出了三段式结构化 + 编辑距离匹配的完整评分设计，而不只是“用强模型当参考答案”这一句。
- 主动披露“实验室 50% → 线上 18% / 57%”的口径差异，体现了实测意识与诚实。
- Kubernetes 基础题明显补强：List-Watch、Reconciler、RBAC、Admission Webhook 都能说清，“为什么要走 API Server”这一段答得尤其好。
- sidecar 注入设计题方向正确，抓住了“写入 etcd 之前注入”这个关键点。

### 需要加强的表达

- **数字口径要统一并说明范围**：模型评测数量（14 个 / 8 个）、单 case Token 消耗（114 万 → 63 万）、Token 削减（平台 50%，线上输入 18% / 输出 57%）、工具调用削减（统一按 30%）在不同场次的说法要固定，并说清统计窗口。
- **沙箱隔离的“不知道”要补**：被问租户间网络隔离时只回答“不是我们团队做的”，建议至少补上你了解的机制（Namespace / VPC 隔离、NetworkPolicy、权限最小化、逃逸防护）。
- **harness 纵向对比要举例**：这是平台的两大目标之一，“平时用得少”会削弱说服力，建议准备一次具体案例（同一模型换 harness 后指标变化）。
- **子 Agent 编排要讲设计动机**：4 个预构建 Agent 的选型依据、DelegateTask 与看板的取舍、失败兜底策略。
- **专有名词首次出现给全称**：HermesAgent、DelegateTask、Istio、MutatingWebhook 等口述时先给定位（如“开源的 HermesAgent 二开”）。

### 一句话总结

这一场是同一批项目的深水区追问，候选人在评测体系设计与 Kubernetes 基础上都有明显进步，动态基准、准入链路、sidecar 注入三处回答质量较高；主要短板是量化口径在多场之间不统一，以及在被问到“不属于自己负责”的模块时缺少可展示的理解深度。
