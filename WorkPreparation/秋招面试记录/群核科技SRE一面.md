## 一、开场与评测框架的六个维度（约 00:34—02:42）

### 面试官问题

面试官开场自我介绍后，直接从简历切入：
> "我看你做的比较多 Agent 相关，在前文实习的时候……那个生产 Agent 覆盖了六个维度的模型测评对比，可以说一下是哪六个维度？"

### 候选人回答

六个维度（候选人说明"比较常见"）：

1. **SRE 任务完成率**——某个 case 交给模型 + 这套 Harness 框架后能做到什么程度；
2. **一致性**——同一个 case / 任务让 Agent 执行多次，结果会有差异，因此要检测每次结果的一致性；
3. **工具调用有效率**——每个任务交给 Agent 执行时会调用很多工具，不能保证每次调用对结果产出都有用，需要检测有效率；
4. **回复的用户友好性**（偏主观）——以根因定位类问题为例，规定不能一上来就给一堆分析，而是"先给总体性结论 → 再给数据支撑与信息分析 → 最后给总体性结论和可行操作建议"这样的结构性回复；
5. **Token 消耗**（客观）——完成每个 SRE 任务消耗的 Token；
6. **模型的平均响应时间**（客观）。

候选人补充：前四个是相对重要的维度，后两个是客观指标。

### 关键评价点

- 面试官**直接拿简历上的一句话发问**，说明简历里的"六个维度"是显性抓手——越是这样的表述，越要能在 30 秒内说清六个维度分别是什么、为什么是这六个。这次回答结构清楚（先说四个效果/过程维度、再说两个客观维度），节奏没问题。
- 唯一可挑的是**顺序**：把"完成率、一致性"这类结果维度放前面是对的，但"用户友好性"这种偏主观的维度夹在中间容易被追问"主观维度谁来打分"。建议主动衔接："主观维度我们用 LLM as Judge + 人工打标校正"，提前把下一问的答案铺好。

## 二、多租户与沙箱方案（约 02:42—04:11）

### 面试官问题

> "这里提到你这个平台是多租户的吗？" → "那一般多租户的话，底层一般都会用 Sandbox……沙箱的方案是用什么？"

### 候选人回答

- Agent 本身作为**无状态应用**部署在云集群上。
- **沙箱由集团提供的基础沙箱平台**承载。
- 每个用户有一个**工作空间，存放在云对象存储**上；用户使用**员工身份登录**，登录后沙箱平台为该用户在沙箱平台开一个沙箱。
- 沙箱创建时会**默认注入**员工在对象存储上的信息：自定义 MCP、个人 Skills、个人工作文件、运维手册、业务知识库等，全部位于个人空间。
- 沙箱有**生命周期限制：平台规定 7 天**，不管是否在使用，到期都要注销并重新开启。

### 关键评价点

- 与百度那场的口径完全一致（无状态 Agent + 一人一沙箱 + 工作空间持久化 + 7 天生命周期），这条主线三场都能对上，说明是真实架构而非临时编的。
- 还可以补两点让回答更完整：**沙箱内是否限制出网/是否可以任意访问公网**、**对象存储与沙箱之间的注入是挂载还是同步**——这两个问题很容易被追问，提前准备好会更稳。

## 三、主观指标的评分机制与人工打标（约 04:11—06:24）

### 面试官问题

> "这个主观性的判断是你们自己判断的，还是谁来做这个评估？"

### 候选人回答

- 最麻烦的是**任务完成率**这一维度。
- 说明归属：**整个平台都是候选人一个人设计的**，设计经过团队评估后采用。
- 采用方案是 **LLM as Judge**：让大模型进行评判。SRE 任务被分成三类——**多轮对话、巡检任务、告警触发（故障定位）**，每类有各自的评分标准；评分标准以系统提示词或附加文件的方式放进评测框架，由模型按评分提示词与标准给不同任务类型打分。
- 针对一些特定任务，模型评分并不尽如人意，因此增加了**人工打标机制**：对不满足要求的评分进行人工打标并给出理由，让评分提示词**自学习、迭代更新**，逐渐达到与人打标相当的效果。

### 关键评价点

- "评测器本身也要被评测"这个意识很加分，与前面几场的口径一致；这里比之前讲得更细（评价标准做成系统提示词/附加文件），说服力更强。
- 可以补一句人工打标的**触发条件与规模**（例如"约每 N 条出现一次、主要由我本人打标"），把"有机制"升级成"有成本意识"。

## 四、运行效率优化与两周上线（约 06:24—09:18）

### 面试官问题

面试官顺着简历中"运行效率优化"的表述追问优化做法与效果指标。

### 候选人回答

- 时间是 7 月底，此时已花了一个多月把评测框架搭起来；**测试用例全部来自生产环境**——业务运维与普通运维人员实际会问到的问题。
- 评测发现的模型差异：
  - **GPT 类模型**：每次工具调用之前会做一次预检查，产生冗余消耗；
  - **部分模型**：工具调用失败后会无限或多次重试，造成冗余调用与时间浪费。
- 针对这些情况做 **System Prompt 层面的限制**，先在测试平台验证：
  - 每个 case 削减**将近 50%** 的 Token 消耗；
  - 削减**近 30%** 的冗余工具调用；
  - 具体幅度：原本每个 case 约 114 万 Token 降到 60 多万；原本每个 SRE 任务要调用 30 多个工具，验证后降到 20 多个（20 个左右）。
- 验证有效后**花两周上线**：第一周在预发环境验证，第二周上线线上。
- 上线后后台统计（分两部分）：**输入 Token 削减 18%、输出 Token 削减 57%、冗余工具调用削减 30%**，达到预期。
- 因为担心影响使用体验，上线后做了**调研**问同事使用体验有无明显变化或不适；反馈普遍挺好，原本冗余的分析与输出消失后信息更精简，大家认可这次优化。

### 关键评价点

- 这是本场最完整的一段：**问题发现 → 现象归因（两类模型偏好）→ 针对性优化 → 平台验证 → 分环境上线 → 回访体验**，闭环清晰，值得作为固定话术。
- 数字讲成了"约 50% / 近 30% / 114 万→60 多万 / 30 多个→20 多个"这种带区间的表达，比咬死精确数字更稳，符合"按幅度"的口径。
- 可以补一句**为什么这两类模型会有这种偏好**（预检查是模型自身的安全倾向、重试是无失败上限约束），从"观察到现象"升到"理解成因"。

## 六、K8s Agent 的由来与 Hermes 选型（约 09:53—13:46）

### 面试官问题

面试官询问该 K8s Agent 项目的定位，以及实习项目为什么选择 Hermes 而不是自己搭框架。

### 候选人回答

- 项目定位坦诚：这个 K8s Agent 相当于是**自己练手**，顺便为实验室做一个运维 Agent——实验室的运维工作主要由候选人与其同门承担，希望借此提效。
- **Hermes 选型的背景**：千问事业部的 Agent 是 4 月立项、候选人 6 月入职，**选型时他并未参与**；后来了解到当时涉及两个方案——集团内部的 **iAgent**，以及最终采用的**基于开源 Agent（Hermes）二次开发**。
- 选择原因（从需求倒推）：
  - 团队当时想要的效果是**快速上线、快速验证**，看能否带来明显提效；
  - Agent 的开发由**运营团队**人员承担，团队共约 **12 人**，每个人都有自己的本职工作，属于**并行开发**；
  - 如果用 LangGraph / LangChain 从零构建，工作量和上线周期都很大，**无法满足"快速上线验证原型"的目标**。
- 什么时候 LangGraph / LangChain 更适用：当对 Agent 有**明确而具体的需求**（例如需要特定的子代理编排机制、特定的 Workflow 编排流程），而当前开源 Agent 无法满足时。举例：Hermes 到后期**越改越臃肿**，运行效率明显下降；Hermes 原本**不支持 MCP 与 Skills 懒加载**，这是他们自己后加的。所以 LangGraph / LangChain 更适合**高度自定义化**的 Agent 开发需求。

### 关键评价点

- 这一版的选型回答是**目前三场里最完整的一次**：既有"我没参与决策"，又有"从工程约束上可以理解"，还给出了"什么条件下该换 LangGraph"的判据——这正是三面常考的"能否理解技术决策背后的 Trade-off"。
- 建议把"12 个人并行开发、每人有本职工作"与"Hermes 越改越臃肿"这两条固定为核心论据，它们比"自研成本高"更具体。
- 小提醒：讲"越改越臃肿"时可以顺带给出**你们自己补的能力**（MCP / Skills 懒加载），把"框架不行"转成"我们在框架之上做了增量"，避免听起来像在抱怨选型。

## 七、CrashLoopBackOff 的排查流程（约 13:46—15:35）

### 面试官问题

> "可以说一下你觉得遇到这个状态的时候，它大概的分析流程是怎么样？"

### 候选人回答

以人工经验视角展开：

1. 用 **kubectl describe** 检查 Pod 当前状态，判断是什么引起 CrashLoopBackOff（资源问题还是其他原因）；
2. 先确认**集群层面**无异常——节点、网络、CPU/内存资源、IO 与磁盘资源；
3. 集群无异常则**深入容器内部**：用 **kubectl exec** 进入 Pod、用 **kubectl logs** 查看日志，从日志层面看运行过程中什么问题导致不断重启（"启动之后迅速挂掉"）；
4. 最终可能定位到**应用代码层面**，看是哪段逻辑导致启动后立即退出，定位后修复。

### 关键评价点

- 这条"集群层 → 容器层 → 代码层"的三段式排查路径讲得很干净，是 K8s SRE 面试的标准答法，建议**主动加上每一层的具体命令**（`kubectl describe pod` / `-o yaml`、`kubectl logs --previous`），把口头流程变成可执行步骤。
- 建议补一个**从"现象"到"层"的映射**：Pending → 调度/资源；CrashLoopBackOff → 应用启动失败/探针；ImagePullBackOff → 镜像与仓库；OOMKilled → 资源限制。这类映射最能体现熟练度。

## 八、Liveness Probe 报错的判别与 127.0.0.1 追问（约 15:35—18:34）

### 面试官问题

- "Event 里显示了 Liveness Probe 探针失败，那我怎样区分是应用启动慢，还是探针配置不合理？"
- 追问："在探针里面配的地址是 127.0.0.1 是吗？……你想一下这个探针执行的过程是怎么样、谁来执行？"

### 候选人回答

- 区分手段一：**启动慢**可以加 **Startup Probe**，避免容器启动慢导致 Liveness（存活）探针过早介入、直接判定失败；
- 区分手段二：如果 Startup Probe 没问题，就检查 **Liveness Probe 的探测方式**（HTTP Probe / TCP Probe），**人工按同样方式探测**验证；若在容器/Pod 层面人工验证是通的，则说明是**探针配置方式错了**。
- 对 127.0.0.1 的追问：候选人思考后回答——探针由 **kubelet** 执行；如果在探针里配 127.0.0.1，可能会探到 kubelet 本地对应端口。

### 关键评价点

- 这是本场**唯一被问住的点**。正确口径是：HTTP / TCP 探针由 **kubelet 发起，但走的是 Pod 的网络命名空间**（kubelet 通过 podIP / 容器网络访问），所以 `127.0.0.1` 指的是**容器自身**，通常没问题；真正的坑在于：**exec 探针**才是在容器内执行命令（`127.0.0.1` 同样是容器内部）；而当探针写成 `localhost` 或配错端口/路径、或容器监听在非 127.0.0.1（例如只监听 podIP 或 IPv6）时才会判失败。建议复习：**三类探针的执行主体与网络命名空间**、`initialDelaySeconds` / `periodSeconds` / `failureThreshold` 的取舍，以及**探针导致的重启循环如何用 `--previous` 日志区分**。
- Startup Probe 这条答得很对，是加分点；可以把三者关系一次讲清：**Startup 管启动、Readiness 管流量摘挂、Liveness 管重启**。

## 九、eBPF 监控接入与分工（约 18:34—19:38）

## 十、根因分析算法：三模态特征融合（约 19:38—22:35）

### 面试官问题

> "你做那个根因分析这一块，这个根因分析大概是怎么做？"

### 候选人回答

- 这是项目的**第二个算法**（第一个是异常检测），本次重点讲根因分析。
- 数据采集：
  - **指标**：Prometheus 采集 CPU、内存、网络 IO，以及 eBPF 层面的 IO 相关指标（时序数据）；
  - **日志与调用链**：使用 **Jaeger 或 OpenTelemetry** 采集微服务框架的日志与 Trace；
  - Trace 数据写入 **Elasticsearch**。
- 特征提取（按模态分别处理）：
  - **时序指标**：用**时序分解 + 自相关**机制提取周期性特征与突发性特征；
  - **日志**：先做日志模板提取，剔除重复的 info 类模板，保留各模板的出现频率作为特征统计；
  - **Trace**：把调用链路做成**图网络融合**。
- 融合与定位：三类特征做**多目标融合**后，对大约 **40 个微服务节点**形成一个矩阵，再基于图网络与多目标融合的学习机制，得出每个微服务节点/应用的异常概率或异常程度，输出**排名**，排名最高的节点作为根因分析结论。
- 明确粒度边界：结论定位在**微服务/应用节点层面**，不能下钻到代码层面。

### 关键评价点

- 这是本场技术含量最高的一段，三模态（指标/日志/Trace）各自的特征提取方法都讲到了具体机制，可信度很高。
- 主动交代**算法粒度的边界**（"只能到微服务节点，不能到代码行"）非常成熟，面试官一般会认可这种边界意识；可以再补一句"因此我们把它定位为**缩小排查范围的工具**，而不是替代人工定位"，把边界转成产品定位。
- 建议补上**与 Eadro 对比的 1%—2% 提升**以及**业务性能损耗低于 9.66%** 这两个简历上的硬指标——本场完全没提到，白白浪费了简历里最能量化的两条。

## 十一、编程题：三线程交替打印 ABC ×10 轮（约 22:35—41:33）

### 面试官问题

> "每个线程分别输出一个字母，然后实现一个交替打印的效果……你觉得 OK 的话，可以再加一个终止条件，就是打印十轮。"

三个线程分别输出 A、B、C，交替打印出 ABC 的顺序，循环十轮。

### 候选人回答（思路阐述）

- 语言选择 Go（候选人熟悉的语言）。
- 整体思路：
  - 用 **`sync.WaitGroup`** 控制每个 goroutine 的生命周期；
  - 用**管道（channel）**控制 ABC 的输出顺序；
  - 主函数里先向 A 的管道发信号让它输出 A，A 输出完成后通知 B，B 完成后通过管道通知 C 输出 C；这样只要主函数给一个初始信号，就能得到 ABC 的循环输出；
  - 循环十次结束后，调用上下文相关的工具把每个 goroutine 关闭。
- 候选人自述**语法细节记不太清**，编码过程在录音里表现为较长静默（约 22:35—40:44）。

### 关键评价点

- 思路是对的（channel 令牌传递 + WaitGroup 管生命周期正是 Go 的标准解法），但**卡在语法上花了将近十分钟**，这是本场最明显的短板。建议把这类题写成肌肉记忆，例如**用三个 channel 串成环**：
  - `chA`、`chB`、`chC` 三个 channel 组成 A→B→C→A 的传递环，每个 goroutine 从自己的 channel 取令牌、打印、再把令牌递给下一个；
  - 主 goroutine 先把令牌放进 `chA` 启动链条；十轮结束后关闭链条或用 `context` 取消，`WaitGroup` 等待三个 goroutine 退出。
- 面试时可以主动说明**风险点**（避免听起来只是背过）：一轮结束后必须保证令牌回到 `chA`、`close` 之后 goroutine 不会阻塞永久、循环次数用计数器而非依赖外部状态。
- 复盘建议：把 Go 的 `sync` 包（Mutex / RWMutex / WaitGroup / Once / Cond）、channel 的关闭与 `select`、`context` 取消这三个主题各手写一到两道题，这类"多线程交替打印"是 SRE / 后端一面的高频题。

## 十二、候选人反问：团队业务与 AI 化现状（约 41:33—45:17）

### 候选人问题

- 团队的运维开发任务与业务内容主要有哪些？
- 部门业务流程 / 任务 AI 化的状态与现状如何？

### 面试官回答

- 运维侧除面向 B 端的软件外，还包括 DNS、负载均衡等传统软件，以及虚拟化、压测之类的系统。
- 另一块偏向 **AI Infra**：因为公司是 AI 公司，**如何让 GPU 高效运行是最重要的业务之一**；具体包括：
  - 有**基于 K8s 的算力平台**，更合理地调度资源，包含**优先级机制**，尽量让业务把资源用满；
  - 与训练、推理团队一起优化他们的训练与推理性能；
  - 根据业务配置与需求做**硬件选型**，硬件部门也在这个大部门之下。
- 候选人确认："所以不只是运维，还有基于 K8s 的 GPU 调度业务。"面试官确认。
- 关于 AI 化：团队**已经有类似 SRE Agent / 业务 Agent 在提效**（有基于不同底座做的），组里负责的组件类型比较多。

### 关键评价点

- 反问问到了**团队的资源与业务重心（GPU 与 K8s 算力平台）**，这是非常有价值的信息：说明该岗位更偏 **AI Infra / 集群侧**，而不是纯业务运维。下次可以在反问里再追一句"这个岗位更偏 GPU 调度还是 Agent 提效"，直接对齐岗位画像。
- 面试官提到团队已有 Agent 在提效，可以顺势追问"Agent 目前的覆盖环节与主要卡点"——这正好是你实习里做过的事（评测框架 + Prompt 优化），能自然带出你的增量价值。
