## 三、调度器的动机与网络探测实现（约 07:15—10:23）

### 面试官问题

- "第一个我不太清楚它是干嘛的，这是什么事情？"
- "这个应用是有状态还是无状态？"
- 追问探测方式与开销。

### 候选人回答

- 问题背景：一个微服务应用由多个微服务组件构成（经典的前端 / 后端 / 数据库三层），分别部署在不同 K8s 节点上；节点/应用之间访问存在延迟。要保证整个微服务应用访问的 **QoS**，就要尽量保持各应用之间访问延迟低——K8s 原生调度器无法实现这种**按网络时延**的调度，因此他们做了针对性调度器。
- 网络探测的两种实现方式：
  1. 在**节点（Linux）层面**用 iperf 或 ping 机制探测各节点之间的网络时延（较基础的方式）；
  2. 在**集群层面**把网络拓扑组件部署成 **Pod 应用**，由组件互相知道对端的应用名/地址并访问，在 Pod 内部把访问延迟数据存在本地；底层涉及 K8s 的容器网络机制。
- 延迟数据的使用：通过 **volume mounts** 把本地延迟数据挂载到各节点本地，调度器通过访问 Pod 暴露的 **metrics 端口**采集这些数据；把每个节点的延迟数据都采集到之后，**在调度器内部构建网络拓扑矩阵**，再结合微服务的访问延迟要求决定组件部署到哪个节点。
- 组件开销：整体影响很小——它本身只是节点间时延探测的应用，CPU/内存占用与网络 IO 占用都比较小；不过当时**没有做具体的开销评估**，同类采集组件的评估是在第二个项目（Trace 监控）里做的。

### 关键评价点

- 这一段的机制讲得完整（探测 → 本地落盘 → volume 挂载 → metrics 暴露 → 调度器汇聚成矩阵），但**开头绕了一圈才讲清"解决什么问题"**。更好的开场是："微服务的 QoS 取决于组件间网络时延，而 K8s 默认调度器不看网络时延，所以我们要做一张实时的节点间时延矩阵，并把它作为调度打分的一项"。
- "没有做开销评估"是坦诚但失分的回答；可以补上已知的数据（例如"探测频率 N 秒一次、单次开销可忽略，第二个项目里我们量化了采集组件对业务性能的损耗低于 9.66%"），把两个项目串起来。

## 四、K8s 使用经验与核心组件（约 12:15—14:52）

### 面试官问题

- "K8s 集群你本身用得比较多是吗？"
- 追问核心组件与控制器机制。

### 候选人回答

- 使用经验：前两年一直在做 K8s 层面的东西，包括 **Operator** 开发；实验室集群从 **1.22.6** 升级到 **1.28.5**，目前仍是 1.28.5。
- 核心组件：**API Server**、**etcd**、**kube-proxy**、**kubelet**、**kube-scheduler**、**controller-manager**、**CoreDNS**，共同构成 K8s 集群。
- 控制器与调谐机制：K8s 把各种数据与应用定义成资源，每种资源都有对应的 Controller；**Controller Manager** 中包含所有基础资源的 Controller，其作用是配合底层 **Informer 机制**，把集群当前状态/资源状态与 etcd 中写入的期望状态进行**调谐**。
- kubelet 以 **DaemonSet** 形式部署在每个节点上；创建 Deployment 时流程为：向 API Server 发请求 → 经过鉴权认证与准入机制 → 写入数据库 → 发送变更事件 → 各节点 kubelet 监听变更事件、判断是否属于本节点 → 若是则启动对应的调谐机制。

### 关键评价点

- 组件列举完整，但**"调谐"只是点到为止**，没有讲 Informer 的三层结构（Reflector / Delta FIFO / Indexer）与 workqueue + Reconciler 的闭环——这在阿里云那场他讲得很好，本场明显简略。同一知识点在两家公司讲出不同深度，会显得"背下来的"而不是"理解的"。
- 建议把这套内容固化成**统一版本**（30 秒版 / 2 分钟版各一个），避免临场深浅不一。

## 五、网络插件与 iptables / IPVS（约 14:52—16:00）

### 面试官问题

- 网络插件相关（Calico / Flannel）。
- "iptables 和 IPVS 呢？"

### 候选人回答

- 集群比较小（一共 **15 个节点**），用的是 **Flannel**；**Calico 了解过但没用过**。
- 理解上：Flannel 更适合集群规模稍小的场景，Calico 更适合大集群节点规模的场景；底层原理**只了解 Flannel 的原理**。
- 对 **iptables 与 IPVS 的对比**：坦诚回答"其实对比比较少，没怎么对比过"。

### 关键评价点

- 这是本场第二个明确的失分点（与阿里云那场同一题）。必须补齐：
  - **iptables 模式**：基于 netfilter 规则链，规则数随 Service 数量线性增长，大规模下规则同步与匹配开销明显；
  - **IPVS 模式**：基于内核 LVS 的哈希表，支持 rr / wrr / lc 等调度算法，支持数万级 Service，转发性能与同步效率显著更好；
  - 一句话结论：**"小集群 iptables 够用，Service 上千后 IPVS 的转发与同步优势就出来了，且 IPVS 支持更丰富的负载均衡算法。"**
- Flannel vs Calico 也可以补一句本质差异：**Flannel 偏 Overlay（VXLAN/host-gw，简单但多一层封装），Calico 偏 BGP 路由直连 + 网络策略（NetworkPolicy 能力强，适合大集群与需要策略隔离的场景）。**

## 六、调度策略与调度框架扩展点（约 16:00—18:05）

### 面试官问题

面试官请候选人讲 K8s 默认调度策略与调度框架的阶段划分。

### 候选人回答

- 流程起点：先看 Pod 是否写了**节点亲和性**；没有则走默认策略。
- 默认策略关注两个层面：**资源**与**镜像**（目标节点上是否已有对应镜像，即镜像亲和性）。
- 资源负载均衡的计算方法分几个阶段，数据来源是 **API Server 的 Metrics Server**，取各节点的 CPU、内存、IO、网络 IO、磁盘占用等基本数据进行排名与计算。
- **调度框架分为若干扩展点**：PreFilter / Filter、Score 等；亲和性作用在 **PreFilter / Filter** 阶段做节点过滤，过滤之后才进入资源打分，最终选出评分最高的节点。

### 关键评价点

- 对扩展点的记忆基本正确，但可以更精确（当前调度框架的扩展点顺序：`PreFilter → Filter → PostFilter → PreScore → Score → NormalizeScore → Reserve → Permit → PreBind → Bind`）；把自己插件挂在 **PreFilter/Filter（做硬性过滤）与 Score（做加权打分）** 这句话讲清楚，就能直接接到自己的项目（NeiLatS 就是在这两个点介入）。
- 建议把"亲和性 vs 资源打分"的先后关系再强调一次：**过滤阶段只做可行性判断，打分阶段才做优劣排序——亲和性不满足会被直接过滤掉，而不是简单扣分。**

## 七、eBPF 项目连续追问（约 18:05—22:09）

### 面试官问题

- "E bpf 你讲一下，eBPF 哪几种？"
- "eBPF 的原理？内核能抓到哪些信息——函数调用还能抓到吗？"
- "eBPF 对内核有要求吗？"
- "eBPF 的挂载点选择哪些？比如说有 XDP 之类的挂载点你当时选了什么？"
- 质疑："我感觉好像就是铺了一个 eBPF Exporter，然后拿到一些数据，这些数据是不是做了一些分析？"

### 候选人回答

- 项目分工：这是团队型项目，他的主要工作偏**算法层**；eBPF 底层的 C 程序由师兄编写，他用 **eBPF Exporter** 接到 **Prometheus 与 Grafana** 做监控。
- 原理理解：eBPF 工作在 Linux 操作系统层面，涉及内核底层的数据抓取，例如 IO 相关指标与块设备数据，都是在内核层面抓取的；并坦诚"这个平时了解比较少一点"。
- 对"内核能抓到什么"的回答：基本上**只要涉及 Linux 底层调用或系统调用都能抓到**；用户态"应该也是能抓到的吧"。
- 内核要求：**不太清楚**，可能有对应的版本要求，一般的内核可能不支持；当时是在 **Ubuntu 24.05** 上做的，内核版本应该到 6，可以使用。
- 挂载点：当时直接用 eBPF Exporter 把对应指标端口暴露出来再抓取，**具体的挂载点实现不是他负责的内容**。
- 对"是否做了分析"的澄清（这一问回答得比较完整）：会部署多种 Exporter、采集多类指标数据，对指标做**异常灵敏度筛选**，再用异常检测模型做异常检测；根因分析则用**对应模态的特征提取 + 多模态融合 + 图神经网络融合**完成定位。

### 关键评价点

- 这是本场**最被动的一段**：连续四问（种类、原理、内核要求、挂载点）都没能给出有信息量的回答，面试官直接质疑"你是不是只是铺了个 Exporter"。**必须补齐 eBPF 基础知识**，至少要能答：
  - **挂载点类型**：kprobe / kretprobe（内核函数出入口）、uprobe / uretprobe（用户态函数）、tracepoint（内核静态追踪点）、XDP（网卡驱动层，最早处理）、TC（流量控制层）、perf_event、socket filter；
  - **内核要求**：内核需带 BPF 支持（4.x 起），生产上常用 **5.4+**；使用 **CO-RE / BTF** 需要内核开启 `CONFIG_DEBUG_INFO_BTF`；老内核需回退到 BCC 风格。
  - **能抓什么**：系统调用、内核/用户态函数调用、调度与网络事件、块设备 IO 等；**用户态要用 uprobe**，且只能抓函数边界，抓不到函数内部变量（除非有调试信息）。
- 更重要的策略问题：**被问到自己不负责的模块时，"不是我的部分"要说，但不能只说这一句**——应该给出"我知道它大概怎么工作 + 我负责的部分如何依赖它"，这次直到被质疑才把算法部分讲出来，是被动的。
- 主动交代能力边界是对的，但可以更早说明"内核侧由师兄负责、我负责采集指标口径与算法"，避免给人留下"只做了集成"的印象。

## 八、故障注入类型与 Pod 起不来排查（约 22:09—24:44）

### 面试官问题

- "Chaos Mesh 对故障注入的检测，注入了哪些故障？"
- "Pod 起不来大概会有什么原因？"

### 候选人回答

- 注入的故障类型：**Pod 网络延迟、Pod Failure、内存 OOM、CPU 占用高**这几类；比赛当时要求覆盖三种类型即可（时延、Pod Failure 应用失败、内存与网络高占用）。
- **Pod 起不来的原因**（分三个阶段）：
  1. **调度失败**——调度器没能调度成功；
  2. **节点资源不足**——调到节点上之后，节点没有足够资源让 Pod 起来（Pod 中定义了 Request 与 Limit）；
  3. **镜像拉取失败**——调度成功、资源足够，但拉取镜像时访问不通。

### 关键评价点

- 三种原因归纳得不错，可以再补两类高频原因把回答补全：**配置/依赖问题（ConfigMap / Secret 缺失、挂载失败、PVC 未绑定）**与**应用自身启动即退出（CrashLoopBackOff，配合 `kubectl logs --previous` 看上一次日志）**。
- 建议用"**从 Pending 到 Running 的每一跳都可能失败**"这条主线组织答案：调度（Pending）→ 镜像（ImagePullBackOff）→ 存储/配置挂载 → 容器启动（CrashLoopBackOff）→ 就绪（Readiness 失败）。这条主线一次讲完，比按点罗列更有结构感。

## 九、监控体系与告警如何验证（约 24:44—26:18）

### 面试官问题

面试官询问监控与算法如何验证"能否发现故障"。

### 候选人回答

- 流程：混沌注入前先对微服务框架做 **Locust 压测**，压测与故障注入同时进行；
- 注入完成后，**Prometheus 采集框架**把数据采集并送到 **Grafana** 面板，可以看到每个应用的 CPU / 内存占用、应用之间的访问延迟、以及应用是否可达；
- 同时用 **Jaeger / OpenTelemetry** 做日志与 Trace 采集；
- 之后由部署的 **Anomaly Transformer** 异常检测模型判断当前是否异常；
- 若判定异常，则对三类模态数据做特征提取，交给后续根因算法，最终完成定位。

### 关键评价点

- 这条链路（压测 + 注入 → 采集 → 看板 → 异常检测 → 根因分析）是完整闭环，讲得比前面几场更具体。
- 建议补一句**验证方式**：即"注入的故障类型是已知的，所以可以用**根因定位准确率**作为指标来评估（与 Eadro 对比提升 1%—2%）"——把"我们有监控"升级为"我们能量化监控的有效性"。

## 十、LangGraph 与 LangChain 的区别（约 26:18—27:45）

### 面试官问题

面试官问两者关系与区别。

### 候选人回答

- **LangChain** 主要用于 AI 应用的**快速构建和验证**；如果要实现**高度自定义化**的 AI 应用或 Agent，还是得用 **LangGraph** 更方便。
- 主要区别：LangGraph 可以在**代码层面做更细粒度的流程编排**——每个 Agent 之间的 Agent Loop 如何执行、状态流转与流程控制都可以用 LangGraph 做，相当于更加细粒度、更加自定义化。

### 关键评价点

- 相比快手 SRE 三面那次，这里讲得偏简，也没有提到"**LangChain 的现代 Agent 实现本身建立在 LangGraph primitives 之上**"这一层，深度略欠。
- 建议固定一套话术：**"LangChain 提供 Model / Tool / Message 等高层抽象，适合快速搭建标准 Agent；LangGraph 提供 State / Node / Conditional Edge / Checkpoint 等显式编排能力，适合我这个项目存在的两级控制流（Supervisor → 专业 Agent，以及专业 Agent 内部 LLM ↔ Tool 循环）。"**

## 十一、四个 Agent 的编排细节（约 27:45—31:39）

### 面试官问题

> "多个 Agent 就是在上面做编排吗？举一个具体的场景，Agent 怎么去编排、你写了哪些代码？"

### 候选人回答

- 项目实现为**四个 Agent 做状态流转与编排**：
  - **Supervisor（主管 Agent）**：接收提问并决定下一步交给谁；
  - **OBS Agent**：连接 K8s 集群做信息获取与操作并分析；
  - **RAG Agent**：检索运维文档、官方运维文档以及自身的运维经验；
  - **Chat Agent**：处理常规信息查询或简单问题。
- 完整流程示例（以 CrashLoopBackOff 为例）：
  1. 用户向 Supervisor 提问；
  2. Supervisor 判断"要分析这个问题，首先要获取当前状态与故障信息"，于是把任务派发给 **OBS Agent**；
  3. OBS Agent 利用已注册的 **Kubernetes MCP Server**（或 CLI 工具）拉取指定 Pod 的状态、Logs 日志、Prometheus 指标数据，整合分析后返回 Supervisor；
  4. Supervisor 判断这些信息是否足以真正定位根因；若不足，则返回 OBS Agent 继续取数，或转向 **RAG Agent**，结合运维经验与手册做分析。
- 关于"谁决定走哪条路"：**由 Agent 自行决定**，并没有给它设置固定的 Workflow，整个分析过程由大模型决定。
- 数据来源补充：Kubernetes MCP Server 负责获取**集群层面**的信息；只要数据库与应用都在集群里，就能拿到数据库日志与应用日志。如果本地部署的场景集群层面取不到，则会考虑在每个节点上部署对应的 MCP Server 或 CLI 工具，去取节点 Linux 系统层面的日志；也可以通过写 **Skill**、或配置访问云端数据库/日志存储的 MCP Server 来补齐能力。

### 关键评价点

- 这是本场最强的一段：**四 Agent 职责 + 完整流转示例 + "由模型自行决定路由，不写死 Workflow"**，把 LangGraph 的价值直接落到代码结构上，非常有说服力。
- 唯一要注意的是"没有固定 Workflow"这句可能被追问"**那你怎么防止死循环 / 怎么限步**"——建议提前准备：**LangGraph 的图仍有最大步数与条件终止（如信息已足够 / 达到 max iterations 即结束），并配合工具调用失败重试上限**。
- 也可以主动提到"RAG Agent 的检索源里包含团队知识库与个人知识库"，与实习的评测口径呼应。

## 十二、Go 语言与并发机制（约 33:20—37:44）

### 面试官问题

- "Go 语言你用来做什么？用多久了？"
- "Go 的 panic 有哪些情况？"
- "读取一个已关闭的 channel 会怎样？"
- "Go 对比其他语言有什么优势？"

### 候选人回答

- 用途：主要用在 **K8s 组件编写**与一些**算法编写**（例如 NeiLatS 调度器）；使用时长**一年多**。
- Panic 场景：主要是异常，例如**向已关闭的管道（channel）写入数据**会触发 panic；其他异常情况一时想不起来。
- **读取已关闭的 channel**：不会 panic，会返回零值；如果管道内容是 int，读到的数据默认是 0（同时 `ok` 为 false）。
- 与其他语言对比：Go 更轻量、更适合高并发，核心优势是 **goroutine 比线程轻量得多**；实现机制是 **GMP 调度模型**——每个 CPU 核心对应一个 **P（工作台）**，系统线程是 **M**，goroutine 是挂在队列上待执行的 **G**；goroutine 初始栈空间小、按需自动扩展；线程从队列取 G 执行；当某个 goroutine 处于 **IO / 网络阻塞**时，会释放 P（工作台）与线程去运行其他就绪的 goroutine。因此比 C++ / Java 的线程机制轻量很多。

### 关键评价点

- GMP 这段讲得相当完整（P/M/G 的角色、栈按需增长、IO 阻塞时 P 的让出），是本场的技术亮点之一。
- Panic 部分答得太薄，建议补齐常见触发场景：**数组/切片越界、空指针解引用、类型断言失败（未用 comma-ok）、除零、向已关闭 channel 发送、close 已关闭 channel、并发读写 map、通道死锁（fatal error: all goroutines are asleep）**。另外注意区分：`panic` 可 recover，**map 并发写与死锁属于 fatal error，无法 recover**——这一句能显出深度。
- 已关闭 channel 的回答是对的，可以补全：**读取已关闭 channel 立即返回零值 + `ok=false`；向已关闭 channel 发送 panic；`close` 一个已关闭的 channel 也 panic。**

## 十三、Linux 排查与 SRE / DevOps 认知（约 38:04—40:43）

### 面试官问题

- "日志怎么查？" "CPU 比较高怎么排查？"
- "你理解的 SRE 是什么？"
- "DevOps 了解吗？" "SRE 最关注什么？" "SRE 的全称是什么？"

### 候选人回答

- 查日志：文件较小时直接用 **grep + 管道**查；文件较大时用 **tail** 看文件最后几百行或几千行，再找对应字符。
- CPU 高排查：先看 CPU **占用率**，注意 **load 与利用率不是一回事**；用 **top** 看 CPU 与内存占用情况；若利用率高，就看排名靠前的进程 **PID**、程序路径与状态；若**利用率不高但 load 很高**，可能是进程处于阻塞或无法关闭的状态，导致资源释放不掉、不断累积——需要结合实际情况判断。
- **SRE**：是**运维开发**，与传统运维不同，它是在运维过程中做开发——对已有成熟应对流程的故障问题，把成熟的应对手段变成**自动化的工作流或平台**，让它自动化处理已经出现过且有处理流程的故障；另一方面是编写监控组件或脚本，**防患于未然**。
- **DevOps**：坦诚"了解比较少一点"。
- SRE 最关注什么：最关注**稳定性**——只有稳定了，公司的业务应用才有正常的质量保证、才能正常运行；在此基础上再去做对应的**安全与成本降低**。
- SRE 全称：**Site Reliability Engineer（站点可靠性工程师）**。

### 关键评价点

- "load 高但利用率不高要看阻塞进程"这个判断很到位，是真实排障经验才会有的直觉，建议展开成完整方法论：**top/uptime 看 load → vmstat 看 r（运行队列）/b（阻塞）→ iostat 看 IO 等待 → pidstat -d 定位具体进程**，用命令链把经验变成可复现的流程。
- **DevOps 答"了解比较少"是本场可以避免的失分**。至少要能说："DevOps 是研发与运维的一体化协作文化与实践，核心是持续集成/持续交付（CI/CD）、基础设施即代码（IaC）、自动化测试与监控反馈闭环；SRE 可以看作 DevOps 在可靠性目标上的具体实现（用 SLO/错误预算把'可靠性'变成可量化的工程目标）。"
- SRE 的定义答得偏"工具视角"（做平台、写脚本）。更好的答法是"**SRE 是用软件工程方法解决运维问题的角色**：以 SLO 定义可靠性目标，用错误预算平衡发布与稳定性，把重复性运维工作自动化（消灭 toil）"——这样才接得上面试官"最关注什么"的追问。
- "最关注稳定性，然后安全与成本"是对的，可以再带出行业通用说法：**稳定性 → 效率 → 成本 → 安全**这个优先级框架。
