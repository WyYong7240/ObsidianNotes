## 一、自我介绍（约 00:00—03:29）

### 面试官问题（根据回答还原）

请先做一下自我介绍。

### 候选人回答

- **教育背景**：本科太原理工大学计算机科学与技术；现在西安电子科技大学读计算机科学与技术硕士。
- **实验室方向**：从云原生计算逐步发展到微服务异常检测与 SRE 相关方向。
- **项目一（2025.01–05）**：接手实验室师兄产出的调度论文，论文本身存在不足，他针对缺陷做了重构，用 K8s 原生的 Scheduling Framework 扩展点重写调度方案，取得了更好的调度决策与效果。
- **项目二（2025.06）**：参加华为举办的第二届中国研究生操作系统开源创新大赛，赛题是针对微服务异常检测框架搭建平台——用 k6、Locust 这类压力测试工具，串起「压力测试→故障注入→异常检测→根因分析」的完整链路。团队 3 人、本人任组长，负责整个平台搭建与算法设计；eBPF 部分是师兄的工作，自己没有参与。
- **项目三（2026.02）**：2 月 Agent 正热，结合自身想法与实验室需求手搓了一个基于 LangGraph 的智能运维助手，采用 ReAct 架构，分为 4 个 Agent。整体效果是：通过自然语言指令获取集群信息，感知集群内的故障与水位信息，对故障做定位与分析并给出操作建议；但最终执行仍由人工完成，没有让 Agent 自己执行。
- **实习（2026 暑假）**：阿里巴巴千问事业部 AI SRE 实习。主要内容分两块：
  - 构建 SRE-Benchmark，用于对 SRE Agent 做模型选型与 Hermes 框架的迭代验证。产出是 System Prompt 优化：实验期 token 消耗下降 50%、冗余工具调用下降 30%；上线后输入 token 下降 18%、输出 token 下降 57%、冗余工具调用下降 30%。7 月测试了 14 个模型、8 月测试了 8 个模型，最终上线 Qwen3.8-Max、DeepSeek-V4-Flash-0731、Kimi-K3，取代了 6、7 月试用的 Claude 与 GPT 系模型。
  - 辅助团队构建 SRE Agent：跨业务多租户共用的 Agent 平台（基于沙箱实现）、子代理编排设计。

### 关键评价点

- 项目链条完整且与 SRE 岗位强相关：调度 → 监控/异常检测 → 运维 Agent → Agent 测评，四个环节都踩在 JD 上，这是本场最大的加分项。
- 主动划定能力边界（eBPF 不归自己、实习只出设计方案不做实现），可信度高，但也让「独立工程产出」的分量变轻，需要靠项目三的实现细节来补。
- 自我介绍里量化数字密度很高，但内部口径不自洽（输入 token 先 18% 后 57%），面试官会据此怀疑数字可靠性——**同一场里说出来的数字必须提前固定一版练习口播**。

## 三、调度优化项目深挖（约 03:56—05:24）

### 面试官问题（引用）

「你在 K8s 里做过哪些调度优化？能举一个印象比较深的例子吗？」

### 候选人回答

- 印象最深的就是 2025 年 1–5 月这个项目。它原本是实验室师兄产出的论文，由他接手继续做。
- 调度要解决的两个问题：微服务网格互相访问的时延问题、多资源负载均衡问题。
- 方案把评估拆成三个部分综合打分：
  1. 四维资源的负载均衡得分；
  2. 服务网格互访时延的两个得分——网络时延稳定性得分，以及用时间序列预测模型预测未来一小时时延情况得到的得分；
  3. 三部分综合打分后，用 Scheduling Framework 选出当前微服务最适合部署到的节点，再调度上去。

### 关键评价点

- 三层打分的结构讲清楚了，但**功效系数法、合作博弈效用函数这两个真正的创新点没说**（简历里有），面试官只听到了「打分 + 选节点」，容易被打成「常规工作量」。
- 简历里有两个硬数字（调度决策时延降低 25.94%、集群平均负载均衡度提升 10.29%），这一问本来是最好的投放位置，却一个都没说——**凡是「举一个项目」的开放问题，都要把简历上该项目的量化结果带上**。
- 时间序列预测那一支最容易被追问：模型选型、预测误差、预测失准时会不会把 Pod 调度到更差的节点？需要准备「预测失效时的兜底逻辑」。

## 七、运维 Agent 平台深挖（约 06:50—09:25）

### 面试官问题（部分引用）

「我刚才也听到你讲的一个运维平台……简单介绍一下它自己做了哪些事情、能解决什么问题，或者说你当时设计它的初衷是什么？」

### 候选人回答

- **设计初衷**：年初做这个平台时并没有用 Codex/Reasonix，一开始是用网页对话的方式一点点搭的，效率比较低。初衷是降低自己和同门维护 K8s 集群、水位信息以及处理可能发生的故障的工作量。
- **架构**：ReAct 结构，共 4 个 Agent——上面是中枢 Agent，下面分为操作 Agent、RAG Agent、Chat Agent。
- **运行逻辑**：集群发生 Pod 故障（例如 CrashLoopBackOff）时，先用自然语言指令让它拉取集群故障信息；再结合故障信息与已有的运维手册、运维经验文档，综合分析当前故障原因并给出合理的操作建议；给出建议后，实际的恢复操作仍由人工执行。
- **任务流转**：中枢 Agent 收到指令后派发任务给子 Agent；子 Agent 通过 MCP 工具或 CLI 获取集群信息、手册的 RAG 信息，或执行 scale 之类的操作；中枢 Agent 做诊断分析，结果满足用户需求就直接输出到对话框。整体逻辑比较简单。
- **能力边界**：诊断深度只到 K8s 集群层面，拿不到容器内部的应用代码，只能获取集群层面的水位信息、Pod 的 YAML 以及日志，据此做诊断。

### 面试官回应

「我理解你这个其实相当于先做 K8s 集群层面的诊断，在人工实践之后再到 K8s 集群层面去做分析，给你做一些辅助判断。」候选人确认「是的，辅助判断」。

### 关键评价点

- 这是本场被挖得最深的一节，面试官连续追问设计初衷和能力边界，说明他对「运维 Agent 到底能替人干多少」很在意。
- 自曝边界（只能到集群层、拿不到容器内信息）很诚实，但**只说了「不能」，没说「怎样才行」**。补一句「再深一层需要接入 eBPF 或应用侧指标/火焰图」，立刻从「知道自己做浅了」变成「知道下一步怎么做」——而这正好可复用自己项目二里 eBPF 的积累。
- 4 个 Agent 的编排只讲了数据流，没有讲**为什么这么切分、失败重试与工具调用幂等怎么做、有没有一次真实误判**。这类问题面试官下一轮很容易接着问。
- 「执行仍由人工完成」要主动给出理由（审批与安全边界），不要让它听起来像「做不出来自动执行」。

## 八、对 SRE 岗位的理解（约 09:25—12:22）

### 面试官问题（部分引用）

「我听下来你这块其实是有一定运维的思维的……你对我们这个 SRE 运维岗位具体要干什么，有没有做过一些了解？」

### 候选人回答

- 实习期间没有参与到实际的 SRE 运维任务里（权限受限），团队给实习生安排的是辅助构建 SRE Agent、搭 SRE Agent 评测平台这类工作。
- 但能参与团队会议、了解他们的实际工作。举 7 月一次故障为例，团队的处理逻辑是：
  1. 先发现、定位故障——判断故障源是团队内部、跨部门还是跨集团；
  2. 若能在团队内部定位，优先快速恢复（快恢），避免损失进一步扩大；
  3. 快恢后拉通各方会议，确定故障的影响范围、爆炸半径；
  4. 在凌晨或人比较少的时段对故障进行复现与演练；
  5. 重要节点之前，对重要业务提前做扩容、水位检查和压力测试，保证流量高峰到来时业务不会崩；
  6. 预先准备预案并对整个预案过程做预演练；
  7. 再往下一步是推动开发侧修复，让问题下次能避免；
  8. 后续走部门之间的赔付流程，最后对整个故障做复盘总结。

### 关键评价点

- 这段回答的质量明显高于前几节：**流程完整、有真实案例、有「爆炸半径」「快恢」「预案预演练」这类岗位黑话**，说明确实近距离看过真实 SRE 工作，面试官随即给出了「有运维思维」的评价。
- 缺口也在同一句里暴露了：这是「观察」不是「实操」。面试官接下来一定会问「那你打算怎么补」。需要准备一个具体计划（如主动认领值班/巡检、从变更与告警链路切入），而不是只说「我欠缺、我想学」。
- 流程描述偏「教科书完整版」，可以再压缩成一条主线（止损→定位→拉通→复盘），把细节留给追问，避免占用太多面试官时间。

## 十、职业发展方向（约 13:02—15:04）

### 面试官问题（根据回答还原）

未来有没有自己想做的方向？想在哪个技术领域继续深入或发展？

### 候选人回答

- 一开始认为 K8s 主要有两个发展方向：调度，或基于 K8s 的运维操作；后来觉得自己还是更偏运维这一块。
- 对发展的规划：目前对实际的、偏传统的 SRE 运维流程还比较欠缺，希望能先参与到实际的基础运维过程中，把这些基础流程和工作了解透彻。

### 关键评价点

- 「先补传统运维、再转 Agent」的路径判断是对的，也正好命中团队「SRE + AI」的定位；这段是全场**与岗位契合度最高**的表达之一。
- 但把「我欠缺传统运维流程」重复讲了两遍，显得不自信。同样的内容改成「我的短板在这一块、我的补法是 XXX」会更有力。
- 面试官提到团队要求「技术设施懂但不需要极专、会安排方向让你学」，与候选人的自评基本对齐，可以在反问环节顺着这条确认培养路径。

## 十一、语言栈与 Agent 构建经历（约 15:28—16:50）

### 面试官问题（根据回答还原）

你最擅长什么语言？到现在自己构建过几个 Agent？

### 候选人回答

- 擅长语言和 AI 这块关联不大：K8s 的原生语言是 Go，所以个人对 Go 比较熟练；如果基于 K8s 就用 Go，AI 这一块主要是 Python，基本就是这两种语言。
- 到现在为止构建过两个 Agent：
  1. 在学校、为实验室构建的智能运维助手——用 Python 实现的；
  2. 在阿里巴巴千问事业部构建的 SRE Agent——但那个只给出了一个 Agent 的设计方案，具体实现并没有让实习生去做。
- 所以真正意义上「自己构建」的，还是实验室那个用 Python 写的 Kubernetes 智能运维助手，整体逻辑前面已经重述过。

### 关键评价点

- 主动区分「给出设计方案」和「亲手实现」，是诚信亮点；但等于承认唯一的独立 Agent 实现是学校项目，**工程深度的举证责任全压在这一项上**。要提前把它的技术细节练到能接住三层追问（工具如何定义、失败如何处理、效果如何度量）。
- 面试官问语言，实际在问「你 AI 工程化的产出工具链是什么」。只报了 Go 和 Python，没有把「用 Go 写 K8s 侧组件 + 用 Python 编排 Agent」的组合讲成一个优势，略亏。

## 十二、候选人反问与团队介绍（约 16:50—20:57）

### 候选人问题

1. 「团队这边主要会涉及到运维的哪些层面？比如从底层硬件到软件到中间件，或者说业务应用的运维？」
2. 「咱们团队现在 AI 化的现状大概是到了什么情况？是否用到了 Agent 去做 SRE 的工作？它现在的状况是什么样？」

### 面试官回答（引用 + 归纳）

- 运维从大方向分为**稳定性与成本**：稳定性是必须守护的，成本则与公司经营直接挂钩。
- 技术栈上，从运维往上是网络硬件、服务器（比如 GPU），再往上是中间件（消息队列、监控组件这类），再上一层是各种应用，比如 Java、Python 的服务。
- 作为运维，每一块都必须要去了解，否则排障过程中容易出现技术盲区。现在有 AI 辅助，可以理解为「一句话的事」，但仍然需要你懂技术。
- 第三块是 AI 相关的：因为团队做 AI，更多会用到大模型的 GPU 资源以及各类集群，要保证高可用性、保证快速调度与资源的高效使用，从而让成本更优化。
- 此外还有线上问题的排查、应急响应、变更发布，这些是运维最基本的、必不可少的工作。
- 岗位要求：技术设施方面要「懂」，但不需要相当的专业性；团队会安排技术方向让你学习。将来会让你在 AI 运维的技术架构平台上做更深入的参与，同时作为 SRE 要推动研发把运维领域的稳定性做得更扎实。
- 关于第二问「团队 AI 化现状、是否已用 Agent 做 SRE 工作」，该段回答未被录音采集到，仅能确认面试官随后进入收尾流程。
- 收尾：面试官表示「我这边大概就这些问题，你还有什么想要向我咨询的」，随后说「那我这边暂时就没什么问题了」，双方道谢结束。

### 关键评价点

- 第一个反问选得好，直接换来了一段**团队全景介绍**（稳定性/成本两条主线、从硬件到中间件的分层、AI 资源调度这条第三块），信息量很大，可以在后续轮次里针对性准备。
- 第二个反问方向也对（问 AI 化现状），但在面试官没有正面回答时缺少追问。更好的收法是把它换成**可验证的具体问题**，例如「团队现在 Agent 是辅助诊断还是已经参与变更执行」，这种问法对方通常会给实质回答。
- 面试官明确说「技术设施懂即可、会安排学习」，同时强调「要推动研发做稳定性」——说明这个岗位**更看重协作推动与运维判断力**，纯技术深度不是唯一标尺。简历上的「AI SRE / Agent 测评」正好是差异化优势，下次应更早、更重地打出来。

## 十三、面试整体复盘建议

### 展现出的优势

- **岗位对口度极高**：调度插件、微服务异常检测、运维 Agent、Agent 测评四条线都能直接对上 SRE 与 AIOps 的工作内容，这是本场最硬的底牌。
- **诚信与边界感好**：反复主动交代「这部分不是我做的」，在只经历一轮的面试里能提升整体可信度。
- **有岗位语感**：7 月故障案例的复述里出现了快恢、爆炸半径、预案预演练、复盘流程，说明确实近距离看过真实 SRE 工作，面试官当场给了正面反馈。
- **有量化意识**：token 消耗、冗余工具调用、模型测试数量、集群规模都能给数字。

### 需要加强的表达

- **数字口径必须固定**：同一段自我介绍里输入 token 削减先 18% 后 57%，自相矛盾。建议定死一版（实验期/上线后分开说），并练到不看稿也不会串。
- **集群规模偏小要提前接招**：15 节点、不到 100 个 workload，遇到大集群追问会吃亏。建议准备一版「小集群经验如何迁移」+「大集群会新增哪些问题（多租户隔离、etcd 压力、监控基数、调度规模）」的回答。
- **诊断深度要主动给出下探方案**：当前只到 K8s 集群层，被追问时要能接 eBPF、应用侧指标、火焰图这一层，正好复用自己的项目积累。
- **Agent 项目要讲「怎么做对的」而不只是「怎么搭的」**：4 个 Agent 的编排只说了数据流，缺失败处理、幂等、误判案例、效果度量。
- **把「我很欠缺传统运维」改写成「我打算这样补」**，并给出可执行动作（认领巡检、跟班值班、从变更与告警链路切入）。
- **反问要收口**：对方没正面回答时要追一句可验证的问题，别让信息白白流走。

### 一句话总结

项目与岗位咬合得非常准、诚信度和岗位语感都在线，但自我介绍的数字自相矛盾、独立工程产出的举证集中在学校单项、集群规模偏小这三点，是这一轮之后最容易被追问、也最该提前补齐的地方。
