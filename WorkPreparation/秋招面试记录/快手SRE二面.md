## 二、现场算法题（约 17:43—21:30）

### 面试官问题（根据回答还原）

1. 实现求 N 的平方根（输入为整数），要求精度到小数点后两位。
2. 一个很大的文件中，如何找出出现次数最多的前 10 个元素？

### 候选人回答

**题一：求 N 的平方根**

- 开场候选人表示“不是很有思路”。
- 随后给出二分法思路：
  1. 先找一个 base，使其平方小于给定的 N，且 (base+1) 的平方大于 N；
  2. 则 √N 一定落在 base 与 base+1 这两个整数之间；
  3. 在该区间内继续二分，直到满足小数点后两位的精度。
- 被问及输入类型时回答“应该是个整数吧”。

**题二：大文件中出现次数最多的 Top 10**

- 文件很大（举例 10 GB），无法一次性读入，因此先做**分片**，例如切成 100 个片段；
- 每个片段各自统计出现次数最多的前若干个，得到局部 Top K；
- 最后把各片段的局部结果做**归并**，得到全局 Top 10；
- 数据结构上使用**优先队列 / 固定大小的堆**来维护 Top K；
- 被追问 Go 标准库是否有现成实现时，候选人表示“Go 原生的话不太了解”，倾向于自己实现堆结构。

### 面试官追问与澄清

- 确认输入是否为整数；
- 明确题目精度要求（小数点后两位）；
- 追问 Go 中是否有可用的原生数据结构。

### 关键评价点

- “分片 → 局部 Top K → 归并”是海量数据 Top K 的标准解法，思路完整。
- 两点可在后续复盘中明确：
  - 维护“出现次数最多的前 K 个”通常使用**小顶堆（最小堆）**，候选人表述为“大顶堆”，属于方向性口误，被追问时需要说清堆序与淘汰逻辑；
  - 归并阶段要说明同一 key 跨分片需要累加计数；若分片按 hash 划分，可让同一 key 始终落在同一分区，避免该问题。
- 平方根一题可补充：二分终止条件、边界情况（N = 0、N < 1、负数），以及牛顿迭代作为收敛更快的替代解法。

## 四、项目详述：微服务异常检测平台（约 22:44—29:05）

### 面试官问题（根据回答还原）

详细讲一下这个异常检测平台：赛题要求是什么？平台怎么搭的？算法是怎么设计的？

### 候选人回答

- **赛题要求**：
  - 覆盖从压力测试到混沌工程的完整链路；
  - 针对指定的开源微服务框架 **Train Ticket** 自建平台与算法，实现异常检测，且检测效率要达标；
  - 必须在给定的开源根因分析算法 **Eadro** 之上做改进。
- **平台搭建**：
  - 在 Kubernetes 上部署该微服务框架；
  - 使用 Prometheus + eBPF 做指标采集；
  - 使用 Grafana 做可视化；
  - 使用 Chaos Mesh 做故障注入，搭建全自动化的可视化异常注入与仿真平台。
- **算法设计**：
  - **多级 KPI 特征筛选**：微服务指标数量很多，并非所有指标都与异常检测强相关，因此先按多级筛选挑出对异常敏感度更高的指标，纳入最终检测；
  - **异常检测模型**：使用 **Anomaly Transformer**，先用微服务正常状态下的数据训练，再引入带标注的异常数据让模型学习并适应异常波动模式，检测出异常后向下一步输出信号；
  - **多模态融合**：将多类指标 / 数据源融合后再做根因分析。
- **异常的定义**：针对具有波动特征的时序数据，主要依据指标的波动来判定异常；典型对象包括 CPU、内存波动、服务之间的网络 I/O 波动、数据库连接、文件系统 I/O 波动等。
- 团队共 **3 人**分工，候选人参与了算法设计部分。
- 比赛背景：**“华为杯”第二届中国研究生操作系统开源创新大赛国家一等奖**。

### 关键评价点

- 平台链路完整：部署 → 采集 → 可视化 → 混沌注入 → 检测，具备端到端工程能力。
- 需要补充的关键细节：
  - 异常数据的**标注构造方式**（如何确定某段数据是异常）；
  - 评估口径：Precision / Recall / F1、误报率、样本规模、异常类型覆盖；
  - “提升 1%—2%”是百分点还是相对比例，以及其统计显著性；
  - 比赛中三人的具体分工边界。

## 五、实习内容：SRE Agent 评测平台（约 29:20—33:24）

### 面试官问题（根据回答还原）

实习期间的平台具体是怎么做的？部门里有多少个 Agent？评测指标怎么设计的？

### 候选人回答

- 所在部门为**阿里巴巴千问事业部—基础设施方向**（录音中称“运维部”）。
- 核心工作目标：基于业务需求搭建 **Agent 评测平台（SRE-Benchmark）**，服务于团队自建运维 Agent 的效果评测与模型选型。
- 部门内确实有多个 Agent（各业务部门也有各自的 Agent），但该平台**只针对本团队的 SRE Agent** 做评测和对比；其他部门的 Agent 仍处于初期发展阶段，暂时做不到 A2A 形式，都是独立开发。
- **评测指标共六个**（与简历“覆盖 6 个维度”一致）：
  1. **任务完成率**：Agent 对 SRE 类 case 的完成情况；
  2. **一致性**：同一个 case 交给 Agent 执行两次或三次，结果是否一致；
  3. **工具有效率**：一次任务可能调用十几个到二十几个工具，需要评判每个工具调用对该任务是否真正有效；
  4. **回复友好性**：运维人员最终只需要结论，期望的形态是“先给结论 → 再给分析过程与数据支撑 → 最后给总结与可操作建议”，而不是长篇大段、非结构化的输出；
  5. **Token 消耗**；
  6. **响应延迟**。
- **评测 case 分三类**：常规对话类（查水位、查故障原因、查 GPU 卡数量等）、定时巡检类、触发器类（线上出现故障或波动时触发，由 Agent 完成分析）。

### 关键评价点

- 指标设计覆盖“效果 + 稳定性 + 成本 + 体验”，超出只看准确率的常规思路。
- 一致性、工具有效率属于难以量化但设计合理的指标，建议准备其具体计算方式与判定阈值。
- 三类 case 与第八节的功能板块可以互相印证。
- 简历里还提到该平台产出“指标性对比、各模型性能对比报告、模型性能表现趋势”，这几项在本场没有展开，可以补进回答。

## 十三、面试整体复盘建议

### 展现出的优势

- Kubernetes、调度器、监控（eBPF / Prometheus）、异常检测与 Agent 运维经历集中，主线一致。
- 能端到端讲清一个平台：部署、采集、可视化、混沌注入、算法与验证。
- 在 Agent 评测上考虑了效果、稳定性、成本与用户体验四类维度，并区分了业务 Agent 与运维 Agent。
- 部署方案（云服务 + 沙箱 + 权限）与一面答述一致，稳定性好。
- 如实说明论文题目“可能比较老”、进度偏慢，态度诚实。

### 需要加强的表达

- **量化口径**：9.66%、1%—2%、30%、50% 都需要说明统计方式（平均值 / P95、样本量、基线、实验时长、数据来源）；简历里另有 25.94%、10.29% 两个数字，本场没有讲，建议主动补上。
- **算法细节**：Anomaly Transformer 的训练与打标流程、异常标注构造方式、评估指标（Precision / Recall / F1、误报率）应准备到可被追问的程度；同时把 Eadro 定位为**根因分析**基线，并说清“多级 KPI 特征筛选 + 多模态融合”各自的作用。
- **数据合规**：用生产 session 做评测集，要主动说明脱敏与访问控制方案。
- **Top K 堆序**：明确“出现次数最多的前 K 个”使用**小顶堆**维护，避免方向性口误。
- **安全边界**：多租户沙箱需补充网络策略、资源配额、逃逸防护、审计与回滚。
- **表达节奏**：自我介绍与项目描述偏长、口语重复较多，建议统一用“背景—目标—方案—结果—复盘”结构收敛。

### 一句话总结

候选人具备扎实的云原生与 Kubernetes 基础，项目覆盖调度重构、eBPF / Prometheus 监控、异常检测算法与 Agent 评测平台，能把 Agent 落地到真实运维流程中；后续重点是把量化口径、算法细节与生产级安全边界讲得更实，并把口语化的长段描述收敛成结构化表达。
