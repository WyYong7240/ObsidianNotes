## 四、实习项目深挖：SRE-Benchmark 评测平台（约 21:52—29:11）

### 面试官问题（根据回答还原）

讲一下你觉得最有难度的项目。这个平台为什么要做？难点在哪？怎么解决的？最终产出是什么？

### 候选人回答

**背景**

- 业务部门的需求：SRE 运维 Agent 需要一个**评测框架**，用来验证每次功能迭代相比上一次是否更有效。
- 评测任务集采用实际业务中运维人员会使用的 case，例如查水位、故障诊断等。
- 另一个背景是成本：运维 Agent 统一采用国外的 **Claude Code** 模型，成本较高；7 月份整个团队的模型成本约 **200 万元**。
- 判断是“不同运维任务并不需要最顶级的模型”，信息收集这类简单任务可用轻量模型。
- 因此规划了两块：
  1. **子 Agent 编排**：主 Agent 把任务拆分后，把简单任务派给子 Agent，子 Agent 使用较便宜的模型；
  2. **评测支撑**：既要有模型选型的数据支撑，也要有对 harness 框架做迭代验证的机制。
- 这个任务交给候选人搭建，团队内称之为 **SRE-Benchmark**。
- 时间要求紧急：6 月初接手，要求 6 月底就能投入生产使用。

**难点一：行业现有 Benchmark 都基于完全静态环境**

- 调研发现已有的 Benchmark 平台都建立在**全静态/全模拟**环境上。
- 要验证一个 harness 框架或模型在某类 case 上的能效，需要先搭一个全模拟环境；Agent 每次从 MCP 获取的水位、指标数据都固定，时间窗不变、不随时间动态变化，同一运维任务获取到的基础数据始终一致。
- 但对当时的业务环境而言，搭建全静态环境的时间成本与迭代成本都非常高。

**难点二：完成度难以用二元标准判定**

- 很多业务 case 无法准确用“对/错”二元标准判断 Agent 做得好不好。
- 例如查水位：Agent 拿到的信息可能全也可能不全，而“具体需要哪些信息”本身无法精确判定；有些信息必须有，多出来的信息可能更好、也可能干扰判断。
- 所以这个 case 的“完成度”很难界定。

**解决方案：动态基准（Dynamic Baseline）**

- 思路是不要构造模拟环境，而是采用**动态基准**：
  - 线上用的是什么模型，就直接用该模型（当时是 Claude Code）在当前 harness 环境下跑一批 case，例如 **50 个**；
  - 把这 50 个 case 上 Claude Code 的**实际回复**当作其他模型的参考答案；
  - 其他模型只要与参考答案**结构相似、数据准确**即可判为合格；
  - 相当于把“不确定的评判标准”结构化成“有参考答案的对比”。
- 同一个动态基准方案也用于解决“完成度如何评价”的问题。

**平台最终提供两个功能**

1. **固定 harness 框架下做模型选型**：同一 harness 框架、同一批 SRE case，比较不同模型的能效；
2. **harness 框架可替换**：用相同模型但不同 harness 框架评测，判断哪种 harness 框架对 SRE 场景任务更有效。

**产出与效果**

- 产出为 **System Prompt 针对性优化**与 **Skills 针对性优化**；
- 效果：SRE 场景下 **Token 消耗削减 50%**，**减少 30% 的冗余工具调用**；8 月份为团队省下不少成本。
- 评测批次：**7 月测了 14 个模型，8 月测了 8 个模型**。
- 8 月根据评测结果上线了三个模型：
  1. 自研旗舰模型 **Qwen3.8-Max**；
  2. 轻量任务采用 **DeepSeek V4 Flash 0731**；
  3. 另一个旗舰模型 **Kimi K3**。
  - 补充背景：8 月份集团已经对国外模型 **Claude** 做了限制，不能再上国外模型。
- 被追问“是不是都上线了”时，候选人回答是**选优**：测了那么多模型，从中挑选性能优良、能满足要求的上线。

### 关键评价点

- “动态基准”是本场最亮的设计点：用线上最强模型的真实输出作为参考答案，避开了搭建静态环境的巨大成本，思路清晰、可落地。
- 需要提前准备好的追问：
  - 50 个 case 是否覆盖了全部任务类型？样本量依据是什么？
  - “结构相似”如何判定——人工、规则还是模型打分（LLM-as-judge）？一致性如何保证？
  - 若线上基线模型本身出错，参考答案会不会把错误固化下来？有没有人工抽检或双重基准？
  - 不同 harness 框架对比时，如何排除 prompt、工具集差异带来的干扰？
  - Token 削减 50% 与工具调用减少 30% 的统计口径、以及是否伴随效果下降。
- 200 万元是 7 月的模型成本，建议准备好统计范围与对比基线。

## 五、微服务调度项目详述（约 29:49—34:37）

### 面试官问题（根据回答还原）

你简历上那个微服务调度的项目具体是怎么做的？算法是怎么设计的？

### 候选人回答

**项目背景**

- 项目为**微服务架构应用的云边异构调度优化（ICPP2023）**。
- 基于 **Kubernetes 与 KubeEdge** 搭建**云边异构集群**，并借助 **Net-topology 组件动态构建跨网段网络时延矩阵**，为位置感知调度提供底层数据支撑。
- 场景举例：前端 → 后端 → 数据库形成一条链路，分别部署成不同微服务、位于不同节点（例如前端在 A 节点、后端在 B 节点、数据库在 C 节点）。
- 不同节点可能位于不同物理位置，节点之间的网络延迟不同。
- 为保证 SLA（服务之间的访问延迟），需要把不同服务调度到指定节点上。

**方案一：四维资源评分（功效系数法）**

- 采用**四维资源模型**：CPU、内存、网络、磁盘 I/O，构建**四维资源亲和性模型**。
- 每个节点上部署 **Prometheus** 监控组件。
- 调度器自动从 Prometheus 获取四维指标数据，对每个指标做归一化，再用**功效系数法**做综合加权评分，得到每个节点四种资源的占用比分数。
- 判定逻辑：四种资源在节点上越**均衡**，得分越高。

**方案二：网络延迟评估**

- 每个节点上部署**网络探针组件**，测量节点到节点之间的网络延迟，作为微服务访问的网络延迟依据。
- 使用两个算法：
  1. **网络稳定性**：用 **ADF 检验**对过去一小时内的网络延迟时序数据做数学打分，波动越稳定得分越高；
  2. **LSTM 时序预测**：用过去一小时的网络延迟数据预测未来一小时，对预测结果打分，看是否仍能满足微服务的时延要求。

**核心机制：网络延迟矩阵**

- 搭建一个网络延迟矩阵，例如 A、B、C 三个节点即构成一个 3×3 的双向延迟矩阵。
- 假设前端到后端的延迟要求是 50 ms（候选人明确说明这是举例、并非实际场景值）：
  - 若前端已在 A 节点，调度后端时先从延迟矩阵中**筛选**满足延迟要求的候补节点；
  - 例如 C 到 A 的延迟是 30 ms、B 到 A 是 100 ms，则只筛出 C；
- 对筛出的可用节点，再用**四维资源打分 + 网络稳定性打分 + 时序预测打分**，并引入**合作博弈效用函数**平衡多资源负载与 QoS 冲突；
- 按综合得分排序，**选取得分最高的节点**作为最终的调度目标。

**对论文的改进**

- 原论文的做法较简陋：给每个 Pod 打上特定标签来标识服务依赖，相当于在调度前对每个 Pod 的 YAML 做**人工打标**。
- 候选人认为该机制简陋，在前面增加了一个**预选机制**：
  - 部署微服务时，先通过 trace 或预选数据得到各服务的 trace 依赖图 / 链路图，形成**微服务拓扑图**；
  - 把拓扑图输入调度器，让调度器理解不同服务之间的依赖关系；
- 采用的样例微服务是开源的 **Train Ticket**。
- 补充说明：项目场景是实验室一个比较小的集群；候选人表示当时没有深入研究论文的实际业务背景，是直接从方案和算法层面接手。

**量化结果**

- 调度决策时延降低 **25.94%**；
- 集群平均负载均衡度提升 **10.29%**。
- 这两个数字在录音里没有完整出现，建议面试时主动讲出来。

### 关键评价点

- 结构清晰：延迟矩阵做**初筛（硬约束）**、三维打分为**排序（软约束）**，符合调度器 Filter/Score 的经典分层；对应简历表述为“基于 Scheduling Framework 落地 **NeiLatS** 调度插件”。
- 可被追问的点：
  - 功效系数法的**指标阈值与满意度函数**如何设定（功效系数法需要为每个指标定义满意值与不允许值）；
  - 网络探针的**测量频率与开销**，以及延迟矩阵的更新周期与时效性，Net-topology 构建时延矩阵的采集周期；
  - 预测在 1 小时粒度上是否足够支撑调度决策（微服务调度通常需要秒级/分钟级响应）；
  - “资源越均衡分数越高”与“选择最空闲节点”相比，在什么场景下更优；
  - 与原生 **Scheduling Framework** 的结合点：算法落在 Prefilter / Filter / Score 哪个扩展点，如何注册为插件；
  - 25.94% 与 10.29% 的实验设置（集群规模、压测方式、对比基线）。

## 六、Kubernetes 组件与调度流程（约 34:37—41:55）

### 面试官问题（根据回答还原）

讲一下 Kubernetes 里你熟悉的组件，以及创建一个 Pod 的完整调度流程。

### 候选人回答

- 开场坦言：“K8s 这一块其实也有一段时间没看，最近一直在搞 AI。”
- **kube-proxy**：主要负责集群网络、不同节点之间的网络，候选人形容为“类似一个 DNS 服务”。
- **kube-controller-manager**：管理集群内不同资源的各种 Controller，包含 **Pod、Deployment、DaemonSet**、Service 等资源的控制器，负责这些资源的生命周期（如创建、销毁）。
- **kube-scheduler**：默认调度器。创建 Pod 时的流程：
  1. **API Server** 收到请求；
  2. 先做 **Admission 准入检查**；
  3. 检查完成后交给 **Informer 机制**，收到事件后加入队列；
  4. 后面有多个 **Worker** 并发处理不同事件变更；
  5. Worker 发现 Pod 的**调度节点**尚未填充时，把任务派发给 kube-scheduler；
  6. 调度完成后 kube-scheduler 把节点信息填上；
  7. 再次经由 Informer 机制，由 **kube-controller-manager** 订阅到该资源，并在对应节点上创建；
  8. 各节点上还有 **kubelet**，接收主节点下发的信息，管理本节点上基础资源的生命周期与通信。
- **CoreDNS**：管理集群内所有容器的网络通信；同时依赖第三方网络插件（如 **Flannel** 或 **Calico**）实现集群内不同 Pod 之间的跨节点访问。

### 关键评价点

- 流程主干正确（API Server → 准入 → 队列 → scheduler → 绑定 → controller → kubelet），组件职责也基本对。
- 几处**明显口误**需要在后续面试中修正：
  - **API Server 不是“组件里的服务”，而是整个流程的唯一入口**，所有组件都通过 watch/list 与它交互；
  - **kube-proxy 不等于 DNS**：kube-proxy 负责 Service 的转发规则（iptables/IPVS）；DNS 由 **CoreDNS** 提供，二者职责要分清；
  - **Informer 是 client-go 的本地缓存 + 事件分发机制**，不是“把事件加入队列再交给 Worker”的独立组件；调度本身是 scheduler 的 watch → 调度队列（activeQ）→ 调度周期；
  - **kubelet 负责 Pod 实际运行与探针执行**，不是“接收信息管理通信”；容器网络由 CNI 插件负责。
- 候选人自述“一段时间没看、最近在搞 AI”，态度诚实，但这类组件题在 SRE 面试中属于**必然出现的基础题**，建议按“控制面组件 + 数据面组件 + CNI/DNS”三层重新梳理一遍。
- 建议准备一份**1 分钟口述版调度流程**（含 Scheduler Framework 扩展点），与第五节的调度项目形成呼应。

## 七、服务暴露、Ingress 与探针（约 41:55—49:54）

### 面试官问题（根据回答还原）

Pod 如何被调度到指定节点？集群内的服务如何暴露？Ingress 是用来做什么的？存活探针和就绪探针的区别？

### 候选人回答

**调度到指定节点的两种方式**

1. 直接在 YAML 里指定 `nodeName`（候选人形容为“比较生硬”）；
2. 使用 **Affinity / Anti-Affinity** 亲和性机制，打上对应的亲和性标签，kube-scheduler 调度时依据亲和性标志把 Pod 调度到对应节点。
- 候选人补充：也可能存在调度失败的情况（提到 Pod 亲和性相关）。

**服务如何暴露**

- 容器本身要有**暴露端口**。
- 集群内涉及两个资源：**Endpoint** 与 **Service**；Endpoint 关联到对应容器暴露的端口，再对应到 Service。
- Service 类型：
  1. **ClusterIP**：只能在集群内部访问；
  2. **NodePort**：通过主节点或其他节点 IP 加 Service 端口直接访问；
  3. **LoadBalancer**：需要在云上有负载均衡器才能获得较好的访问；
  4. **Ingress Nginx**：集群内部署 Ingress Nginx，通过域名访问；先在 Ingress 层做负载均衡，再在 Service / Pod 层做一次负载均衡，最终访问到 Pod 容器内的服务。

**为什么要用 Ingress**

- 直接通过 Service 访问时，若某应用有 5 个 Pod，Service 是**轮询**机制，第一次请求给第一个 Pod、第二次给第二个。
- Ingress 是在**另一个层面做聚合**：多个 Service 可能对应不同的 Pod，但它们同属一个应用的不同功能，需要**同一个域名**加不同的访问路径来区分。
- 做法：在 Ingress 里配置域名，把不同域名 / 路径配上不同的 Service 资源，即可通过 Ingress 访问同一应用的不同功能，实现服务聚合。
- Ingress 由两部分组成：
  1. **Ingress Controller**：以 **Pod** 方式部署；
  2. **域名配置**：本身是一份配置文件，不以 Pod 方式部署；
  - Ingress Controller 读取 Ingress 配置文件后实现对应的路由机制。
- 候选人补充：“这块可能还是没往细节去了解。”

**探针（Probe）**

- **存活探针（livenessProbe）**：看当前容器是否正常运行。
  - 一个 Pod 里可能有不同容器，例如 sidecar 以及 Pod 自带配置中类似代理的容器；
  - 存活探针主要判断容器是否处于正常运行状态；
  - 候选人提到底层有一个 **pause 镜像**，通过探活该镜像判断容器是否正常；
  - 容器有两个状态：**Running** 与 **Ready**，存活探针主要管 Running 状态。
- **就绪探针（readinessProbe）**：访问容器对应暴露的服务端口。
  - 例如服务暴露在 8080，会有对应的地址如 `/healthz`；
  - 就绪探针主要检查该端口 / 地址，判断服务是否已经**准备就绪**、可以正常接收流量；
  - 候选人总结其作用是保证服务稳定性，相当于一种**容灾**机制。

### 关键评价点

- 主干正确，但有几处需要纠正：
  - **Endpoint 不是与 Service 并列的“另两个资源”**：Endpoints 是 Service 背后的实际后端地址列表（由 EndpointSlice 维护），二者是绑定关系而非并列；
  - **Ingress 与 Service 不是“两个层次的负载均衡”这种描述**：Ingress Controller 通常本身就是 7 层代理（Nginx），它直接转发到 Service 的 Endpoint，不存在“Ingress 层均衡一次、Service 层再均衡一次”的两次独立均衡；
  - **pause 镜像与探针无关**：pause 容器只负责持有 Pod 的网络命名空间；探针是 **kubelet 发起的 HTTP/TCP/exec 探测**，与 pause 无关；
  - **Running / Ready 是容器状态字段**，而探针作用于 **Pod 级别**（严格说是 container 级探针、Pod 汇总为 Ready 条件）。
- `nodeName` 与亲和性之外，还应提到 `nodeSelector`、Taints/Tolerations，以及**亲和性调度失败时的表现**（Pod 处于 Pending，可通过 event 排查）。

## 八、服务稳定性保障（约 50:16—52:32）

### 面试官问题（根据回答还原）

在生产环境中，如何保证一个服务（一组 Pod）的稳定性？

### 候选人回答

1. **单点故障**：不能把所有 Pod 都调度到同一个节点。
   - 一是会加重该节点负载；
   - 二是节点宕机则整个服务不可用。
2. **扩缩容**：
   - 低谷时保留 2—3 个副本；
   - 随着访问量增加，使用 **HPA** 做横向扩缩容，从 2—3 个扩到 5—10 个甚至更多，保证访问质量与延迟。
3. **发布与滚动更新**：
   - 不能把所有 Pod 一次性 kill 再发新版本；
   - 有渐进机制：例如一共 6 个副本，先 kill 一两个并替换为新版本，确认稳定后再逐步替换剩余 4 个。
4. **监控与告警**：对服务做指标监控与**阈值告警**；
   - 最好有自动化脚本，出现简单故障时能**自动重启 / 自动修复**。

### 关键评价点

- 四个方面（反亲和、HPA、滚动更新、监控告警+自愈）覆盖了 SRE 的主要动作，属于合格回答。
- 可以进一步补强：
  - 反亲和的具体手段（`podAntiAffinity`、`topologySpreadConstraints`、PDB）；
  - HPA 的指标来源（CPU/内存/自定义指标）与扩缩容延迟；
  - 滚动更新的参数（`maxSurge` / `maxUnavailable`）与配合 **readinessProbe** 才能保证不断流；
  - 加上 **PDB（PodDisruptionBudget）** 保证人为/节点维护时的可用性；
  - “自动修复”要说明边界与防误伤（这恰好是候选人实习中 Agent 的场景，可以串起来讲）。

## 九、Go 与 MySQL 基础（约 52:41—56:26）

### 面试官问题（根据回答还原）

Go 里的 slice 是怎么实现的？扩容是怎么做的？channel 关闭之后还能读写吗？MySQL 慢查询怎么排查？

### 候选人回答

**Slice**

- 候选人记忆较为模糊：“切片它好像利用了动态数组”，“分配在堆里面，有点像 C++ 的 vector”；
- 描述为：一开始定义时会分配比如 10 个元素的空间，逐渐占满之后会迁移到内存 / 堆的另一块空间去完成扩容；
- 自述“不太熟悉”“用的比较少”。

**Channel 关闭后**

- 候选人表示：channel 不像其他语言那样中间有一个缓冲区，Go 的 channel 是“通过内存直接访问到另一个区域去的”，因此“channel 关闭的话应该是不能（读写）了”；
- 随后补充“其实我不是很确定”；
- 并说明自己在 Go 里 **channel 用得比较少**。

**MySQL 慢查询排查**

- 候选人表示自己 MySQL 用得多一些，**Redis** 之类用得少。
- 排查思路分两个层面：
  1. 先检查**网络**，看是否是网络延迟导致 MySQL 慢；
  2. 再检查自己在 Go 里写的 **SQL 是否合适**，是否会造成慢查询；
  3. 如果以上都没问题，则可能是 **MySQL 服务器端**的问题；
  4. 另外考虑 **连接池**：连接过多、或 MySQL 服务器处理不过来，都会导致慢查询。

### 关键评价点

- **Slice 部分答错关键点**：Go 的 slice 是**三元描述符**（array 指针 + len + cap），扩容由 `runtime.growslice` 完成；容量小于 256 时约按 2 倍增长，更大时增长比例逐步下降；**不保证永远是 2 倍**。建议按“描述符结构 → 容量足够直接写 → 不足则分配新数组并拷贝 → 共享底层数组的陷阱（三下标切片）”重新组织。
- **Channel 部分答错**：channel 关闭后**仍可读**——有缓冲则先读完缓冲区再返回零值与 `ok=false`；无缓冲则立即返回 `ok=false`。**关闭后写入会 panic**（`send on closed channel`）。nil channel 读写均永久阻塞、close 会 panic、重复 close 会 panic。这是高频必问题，务必记牢。
- 这两题与快手二面考的是同一组知识点（slice、channel），两场都答得不够扎实，属于**优先级最高的补强项**。简历里写了“并发编程实现 Raft 共识算法并通过测试”，channel 答成这样会显得矛盾，务必补上。
- MySQL 排查思路方向正确（网络 → SQL → 服务端 → 连接池），可以再补：慢查询日志与 `EXPLAIN`、索引与最左前缀、`SHOW PROCESSLIST`/`SHOW ENGINE INNODB STATUS`、锁等待与连接池参数（`max_open_conns` 等）。

## 十、线上故障处理流程（约 56:58—59:23）

### 面试官问题（根据回答还原）

你参与过线上故障的处理吗？讲一下完整的处理流程。

### 候选人回答

- 候选人如实表示：实习期间**没有具体处理过某个线上故障**，但团队带着他完整参与了流程。
- 以 7 月份一次较大的**集团级故障**为例：
  1. **感知**：业务运维员与普通运维员都能感知到故障；
  2. **确定归属**：第一步判断根因在哪一侧——是哪个集团 BU、哪个部门的事件变更导致的；
  3. **自身侧排查**：通过 SRE Agent 收集各种变更信息与水位信息，判断是哪个组件或哪个水位异常导致；
  4. **定位**：查到是 **DNS 访问量暴涨**；进一步查 DNS 的变更事件，发现是有团队在做**容灾演练**导致访问量暴涨；
  5. **沟通**：业务运维员、普通运维员、稳定性运维员与该团队沟通，了解其具体机制；
  6. **快速恢复**：对方团队感知后先做“快恢”，即**切流**——把当前 DNS 使用的集群切到另一个集群，保证业务与集团内服务不受影响；
  7. **根因定位与排查**：联系多方与导致问题的部门做根因定位和排查；
  8. **复盘与演练**：排查后做了故障复盘与演练，之后对本次故障做总结与交流。

### 关键评价点

- 虽然只是“参与观察”，但把“感知 → 归属判断 → 收集信息定位 → 跨团队沟通 → 止血（切流） → 根因排查 → 复盘演练”的链路讲清楚了，**止血优先、根因后置**的顺序正确，也正好呼应实习项目里 Agent 覆盖的环节。
- 需要准备的追问：
  - 为什么是切流而不是回滚变更？判断依据是什么；
  - 演练导致生产故障，是否有变更管控 / 演练隔离机制，事后如何防止；
  - 你自己在这个流程里具体做了什么（哪怕是收集数据、记录时间线）；
  - 故障时长、影响面、MTTR 等关键指标。
- 建议把这段与第一面的“1 分钟感知、5 分钟定位、10 分钟完成”目标口径对齐讲述，形成一致的个人叙事。
