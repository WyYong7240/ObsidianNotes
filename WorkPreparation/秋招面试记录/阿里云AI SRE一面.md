### 编程题：力扣 Hot 100「两数之和」

题面（经本人确认）：给定一个整数数组 `nums` 和一个目标值 `target`，在数组中找出和为 `target` 的两个整数，返回它们的数组下标；同一元素不能重复使用，答案唯一。

候选人提交的是核心逻辑函数，采用哈希表一次遍历：

- 遍历数组，对当前元素 `nums[i]` 计算补数 `target - nums[i]`；
- 若补数已在哈希表中，直接返回 `{map[补数], i}`；
- 否则把 `nums[i] -> i` 存入哈希表，继续遍历。

时间复杂度 **O(n)**（每个元素只访问一次），空间复杂度 **O(n)**（哈希表最多存 n 个元素），相比暴力双重循环的 O(n²) 是标准最优解。

### 关键评价点

- 这道题属于力扣 Hot 100 的入门题，**关键是别只写出来，还要讲清为什么用哈希表**：朴素解法要两层循环枚举所有配对（O(n²)），用哈希表把"查找补数"从 O(n) 降到 O(1)，把两层循环压成一次遍历。
- 讲完最优解后再补一句可延伸方向会更完整：如果数组已排序，可以用**双指针**做到 O(n) 时间、O(1) 额外空间；如果要返回"所有不重复的配对"（两数之和 / 三数之和类变体），还需要额外做去重。
- 别漏边界条件：数组为空或长度小于 2、存在重复元素、负数以及 `target` 为 0 的情形——这几句话只要 10 秒，却能体现工程习惯。
- 从"直接写核心逻辑函数"到"主动阐述算法思想"的节奏是对的，**写完主动讲思路**比等面试官提问更占优。

## 四、Agent 的实际提效与"1-5-10"目标（约 15:45—18:40）

"数据层面有没有做过对比？"

### 关键评价点

- "流程时间缩短"这个替代指标选得合理，但**表述偏保守、也偏模糊**。建议改成"定位阶段耗时从十几分钟压到几分钟"这种可引用的量化句，并主动说明这是同事使用后的反馈而非严格 A/B 数据——先自我限定，反而更可信。
- 1-5-10 是很好的行业锚点，建议记牢并说明**你们的 Agent 主要贡献在"5 分钟定位"这一段**，这样听众能立刻抓到价值点。

## 五、为什么用 Agent 而不是算法（约 18:40—21:27）

### 面试官问题

"为什么使用 Agent 而不是算法？"

### 候选人回答

- 团队原本的根因定位方式其实靠**拉会议 + 人工**，当时似乎并没有考虑过使用算法。
- 如果使用算法：从"感知"到"信息收集"这一段仍然需要人工介入，或者必须自己额外搭建一条串联的平台链路，才能做到"感知 → 信息收集 → 算法给出根因 → 人去执行"。
- 使用 Agent 的好处是它**更接近人的思维方式**：能够端到端理解"从故障感知到根因定位"的完整过程；并且可以通过**长短期记忆 + 团队知识库 / 个人知识库**减少人力投入；在后续恢复、流程处理等环节，Agent 还具备**全局记忆**，能够像人一样继续跟进故障处理流程。

### 关键评价点

- 这个回答把差异落在了"是否需要人搭一条链路"和"是否有贯穿全流程的记忆"上，比"Agent 更智能"这种空泛表述扎实得多，是本场的高分点之一。
- 可以再补一句边界：**"感知环节仍依赖监控平台，Agent 的价值集中在感知之后的收集、整合与定位"**，避免被追问"感知为什么不交给 Agent"。

## 六、Agent 平台与既有平台的差异（约 21:27—24:13）

### 面试官问题

面试官追问为什么要把这些事情都集中到一个 Agent 平台上。

### 候选人回答

- 候选人当时构建的原型 demo 已在团队内部运行，可以拿它和算法方案对比：算法能覆盖的只是"信息收集 → 故障定位 → 给出结论 → 进入后续流程"这一部分。
- 引入 Agent 之后还能覆盖**巡检任务**等更多场景。
- 关键在于**把 SRE 的各项任务集中到一个平台上**：此前"从信息收集到根因定位"是一条技术线、**巡检**可能是另一个平台或另一条线、**水位监控与值班排班**以及**压测与演练安排、人员安排**又是另外的线；使用算法方案时，这些工作天然分散。
- 目标是在同一个平台、同一个体系下处理多项事务，让业务运维与质量保障人员**不再跨平台**。

### 关键评价点

- "把分散的多条技术线收敛到一个入口"是很好的一句话总结，本质上做的是**运维工作流的统一入口**，可以更自信地说出来。
- 建议用一句话点明边界："平台负责统一入口与编排，各业务部门的底层能力仍以 MCP / CLI 形式接入"，这样既准确，也自然过渡到后面 MCP 与 CLI 的讨论。

## 七、System Prompt 优化的来龙去脉（约 24:13—28:30）

### 面试官问题

"System Prompt 优化这一块当时是怎么考虑的？"

### 候选人回答

- 优化是基于自己构建的评测框架平台做的；评测框架的构建花了大约一个多月，7 月中下旬产出了 Prompt 优化。
- 背景问题：6 月份线上使用的是 **Claude 系模型**，而 Agent 平台是**多人共同使用**，6—7 月的 Token 消耗与模型成本都偏高。
- 因此有两条优化方向：
  - **方向一：在 Harness 层面做 System Prompt 优化**（包括对 Skills 的优化），压降冗余工具调用与冗余 Token；
  - **方向二：把 Agent 改造成多层子代理结构**，让不同子 Agent 针对不同任务使用不同模型——轻量任务用成本较低的模型分层处理，而不是把所有类型的任务都塞给配置高成本模型的主 Agent。
  - 候选人分到的是**方向一（System Prompt 优化）**。
- 评测 case 的来源非常关键：把业务运营人员与业务人员在使用 Agent 时**真实问过的问题、真实 session 存到评测平台**，作为后续的评测 case。
- 评测得到的结论：**不同模型在相同 Harness 框架下有不同偏好**——
  - **GPT 系模型**在每次工具调用之前会先做一轮环境预检查，导致大量冗余 Token 消耗与冗余工具调用；
  - **某些模型**在 MCP 或 CRM 调用失败时会高频重复（十几次到二十几次）且全部失败，需要对重试次数做预先限制。
- 基于这两类现象做针对性 System Prompt 优化后，用同样的模型、同样的 Harness 框架、同样的 case 重新评测，得出"可削减 **50%** Token 消耗与 **33%** 冗余工具调用"的结论；一周后上线到预发与线上环境测试，效果良好。

### 关键评价点

- "用真实 session 做 case"是本场最值得记住的一个设计，它同时解决了**样本真实性**和**评测集与业务对齐**两个问题，建议在讲评测框架时优先抛出来。
- "不同模型在同一 Harness 下有不同偏好（预检查型 / 重试型）"是很有辨识度的观察，比笼统说"某模型更好"更有说服力；可以把它概括成一句可复述的结论。

## 八、System Prompt 的演进与"19 条预定义"（约 28:30—30:43）

### 面试官问题

面试官追问 Prompt / 框架的迭代方式（并提醒 Prompt 过长可能带来的问题）。

### 候选人回答

- 8 月初中之前，Agent 的迭代整体比较**无序**：谁认为 Agent 在某方面有问题，就往 System Prompt 里加一条。
- 到离职前，System Prompt 大约积累了 **19 条预定义**，例如：执行某些任务前必须先查看数据库文档或团队知识库；执行工具调用时不需要做冗余的环境检查；对工具调用失败次数做明确限制等。
- Agent 的整体开发由一个专门的业务运营小团队在运营工作之余进行，因此迭代偏随意；直到 8 月问题逐渐显露，才想到去系统性地优化 System Prompt 与 Skills，并做更好的整合。
- 对于面试官提出的"Prompt 比较长会不会导致问题"，候选人认同：Prompt 太长会让模型注意力涣散，最终可能偏离原本的设计。

### 关键评价点

- 这一段的坦诚是加分项，**但不要把"无序"讲成散漫**。更好的说法是："早期迭代是问题驱动、逐条追加；当条数积累到近 20 条后，副作用（注意力涣散、规则冲突）开始显现，因此我们转向通过评测来验证每一条规则是否真的带来收益。"
- 19 条这个数字很有信息量，如果记得其中**哪几条是收益最大的**，会让回答从"我参与过优化"升级成"我知道哪条优化最有效"。

## 十、评测框架的 case 分类与六个维度（约 31:48—36:13）

### 面试官问题

"这些指标和标准是怎么定的？"

### 候选人回答

- 候选人先明确归属：**整套评测平台都是自己设计的**，只是需要按照团队既有的评测标准与业务迭代框架的需求来设计。
- 评测 case 分为三类：
  1. **多轮对话类型**：在 Agent Chat 页面与 Agent 对话，涉及水位信息、集群水位与模型水位、卡的数量、人员管理等基础问答；
  2. **定时巡检任务**：一般属于两轮对话——第一轮给出指令，第二轮模型给出巡检的实际回复，并把结论推送到内部客户端；
  3. **告警触发类型**：发生故障或水位突变时自动触发，做故障定位与根因分析、给出建议，并把建议做成卡片推送给对应业务人员。
- 针对三类 case 使用不同的评价标准，指标分为**六个维度**：
  1. **完成率**：模型结合当前 Harness 框架对该 case 能做到什么程度；
  2. **回复稳定性**：同一个 case 让同一模型 + 同一框架评测三到四次，看每次结果差异有多大；
  3. **响应时间**（模型响应速度）；
  4. **Token 消耗**；
  5. **友好性**：回复的结构性——以根因定位类 case 为例，要求开头先给结论信息，再给结论的数据支撑与分析过程，最后给总结性分析与可行的操作建议，并做成用户友好型卡片推送到客户端；

- **标准答案的来源**：线上使用 Claude 模型结合当前 Harness 框架时，业务人员或运营人员认可的回复与任务执行路径被记录下来，作为对应 case 的标准答案；再用不同模型作为"考生"参与后续评测。

### 关键评价点

- "线上真实被业务认可的回复 + 执行路径作为标准答案，不同模型当考生"这句话，比"我们做了基准测试"高级得多，是这一题的核心加分句，建议背下来。

## 十二、Kubernetes 深度考察（约 37:00—48:02）

### 面试官问题

- "Kubernetes 这块了解得多吗？日常有用过吗？"
- "Pod 的状态机管理、什么时候是活着的、怎么保持在线的 Pod 数量可控，是怎么做的？"

### 候选人回答

- 实验室 **15 个节点的 K8s 集群由候选人自己搭建**，日常运维任务与应用部署、扩容也由他负责；K8s 的技术组件、**Informer 机制**、**CRD 自定义资源**的定义他都做过。
- 对 K8s 的整体理解：它是跨多节点的容器编排系统，可以理解为"云操作系统"；相比传统 Docker 在单机上以容器方式部署、应用之间隔离，K8s 把多个节点连到同一网络中统一编排。
- 技术组件：**API Server**、**Controller Manager**、**Scheduler**、**etcd**、**CoreDNS**、**kube-proxy**；资源抽象包括 **Pod**、**ConfigMap**、**Service / Endpoint** 等；跨节点容器通信依赖 Service + Endpoint 机制与 kube-proxy。
- 一次创建请求的完整链路（候选人主动展开的重点）：
  1. 定义 YAML 文件，通过 kubectl 等方式向 **API Server** 发送请求；
  2. API Server 先做**认证**（判断请求来源是否合法），再做 **RBAC 鉴权**（判断该角色对目标命名空间/资源是否具备相应权限，例如 kubectl 使用的 ClusterRole 是否包含创建权限）；
  3. 通过 **Mutating Webhook** 与 **Validating Webhook** 做准入检查：先由 Mutating Webhook 对不合法的配置做预修改，再由 Validating Webhook 校验，通过后写入 **etcd**；
  4. 各节点上的 kubelet 内对应的 Controller / Informer 通过**订阅机制**收到资源创建或变更消息，写入 **Delta FIFO** 变更事件队列；
  5. Controller 从队列取到变更后，配合本地 **Index 缓存**避免对 API Server 高频访问（否则可能把 API Server 甚至集群压垮）；
  6. 变更事件进入各资源对应 **Reconciler** 的工作队列（延迟队列实现），工作线程按 Reconcile 逻辑反复调谐，让集群实际状态不断逼近 etcd 中的期望状态，最终使 Deployment 正常运行起来。
- 关于 Pod 状态机与保活：
  - Pod 内除了业务容器，还有一个底层容器（pause 容器）；
  - 状态定义上，**Running** 判断容器是否在运行，**Ready** 通过容器暴露端口上的探针判断服务是否可访问，服务可达后 Pod 从 0/1 变为 1/1；
  - 扩缩容与保活分两种情况：
    - **静态副本数**：Deployment 中定义副本数量（如 5 个），控制器检查实际 Pod 数量与期望值的差异——多了缩容、少了扩容；
    - **HPA 水平扩缩容**：基于流量阈值或 Pod 的 CPU / 内存占用达到设定值触发，并受副本数上下限约束，例如流量攀升时从 5 个扩到 10 个，流量回落后再缩回 5 个或更低，保持动态平衡。

### 关键评价点

- 这是本场最长、也是最扎实的一段：从 API Server 认证鉴权 → 准入 Webhook → etcd → Informer / Delta FIFO → Reconciler 调谐，链路完整，属于**超出一般校招生水平**的回答。
- 可以再补两个常被追问的点：**Informer 的 Reflector / Delta FIFO / Indexer 三层结构**，以及 **kubelet 与 pause 容器、Sandbox 的关系**（可以顺势接到实习里的沙箱话题）。
- 值得注意的风险：整段回答缺少"实践证据"。建议在讲完原理后补一句"这些机制我在自建集群和 CRD / Operator 开发里都实际用过"，把知识变成经历。

## 十三、Agent 项目的动机与职业规划（约 48:02—52:51）

### 面试官问题

面试官请候选人说明做这个 K8s Agent 项目的动机，以及自己的职业规划。

### 候选人回答

- 动机来自日常痛点：实验室集群的运维全由候选人自己做，**Prometheus 指标采集、各类日志采集都是人工操作**；遇到 **Pod 故障**时每次都要用 `kubectl describe` 查看状态，必要时还要 `kubectl exec` 进容器查日志手动定位，再把日志与指标信息用算法或上网搜索的方式做根因定位——对实验室而言这是一个**重复且繁琐**的过程。
- 因此想借助 Agent，让 AI 去执行"诊断与恢复信息收集"这一过程。
- 实现方案的框架选择：当时考虑过 **LangChain** 与 **LangGraph**——LangChain 的特点是能快速完成 AI 应用的构建与迭代验证；LangGraph 粒度更细，更适合做多 Agent 之间的流程编排与流程控制。
- 最终选择 LangGraph，是因为**故障定位本质上存在状态流转**：从故障感知 → 信息收集（先问 Pod 当前状态、为什么故障）→ 信息整合 → 结合运维手册与经验做综合诊断 → 判断结果是否足以给出定位与可行建议，如果不够还要**回到前面的步骤**调用 MCP 工具获取更详细的信息（如 ConfigMap 等）。这种不确定的状态流转更适合用多 Agent 系统承载，因此他把系统定义成**四个 Agent 协同**的流程控制架构。
- 职业规划：先**从运维入手**，逐渐了解企业里的流程、常见操作方式与真实痛点；再据此不断用 Agent 去解决这些痛点，最终把 Agent 做到 **AI SRE / AIOps 比较理想的状态**——流程由人审批与执行，但前面整个过程有较高的可用性与正确性保障。

### 关键评价点

- "痛点驱动 + 框架对比 + 状态流转论证"这条线讲得非常完整，是本场最能体现工程判断力的一段；LangChain / LangGraph 的对比口径与快手 SRE 三面的回答一致，可以放心复用。
- 需要补强的是**效果与边界**：本场没有提到"操作执行仍由人工完成"的安全边界，也没有给项目的量化结果。建议补一句"暂不开放写操作、只在只读诊断与建议环节自动化"，与前面的安全叙事一致。
