## 三、算法基础：NlogN 排序与堆排序实现（约 11:40—15:08）

### 面试官问题

- "N log N 的算法有哪些？"
- "讲一下堆排序的实现逻辑。"（并明确要求"从代码上面去讲大顶堆实现逻辑"）
- "为什么是 log n？"

### 候选人回答

- N log N 的经典算法：**快排**（平均 N log N，最差 N²）、**堆排序**、**归并排序**。
- 堆排序实现（候选人按"数组存二叉树"的思路讲）：
  1. 堆用**数组**存放二叉树结构，通过下标定位子节点（下标 0 的左右子节点为 1、2 这类关系）；
  2. 有一个**初始化**过程：从数组中间位置（即最后一个非叶节点）开始，对最小的子树做堆调整（以大顶堆为例，让子节点都小于根），再逐级往上调整，直到整个堆的根节点是数组最大值、逐层递减，完成初始化；
  3. 初始化后把**大顶堆的根节点摘下来放到数组末尾**，把末尾的数换到堆顶，再做第二轮调整；第二轮调整不再涉及已摘除的最大值，**调整范围逐轮缩小**；
  4. 重复"摘根 → 换末尾 → 调整"，直到整个排序完成；
  5. 复杂度：每次调整是 **log n**，一共调整 n 个数，所以整体是 **n log n**。
- 对"为什么是 log n"的回答：堆是以**完全二叉树**形式存在的，数组长度为 n 时，树的高度是 log n，因此从堆顶调整到最底层叶子的最大频次就是 log n；调整过程是逐层与左右子节点比较、对调后进入下一层，直到叶子节点。

### 关键评价点

- 原理部分讲得清楚（数组下标关系、从最后一个非叶节点起调整、缩小堆范围），但**面试官明确要求"从代码上讲"，你只给了原理**，没有给出代码实现。这是本场第一个遗憾点。
- 建议准备一段 10 行的 Go 代码骨架并在脑中过熟：`heapify(arr, n, i)`（比较 `2i+1`、`2i+2` 并递归下沉）+ `for i := n/2 - 1; i >= 0; i-- { heapify(...) }` 建堆 + `for i := n-1; i > 0; i-- { swap(arr[0], arr[i]); heapify(arr, i, 0) }` 排序。
- 顺带补两个常被追问的点：**建堆的复杂度是 O(n) 而非 O(n log n)**（自底向上建堆的求和收敛），以及**升序排序要用大顶堆、降序用小顶堆**。

## 四、网络基础：TCP/UDP 与可靠性机制（约 15:08—21:42）

### 面试官问题

- "TCP 和 UDP 的区别？"
- "TCP 的可靠性是怎么保障的？"
- "拥塞控制呢？" → "窗口大小一般怎么调节？"

### 候选人回答

- **TCP** 适用于稳定传输：有三次握手与四次挥手的连接过程；每次连接前发连接请求、ACK 确认后才传输；后续每个数据包的发送都伴随接收端的 ACK 确认，未收到 ACK 会**重传**，因此能保证**顺序与稳定**的传输。
- **UDP** 没有稳定性保障：只负责发出去，不保证顺序、也不保证对方一定收到。
- 但 TCP 的缺陷是不适合**音视频**这类实时性要求强的场景（延迟敏感），反而是 UDP 更适合直播、通话——即使损失一部分语音/视频信息也可以接受。
- TCP 的可靠性机制：
  - 三次握手 / 四次挥手建立与释放连接；
  - 通过 **ACK 确认 + 重传机制**保证可靠；
  - **重传采用指数退避**：第一次失败后按一个单位时间重传，再次失败则成倍拉长（1→2→4→…），直到达到上限后不再继续上升。
- 拥塞控制：
  - **滑动窗口**机制：发送端有窗口、接收端也有窗口；接收端对窗口内的数据包做确认并回送发送端，发送端发现窗口数据已被确认后把窗口向后滑动若干个单位，再发送新窗口内尚未发送的数据包，接收端同样按确认情况滑动窗口，形成持续的滑动过程；
  - 窗口大小可以调节——候选人理解为**根据网络指标计算调节**（如通信信道的状况、以及收发双方事前约定的协议）。

### 关键评价点

- 基础答得稳（三次握手/四次挥手、ACK、重传、指数退避、滑动窗口），属于合格线以上。
- 可以再补三层深度，把"知道"变成"懂"：
  - **可靠性的完整组成**：序号/确认号、超时重传与快速重传（三次重复 ACK）、校验和、流量控制（滑动窗口 + 零窗口探测）、连接管理（TIME_WAIT）；
  - **拥塞控制的四个阶段**：慢启动（指数增长）→ 拥塞避免（线性增长）→ 快速重传/快速恢复；以及现代算法 **CUBIC / BBR**（BBR 基于带宽与时延估计而非丢包）；
  - **窗口调节的本质**：发送窗口 = min(拥塞窗口 cwnd, 接收方通告窗口 rwnd)，两者分别由网络拥塞与接收端处理能力决定——这一句能直接回答面试官那个"窗口怎么调节"的问题。

## 五、项目深挖：SRE Benchmark 的设计动机与方案（约 22:09—28:57）

### 面试官问题

> "讲一个你觉得困难的项目，或者最有成就感的项目。"

### 候选人回答

- 选择**实习期间的 SRE Benchmark 评测框架**。
- **遇到的困难**：
  - 业务需求要求**尽快上线、快速做原型验证**；
  - 但现有论文与现成的 SRE 评测框架，基本方法都是**搭建一个完全虚拟的环境**，再把 Agent 放进去评测；
  - 而当时整个框架只有他一个人搭建，若要做完全虚拟环境：一方面 SRE Agent 所连接的 **MCP 提供方跨不同业务部门**，需要跨部门协同，各 MCP 的**数据快照建设**涉及层面多、非常耗时；另一方面 **Harness 框架不断迭代、SRE 任务迭代速度也快**，完全虚拟环境跟不上这种节奏。
- **采用的方案**：
  - 用**线上模型产出的答案作为参考基准**，用**线上运维人员真实会问的问题**作为评测案例；
  - 每个评测案例记录**两部分**：① 模型对任务的真实回复（业务人员能看到的那份回复）；② Agent 执行任务时的**工具执行链路**——执行了哪些工具、顺序如何、每个工具传入的参数是什么；
  - 这两部分共同用于解决**任务完成率**的评价问题。
- **六个指标**：Token 消耗、模型响应时间、任务完成率、任务执行一致性（同一 SRE 任务执行多次要求结果尽量一致）、工具调用有效性、用户阅读友好性。
- **评分机制**：其中两个指标使用 **LLM as Judge**（大模型评分），但其输出稳定性不理想；因此把 SRE 任务分成三类——**多轮对话类型、巡检任务类型、告警触发类型（故障定位）**——针对不同类型制定不同的评分标准；并支持**人工打标**：对评分与实际需求有出入的案例人工打分并给出理由，让**评分提示词不断迭代优化**，最终让评分标准满足业务需求。
- **最终效果**：能够在评分框架下区分各模型在该 Harness 框架下的性能差异；能分析出哪些模型适合根因定位 / 告警触发、哪些适合多轮对话与日常复杂任务、哪些适合巡检任务；最终产出**各模型对比报告**，据此确定上线哪些模型。
- **额外产出**：System Prompt 优化。
- **对项目的自评（这段很关键）**：
  - 它在项目**初期**起到了迭代验证作用，但**到后期对 Agent 迭代循环的帮助有限**；
  - 因此他后期的设计需求是：评测框架不能只"发现问题"，还要把 **Better Harness** 加入循环——由 Better Harness 仔细检查当前 Agent Harness 具体有哪些问题、输出一份 **Harness 诊断报告**，交给 SRE Agent 研发去解决，解决之后把新 Harness 放回评测平台验证，从而形成"**评测发现问题 → Harness 诊断 → 研发修复 → 再评测验证**"的迭代闭环；
  - 离职前该循环**已经实现**。

### 关键评价点

- 这一段是本场的高分核心：**"不做完全虚拟环境，改用线上真实 session + 工具调用链路作为基准"**，是一个有真实工程约束支撑的取舍（人力、跨部门协同、迭代速度三个约束都说清了），比"我们做了一套评测系统"有说服力得多。
- "**评测器要能输出可执行的问题定位（Better Harness 诊断报告）**"这一步是把评测从"打分"升级成"闭环"，是本场最亮的思考，建议作为固定主线表达。
- 待补强：**为什么 LLM as Judge 不稳定**没有讲（可以说"同一 case 多次评分方差大、对结构化要求类任务偏好宽松"），以及**人工打标的量级**（多少条、谁打）——这两个细节能让"机制"显得落地。

## 六、System Prompt 优化的具体过程与效果（约 28:57—30:49）

### 面试官问题

> "你觉得做的最有成就感的地方？"

### 候选人回答

- 最有成就感的是 **System Prompt 优化**——它算是额外产出，但当时对团队 Agent 的使用帮助很大。
- 发现过程：用评测框架评测 Harness 时，发现**不同模型对 Agent 任务有不同的工具调用偏好**：
  - **GPT 系模型**在调用工具之前喜欢先**预先检查当前环境**是否满足调用需求；
  - **某些模型**在工具调用失败之后会**重复调用同一工具**，一个失败可能重试十几次、二十几次，产生大量冗余 Token 与冗余工具调用，导致响应时间与 Token 成本上升。
- 优化与验证：
  - 产出 System Prompt 优化后，**实验平台**上的效果是削减 **50% 的 Token 消耗**、**33% 的冗余工具调用**；
  - 上线时先在**预发环境**验证，再上**线上环境**；验证后确实能削减约 **18% 的输入 Token**、**57% 的输出 Token**、**30% 的冗余工具调用**；
  - 上线后调研：同事认为优化前后使用体验没有衰减，甚至有所提升；
  - **8 月份的整体 Token 消耗相比 6—7 月有明显降低**，对团队帮助较大。
- 项目缺陷自评：当时设定的**任务粒度还不够细**——三类任务（多轮对话、告警触发、巡检）应进一步细分并结构化（例如多轮对话里还包含水位查询、人员值班安排修改、Skill 沉淀、故障定位等真正不同的任务类型），针对更细类型再做对应评分标准，并让评分输出稳定（而不是依赖 LLM as Judge 的不稳定评分），这样才能对不同模型在该类 SRE 任务上给出**更明显的区分度**，让模型选型效果更好。

### 关键评价点

- "**不同模型有不同工具调用偏好**"这个观察非常具体（预检查型 vs 重试型），是别人很难抄的经验，建议在每场面试都主动讲。
- 缺陷自评（任务粒度不够细、评分要结构化）是很好的"自我批判"素材，说明你有工程反思能力；可以再补一句"如果重做，我会先定义**任务分类树**再设计指标"。
- 注意口径：本场"上线输入 18% / 输出 57%"，与自我介绍里的"输入 18.5% / 输出 54%"不一致——同一个面试里前后不一致会被察觉，**至少在同一场里保持一致**。

## 七、故障定位的期望值与实际效果（约 32:37—38:22）

### 面试官问题

- "可以请您重述一遍吗？"
- "我们当时的期望是多少？" → "理解一下怎么评判这个结果？"

### 候选人回答

- 期望：Agent 在**故障定位**上达成 **1-5-10**——1 分钟感知、5 分钟定位、10 分钟恢复。
  - 补充说明：一开始大家比较激进，认为能到"1-1-10"（1 分钟感知、1 分钟定位、10 分钟内恢复）；后来把预期放宽到 **1-5-10**；再往后在实际中发现这个预期偏高，逐渐放宽，最后大家不再提这个概念。按他当时的观察，Agent 实际能完成的情况大概在 **1-5-10 到 1-10-15** 之间。
- 实际效果：虽然没有达到 1-5-10，但相比传统手段（人工做故障诊断、信息收集，再定位、给恢复操作），整个链路的**执行速度有较大提升**——从原本**十几二十分钟**提升到**十分钟量级**（但还没完全压进 10 分钟）。
- 典型案例：6 月底**千问高考**期间（高考访问流量很大）：
  - 现象：模型水位经常比较极限，或触发告警；
  - Agent 能做到：根据告警**迅速定位到哪个模型的水位不对**，或 **QPM / TPM 被限流**、不满足要求；
  - 定位后通过 Agent 自带的 **MCP 工具**把告警信息与定位结论**推送给对应业务人员**；
  - 但**恢复操作仍由业务运维执行**——写入以及与模型侧协调仍由人来做，当时没有实现完全 **A2A** 的形式；
  - Agent 在写入侧能做的只有 **Skill 沉淀**与**值班人员安排**。
- 评判标准与效果口径：常规告警处理的有效率大概在 **40%—60%**；相比当时的人工方式已大幅提高运维效率，满足了对该 Agent 在故障定位上的**初步预期**；此外 Agent 还服务于其他功能（巡检任务由 Agent 自己执行；日常安排、水位查询、信息查询由 Agent 统筹）。

### 关键评价点

- 面试官连问两遍"期望是多少"，说明他想要一个**干净的数字结论**，而回答里出现了"1-1-10 → 1-5-10 → 后来不提了 → 实际 1-5-10 到 1-10-15"的绕线。建议固定成一句话："**目标是 1-5-10；实际做到感知约 1 分钟、定位 10—15 分钟、恢复仍由人工执行，比人工的十几二十分钟有明显提升。**"
- "有效率 40%—60%"这个口径要说明是**哪一类告警**、**分子分母是什么**（是告警自动处理成功率，还是定位准确率），否则容易被追问到答不上来。
- 主动讲"没有做 A2A、写入仍人工"是加分的安全边界意识；也可以顺势说明原因（**写操作的权限与影响面管理尚未建立**）。

## 八、为什么慢，以及后续优化路径（约 38:22—43:48）

### 面试官问题

- "为什么会慢？后面怎么优化的？"
- "有没有量化的标准？"

### 候选人回答

- 慢的原因（经过团队探讨）：
  1. **模型本身**：6—7 月采用的是 **Claude 系模型**，整体 Token 消耗与响应时间都偏慢；
  2. **数据接入方式**：所有数据都通过 **MCP Server** 接入，而 MCP 由不同业务部门提供，**跨部门 MCP 稳定性一般**；MCP 取数后会返回**大量时序数据与纯数值数据**，量比较大，容易占用过多上下文、**分散模型注意力**；
  3. **Harness 层面**本身也有问题。
- 优化动作：
  - 把 **MCP 服务替换成 CLI 服务**——工具调用准确率更高、数据提供的稳定性更好；
  - 在**脚本层面做数据预处理**，把数据**精炼化、特征化**之后再交给 Agent 分析；
  - 结果：有效率从原来的 **40%—50%** 逐步提升到 **50%—60%**。
- 关于"量化标准"：候选人坦言**当时没有一个可量化的标准**；面试官补充了自己的口径——**6 月用的是国外模型、8 月用的是国产模型，只要国产模型能达到 6 月那个外国模型的效果就可以了**。
- 面试官进一步指出：**工程化落地最重要的是能有稳定、可量化的产出**，候选人表示认同，并说明自己的产出就是 SRE Benchmark、System Prompt 优化与评测框架。

### 关键评价点

- "**MCP → CLI + 数据预处理**"这条优化链路讲得很好：把"慢"拆成三类原因（模型、数据通道稳定性、数据噪声占用上下文），再给出对应动作，逻辑完整。
- "没有统一的量化标准"是坦诚，但可以立刻补一个可行的替代方案："**我们后来用同一批 case 上的定位准确率与平均耗时做纵向对比**"——即使不是行业标准，也说明你有量化意识（面试官明显很在这一点上给分，他直接说了"工程化落地最重要的是稳定可量化的产出"）。
- 记下面试官这句话，它既是评价也是提示：**下次讲实习产出时，先给"可复现的量化口径"（同一批 case、同一指标、前后对比），再讲定性收益。**

## 九、知识库与团队能力建设（约 44:39—47:00）

### 面试官问题

- 追问团队知识库与应用文档的组织方式。

### 候选人回答

- 评测框架本身**不涉及 Harness 框架的开发**，但他对 Agent 的重要组成部分有了解：
  - 每个业务运维各自的**个人 Skill**；
  - **团队知识库**；
  - 数据从最初 **MCP 提供**改为后来 **CLI 提供**。
- 当时团队**并没有在"记忆"这块做更多迭代与开发**，重点放在三个方面：**子 Agent 的多 Agent 协同、多租户多业务的实现、团队知识库的构建**。
- 团队知识库：
  - 最初方案是用**内部知识库平台**做存储，后续可能引入 **Obsidian** 这类开源组件；
  - 构建方式：让 Agent 大量学习此前已经沉淀的团队知识库文本，自己去沉淀记忆与检索内容；把这些沉淀内容与线上业务应用构建成**网格化的调用链路知识图谱**，再通过 **RAG** 方式检索出对应业务应用及其上下游应用的文档、技术文档与应用状态。

### 关键评价点

- 这里出现了一次**边界表述上的风险**：面试官追问"这个文档是怎么复制的"时，你先讲了一轮知识库的整体设计，随后才澄清"我不是知识库的负责人，我是辅助构建 Agent，主要负责子代理编排与沙箱多租户实现"。**先划边界、再讲了解**会更稳：`"知识库不是我负责的模块，我了解的是它的存放与检索方式；我负责的是子代理编排与沙箱多租户。"`
- "网格化调用链路知识图谱 + RAG 检索上下游文档"这个描述如果确实见过，值得保留；但要能说清**只做到什么程度**（例如是否已覆盖全部业务、是否有人工校验），否则容易被追问穿。

## 十、子代理编排的两种模式（约 47:00—51:23）

### 面试官问题

> "子代理编排这块你做了什么？" → "你选的是哪一种？" → "怎么保证这个中枢 Agent 不会失效？"

### 候选人回答

- 子代理编排设计**借鉴了 Hermes 的子代理编排**，实现两种方式：
  1. **Delegate Task（委托任务）**：中枢 Agent 在任务执行过程中，根据需求判断哪些任务可以交给子 Agent；创建的子 Agent 运行在**中枢 Agent 对应的 gateway 进程内**；子 Agent **可以并行创建、并行执行**各自任务；完成后把结果返回中枢 Agent，由中枢 Agent **聚合、统筹、分析**并输出。
  2. **看板方式**：**预先构建四个子 Agent**（相当于一个专家团队）；中枢 Agent 收到任务后把任务**拆解成多个子任务放到看板**里；各专家 Agent 判断哪些任务自己能做，从看板**领任务**，执行时还会做**二次分析**——若需要更细的拆解，就把拆出的任务再放回看板，由下一轮其他 Agent 领取；所有任务完成后结果回流到中枢 Agent 统一统筹与分析后输出。
  - 说明：**两种方式当时都实现了**。
- 两者的差异（候选人的对比）：
  - **Delegate Task**：子 Agent 与中枢 Agent 同处一个 gateway 进程，中枢把**任务上下文精炼后**传给子 Agent，子 Agent 拥有**自己单独的上下文段**，完成后把结果返回中枢的上下文；
  - **看板方式**：存在一个**全局的任务表 / 状态表**，子 Agent 领任务后把任务上下文注入自己的上下文（同样是独立上下文），完成后把执行结果写回**全局看板的状态栏**，中枢再统一收集统筹。
- 关于"怎么保证中枢 Agent 不失效"：
  - 每个子任务返回时都会对**结果做一次预处理**，再返回给中枢；
  - 中枢上下文过长可能失效的问题，可以通过**上下文压缩机制**解决——利用看板的全局状态存储，在任务完成后对子任务上下文做**预压缩**，让中枢读取压缩后的结果。

### 关键评价点

- 这是本场**技术含量最高的一段**，两种模式的对比（进程内委托 vs 共享任务看板、独立上下文 vs 全局状态表）讲得清楚且具体，属于可以拿出来当亮点的内容。
- 被问到"中枢失效"时才抛出上下文压缩，略被动。建议主动把**三个风险点**一次讲全：**上下文膨胀（压缩/摘要）、单点失效（看板方式天然抗中断，中枢可从全局状态恢复）、任务重复领取（任务状态机 + 领取锁）**。
- 可以再补一句落地的取舍结论："**Delegate Task 适合短平快的并行子任务，看板方式适合长流程、需要人可介入的复杂任务**"——有取舍结论的回答最能体现工程判断。

## 十一、评测 case 规模与职业规划（约 53:55—58:19）

### 面试官问题

- 追问评测场景与 case 量级。
- "你自己对职业的规划是怎么样的？"
- 追问实习产出。

### 候选人回答

- 评测场景：把**线上真实的业务问题 / 业务 case** 存下来作为评测场景。
- **case 量级**：7 月那批一共 **107 个 case**，8 月那批 **56 个 case**；原因是 7 月正值高考期间使用人多、产生较多 case，8 月之后不重复的 case 较少，还需要筛选。
- 职业规划：
  - **地域**：比较偏向**杭州**（因此投阿里云）；
  - **工作内容**：自己对 SRE 方向比较感兴趣，也对 AI 热潮感兴趣，认为两者结合并落地能**大幅解放运维工作量、推动 SRE 岗位迭代升级**；
  - **路径**：先从基础开始，真实地学习和了解**传统业务运维的完整流程**（故障定位、水位分析、故障演练、容灾方案制定、压力测试等），后续再结合 AI Agent 与更好的 Harness 框架（知识库融入、上下文问题）解决实际场景问题；
  - **最终形态**：像"**数字员工**"一样，能把传统 SRE 中成熟的故障应对手段自行执行、自行恢复、自行定位与恢复，并接收处理其他部门提出的工单。
- 实习产出总结（3 个月）：
  1. **SRE Benchmark 构建**——团队对他最重要的要求，且对线上 SRE Agent 的 Harness 迭代确实有用，主管与 Mentor 已认可；
  2. **System Prompt 优化**——7 月对团队使用体验与成本控制有较好产出；
  3. 由于当时没有可完全借鉴的方法论，在 Mentor 与主管帮助下把这个工作**整理成一篇论文并投稿到学术会议**（目前状态为在投）。
  - 实习满意度自评：满意的是**明确了整个 SRE 任务流程与现状**，并对构建、评测、迭代有实际帮助；还需要深入的是**真实故障处理流程**（业务水位分析、容灾演练等）以及 **Agent 层自身能力的构建**。

### 关键评价点

- case 量级（107 / 56）是很好的"可量化产出"证据，比只说"用真实 session 评测"更有分量，建议以后主动报这两个数字。
- 职业规划讲得有愿景但偏长，可以把落点收得更锋利："**我想做的是把 SRE 的领域知识和 Agent 工程结合起来，第一步是把传统运维流程吃透，第二步是用评测与优化让它可度量、可迭代。**"
- 面试官问你"千问那边有转正吗"时你答了 base 倾向（不想去广州、偏向杭州），这是合理的意愿表达；注意**先给结论再给原因**（"我倾向杭州，一是离家近，二是朋友圈与实验室资源都在杭州"），比"其实哪里都可以，但是……"更利落。
