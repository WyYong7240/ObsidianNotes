- **实习经历：2026 年暑假，阿里巴巴千问事业部 AI SRE**，工作内容分两部分：

### 关键评价点

- 三段经历串成了一条"渐进式 AI 运维"主线（调度 → 可观测与异常检测 → Agent 排障），叙事完整，面试官后续的追问也基本沿着这条线展开。

## 二、Agent 平台的定位：把三条运维线揉进一个平台（约 06:10—07:58）

### 面试官问题

面试官基于自我介绍确认："我刚听你介绍，主要是做一些集群的检测、日志收集这类工作吗？"

### 候选人回答

- 这只是 Agent 功能的一部分。传统运维在团队内实际被分成好几条线：
  - 一条线是**故障场景**：故障定位、信息收集、恢复与演练；
  - 一条线是**业务应用与集群的日常巡检**（原先在集团内部另一个平台上做）；
  - 一条线是 **GPU 卡分配、工单处理、人员值班安排**等事务性工作。
- 过去每条线由不同人负责、或同一个人跨多个平台执行流程，信息分散。
- Agent 平台的主要做法就是**把这些线和事件全部收拢到一个平台**，让业务应用人员和基础质量保障人员在同一平台里结合 AI 处理这些事情，实现**跨业务、跨租户**。

### 关键评价点

- 回答把"Agent 做了什么"上升到了"团队运维流程重组"，格局不错；如果能顺带说明**平台上线前后的效率对比**（例如单次排障耗时）会更有说服力。

## 三、多租户与流程隔离怎么做（约 07:58—10:41）

### 面试官问题

- "多租户这一块和这些流程是怎么做的、怎么隔离的？"
- "一个人一个沙箱？"（候选人回答后面试官确认）

### 候选人回答

- Agent 本身作为**无状态应用**部署在应用集群上，有 **5 个副本**。
- 每个业务人员使用**公司账号**登录 Agent。
- 每个员工对应一个个人的**工作空间**，工作空间落在**云对象存储**上；工作空间里默认包含各自的个人 Skills 等内容。
- 隔离方式：**一个人一个沙箱**，通过沙箱做执行隔离；工作空间只承担**个人状态持久化**的职责。
- 方案由候选人提出，实际实现由团队其他同学完成；候选人在实现之后负责**保证沙箱的稳定性与高可用**。

### 关键评价点

- 这一题的信息密度是本场最高的一段：明确区分了"隔离"（沙箱）与"持久化"（工作空间/对象存储），与前面快手 SRE 三面的沙箱高可用口径完全一致，说明这条主线是站得住的。
- 主动说明"方案我提、实现他们做、我负责稳定性与高可用"是加分项——边界清楚，不会被追问"你凭什么保证平台 HA"。

## 四、评测框架的六个维度（约 10:41—12:51）

### 面试官问题

面试官要求说明评测框架具体评什么。

### 候选人回答

六个维度（候选人自述"相对通用一些"）：

1. **任务完成率**：不同 SRE 任务的 case 交给某个模型 + 这套 Harness 框架后，能完成到什么程度。
2. **一致性**：同一个 case 交给 Agent 执行多次，结果是否稳定一致——第一次回答得好、第二次很敷衍，就会拿到较低评分。
3. **工具调用有效率**：执行任务过程中会调用不同 CLI、MCP、Skills、Terminal 等工具，但并非每次调用都对最终结论有贡献，需要评估冗余调用情况。
4. **回复友好性**（偏主观）：以故障定位为例，要求回复结构为"开头先给结论性的定位结论 → 下面列举原因分析与数据支撑（调了哪些工具、给出了什么数据、为什么这么判断）→ 最后给总结性结论和可行操作建议"，是总分总结构，而不是一大段分析让用户翻到最后找结论。
5. **Token 消耗**（客观指标）。
6. **响应速度**（客观指标）。

### 关键评价点

- 六个维度分层清晰（效果类 / 过程类 / 成本类），其中"一致性"和"工具调用有效率"是比较有思考深度的设计，建议面试时把这两点讲得更展开一些，它们最能体现"评测体系不是简单跑分"。
- 四个效果维度里，**完成率与一致性是"结果维度"，工具有效率与友好性是"过程维度"**，面试时可以用这句话做总起。

## 五、数据关联慢与 MCP / Skills 懒加载（约 12:51—15:18）

### 面试官问题

- "你做的那个平台需要关联很多外部数据对吧？速度上会不会有影响？"

### 候选人回答

- 一开始确实**很慢**，因为要关联很多平台，而取数方式都是通过 **MCP**：这些 MCP 由不同业务部门提供，跨部门的 MCP 稳定性较差、速率也慢。
- 在别的部门没有做优化、也没有更多支持的情况下，团队自己做的方案是：
  - **MCP 懒加载**：先给出一个 MCP 名单，让 Agent 自己判断如果需要某个 MCP，再把它加载进来；
  - **Skills 懒加载**：最终沉淀了**三百多个 Skills**，全量挂载体量太大，同样先给名称与简单描述，让 Agent 判断后再去调用。
- 这两项优化带来了比较明显的影响。后续各业务部门也逐渐把 MCP 换成 **CLI** 方式——CLI 对模型调用而言稳定性和成功率都高很多，MCP 这块因此有比较好的效果；但 Skills 那部分，候选人离职前团队还没有做出明显优化。

### 关键评价点

- "懒加载"其实是**工具/技能的选择性加载（动态工具下发）**，与"工具越多、幻觉越多"的经验一致，是很好的架构表达；如果能把懒加载前后的调用成功率或耗时用一个数字对比出来，回答会更强。
- 也可以补一句"判断依据"（由模型读名称与描述决定是否加载），说明这不是关键词匹配的土办法。

## 六、从评测结论到 System Prompt 优化（约 15:18—17:51）

### 面试官问题

面试官追问评测结论是如何产出的、优化具体做了什么。

### 候选人回答

- 优化动作有两个代表性方向：
  - **工具调用前不做预检查**：测试发现部分模型在每次工具调用前会先做一轮预检查、调用很多工具、消耗大量 Token；因此把提示词改成"直接执行、不要预先检查"，因为环境本身是受控的。
  - **工具调用失败最多重试三次**：有的模型在工具失败后会连续重试十几次，带来 Token 与时间的双重浪费；因此在 System Prompt 中限制重试次数并给出指令性约束。
- 验证路径：**实验平台验证 → 预发环境验证 → 线上**。线上有独立的数据统计。
- 线上效果：**输入 Token −18%、输出 Token −57%、冗余工具调用 −30%**，并且上线后做了一次调研，确认业务人员的使用体验没有受影响，因此认为优化有效。

### 关键评价点

- "先评测、再改 Prompt、再分级验证（实验 → 预发 → 线上）、最后回访体验"是完整的工程闭环，是本场最能体现个人工程素养的一段，建议固定成话术。
- 注意避免把"实验平台效果"和"线上效果"混说（见第一节评价点）。

## 七、评测中的人工环节与评分标准自学习（约 17:51—18:42）

### 面试官问题

面试官确认评测流程是否全自动。

### 候选人回答

- 中间有一段**人工**过程，主要针对评测框架的评分标准：评分使用 **LLM as Judge**（让大模型按不同任务类型的评分提示词打分）。
- 并不是每次打分都符合要求，因此对不满足要求的评分安排**人工打标**，再让评分提示词**自我迭代优化**，形成评分标准的持续优化过程。
- 除此之外的流程都是自动化的。

### 关键评价点

- 这里体现了"评测器本身也需要被评测"的意识，很加分；可以补一句"人工打标主要解决哪类偏差"（例如宽松/严苛偏差），回答会更硬。

## 八、云边异构调度项目追问（约 18:42—20:48）

### 面试官问题

- "这个网络实验是用探测的吗？主动探测还是被动采集？"
- "是相互之间探测吗？"
- "调度策略是针对什么不满？"

### 候选人回答

- 实验在实验室集群环境完成：**中心节点 15 个**（Linux 集群），**边缘节点使用 4 个树莓派**，构成云边异构环境。
- 网络拓扑组件是**主动探测**：每个节点上都部署一个网络拓扑组件，每隔一段时间自动探测各节点之间的网络时延，节点之间相互探测。
- 这些探测数据不是每次都使用，**只有在有对应调度需求时才使用**。
- 调度策略针对的是两类问题：一是**微服务网格之间的网络延迟要求**；二是**资源负载均衡**。K8s 默认调度器要么不做额外处理，要么只侧重镜像亲和性、资源负载均衡，**并没有涉及网络延迟**，因此团队设计并落地了针对微服访问网络时延的调度器。

### 关键评价点

- "主动探测 + 按需使用"的表述准确地划清了采集成本与调度决策之间的关系，比笼统说"构建了时延矩阵"更可信。
- 面试官连问两遍探测方式，说明他在意**数据来源的真实性**；建议主动交代探测频率与开销，避免被追着问。

## 九、两个核心指标是怎么衡量的（约 20:48—22:41）

### 面试官问题

"你这几个数字是怎么衡量的？"

### 候选人回答

- **集群负载均衡度 10.29%**：数据来源是 Prometheus，选取四类资源——**CPU、内存、网络、磁盘 IO**；每类资源都有固定的利用率或速率上限，对每个指标做**归一化**，再做**加权平均**，得出每个节点的负载均衡度评分；再对集群内所有节点的评分求平均，得到集群层面的负载均衡度。对比使用调度器前后的差异即 **10.29%**。
- **调度决策时延降低 25%**：调度器内置一个"记录节点"机制——如果容器此前在该节点上有过部署记录，就直接调度到该节点。实验时**手动构造资源负载不均衡场景**（一次投入二十几个到几十个 Pending Pod），统计使用与不使用该调度器时的调度完成时间，对比后得到约 **25%** 的降低。

### 关键评价点

- 两个指标都讲清了**数据来源 + 计算公式 + 对比实验设计**三要素，这是本场最扎实的一段，建议作为"指标可信度"的标准答法固化下来。
- 需注意口径统一：转写里说的是"时延降低 25%"，简历写的是"25.94%"；负载均衡度 10.29% 与简历一致。对外表述建议统一用简历版本。

## 十一、Service 负载均衡与 kube-proxy 实现模式（约 24:15—25:46）

### 面试官问题

- "你现在对外暴露服务一般怎么做？"
- "你知道 Service 现在的实现有几种模式吗？iptables 和 IPVS 的区别是什么？"

### 候选人回答

- 轻量应用直接用 K8s 原生的 **Service**（LoadBalancer 方式）暴露端口；较重一些的应用使用 **Ingress + Ingress Controller** 做负载均衡。
- 关于 Service 实现模式：候选人表示底层了解较少，当时集群用的是 **iptables** 模式，没有开启 IPVS 这种高性能模式。
- 补充信息：实验室集群一共 **15 个节点**；候选人表示没有权限登录这些系统环境。

### 关键评价点

- 这里是被问住的点。iptables 与 IPVS 的区别是 K8s SRE 的常考基础题，建议补齐：**iptables 模式基于 netfilter 规则链、规则随 Service 数量线性增长、大规模下同步开销大；IPVS 基于内核 LVS 哈希表，支持更多调度算法（rr/wrr/lc 等），在数千 Service 规模下转发性能和同步效率明显更好**。
- 被问住时不要只说"了解较少"，可以补一句"我知道它在高 Service 规模下的性能差异"，把话题拉回自己能掌控的范围。

## 十二、实习期故障处置流程复盘（约 25:46—31:45）

### 面试官问题

- "实习过程中有没有参与过实际故障处理？"
- "你指的集群 DNS 是 K8s 集群的 CoreDNS 还是办公网的 DNS？"
- "那你觉得整个故障最核心的点在哪里？"

### 候选人回答

- 候选人没有直接参与处置，但团队每次有故障都会带他参会，要求他**了解整个故障处理流程**，并思考 Agent 能在哪些环节介入。
- 印象最深的是 7 月的一次**办公网 DNS 故障**：
  - **现象**：访问应用时 DNS 解析变慢、页面一直转，随后完全无法访问。
  - **定位**：业务运维人员根据现象判断 DNS 环节异常，通过网络溯源、抓包定位到根因——**另一个部门正在对该 DNS 做压力测试**。
  - **处置**：与对方部门沟通停止演练；把能够切流的访问先切到另一个 DNS 集群，先恢复一部分，再逐步恢复；随后拉会评估故障影响范围（爆炸半径）与对各业务部门的影响程度；当晚做故障复演；最后完成全面总结并对受影响部门做相应处理。整个流程在 7 月底执行完毕。
- 对"最核心的点"的回答：根因在于**那个部门没有把控好演练/压测的影响范围**——不应该在白天做压测，也没有预先通知可能被影响的部门、组件与业务，属于流程问题；同时他认为当时的恢复方案缺少容灾设计，只能"能切流的先切流、不能切流的只能慢慢等"。

### 关键评价点

- 面试官随后说"我听下来是决策的问题——他们是在压测过程中才知道影响了这些应用和部门，才临时停的"，这与候选人的判断一致，说明这一段的诊断是对的。
- 建议把这次复盘抽象成一句可复用的话术：**"变更/演练流程缺少影响面评估与通知机制 + 缺少容灾切换预案"**，这比复述时间线更有价值。
- 如果被追问"Agent 能在这个流程里做什么"，可以答：**影响面预评估（变更前查依赖与受影响对象）、压测期间的异常发现、切换预案的执行编排**——这三点正好对应你们 Agent 平台的能力。

## 十三、实习中的阻力与跨部门协作（约 31:45—35:42）

### 面试官问题

- "有什么让你觉得困难的场景？"
- "跨部门协作、需求推不动的时候你怎么处理？"

### 候选人回答

- 小场景：实习初期**权限很小**，创建应用、申请平台都要走审批，有些应用或平台完全无法访问，只能借同事权限创建好之后给自己用；不过提出申请后审批与推进速度都比较快。
- 较大的场景：构建出评测平台后发现 SRE Agent 存在**Token 消耗高、冗余工具调用多**的问题，候选人给出优化结论后，团队在会议上讨论，最终决定"先在预发集群试一下"。候选人自述第一次实习比较谨慎（原话"唯唯诺诺"），先预发验证、有效果后再逐步上线，上线前会提前通知，上线后还会做调研。
- 阻力整体不大，"大家不会反对，但各自比较忙，有时候需要催一下"。
- 催办方式：内部使用**客户端**（原为钉钉，已脱敏），先在群里说明"这次优化/改动要上线了"，征求是否有意见或需要预先防范的地方；需要单独催的，把**需求内容 + 为什么这么做**整理清楚发给对应处理人、审批人或业务同事，看到对方已读就先不打扰，次日日会上问进度；如果对方给出的预期完成时间没兑现，再线下沟通卡点与解决方案；线下沟通之前，先和自己的主管讨论这个问题的影响范围与紧急程度。

### 关键评价点

- 这一段的最大亮点是"**先说明背景与原因、再看已读、再到日会跟踪、最后线下沟通并提前对齐主管**"的推进节奏，非常像成熟工程师的做法，建议保留为固定话术。
- "唯唯诺诺"这类自贬表述建议去掉，改为"第一次实习，我倾向先把效果在预发环境验证清楚再推动上线"，同样的意思但更专业。

## 十四、面试官介绍百度这边的工作与业务（约 35:42—38:12）

### 面试官提问与介绍

面试官介绍了百度这边 AI 与运维结合的现状，并确认候选人理解是否到位。

### 对话要点

- 百度这边同样在做 AI SRE，用 Agent 处理运维工作：把以前的数据预置、各种接口与平台通过 API / MCP 方式统一化结合，让 AI 分析并给出结论；给出结论后还会推荐**预案**——低危操作直接推荐预案、可点击执行，高危操作需要加审批，中低危直接执行。
- 除预案外，还有**巡检**类工作（涉及所有容器、中间件、容量是否异常等），以及**故障处置**的完整流程，目标是把日常工作流化。
- 目前仍由人来做这些工作，团队要做的是把平台能力对外提供出来，方便调用。
- 面试官确认 Agent 已能执行高危与非高危操作，候选人回应"现在已经做到第四步了"。

### 关键评价点

- 这一段是**反向信息收集**的好机会：可以顺着"预案 + 审批分级"追问一句"高危预案的审批是人工点还是流程审批、审批粒度是单条命令还是整个预案"，既显得懂行，也能拿到团队真实的技术细节。

## 十五、候选人反问与行业讨论（约 38:12—45:50）

### 对话要点

- 候选人提问：Agent 在实际运维中会不会越来越有效果？
  - 面试官：以前是"一个大脑 + 聊天式输入"，现在 Agent 已经能直接写代码、执行；Agent 承担的比例会越来越高。
- 关于"Agent 是否会替代传统 SRE 人员"，候选人给出的回答：
  - 运维真正有价值的地方在于**运维经验与流程处理能力**；让 Agent 去做死板的流程化事情没有问题，随着模型智能化程度提高，它能做的 SRE 工作会越来越多；
  - 但**经验沉淀**这件事仍然需要从人身上抽取，SRE 的创新性工作也需要人机结合、由人和 Agent 一同推进；
  - 即使未来 Agent 完全替代传统 SRE，**运维 Agent 本身也需要有自进化、迭代与管控的岗位**。
- 关于"阻碍 AI SRE Agent 发展最核心的点"：
  - 候选人：模型还没有聪明到能执行那么多角色与操作；可落地场景偏少、还需要不断扩充；"很多场景还是无法触及，还差最后一公里"。
  - 面试官补充：模型能力其实不是最重要的卡点；**卡点在上下文获取**——拿不到足够的环境信息、缺少可运行的环境把各处断点连通起来；现在做了很多工作都是"一段一段的"，没有真正连通整合，很重要的一个卡点就在环境上。
- 面试官还追问过一个候选人未实际接触过的技术，候选人如实回答"没太用过"。
- 最后一道问题（问题原话未被完整采集）：候选人回答的思路是——针对过往故障与问题的流程处理，流程中会根据实际情况做不同分支选择，类似于**在流程编排中插入 Agent 决策节点**；这种方式适合放在决策节点上，因为此时模型**输出小、占用上下文少、能理解的信息更多，在决策上比人更快更准**。

### 关键评价点

- "经验沉淀必须从人身上抽取"+"Agent 本身也需要管控与迭代岗位"是一个有深度的收尾；而面试官强调的"卡点在上下文与环境连通"值得记下来——这与你们实习中做的 MCP/CLI 统一、懒加载其实是同一个问题的不同侧面，下次可以主动把这个关联说出来。
- 最后那道题的答题方向（**Agent 只放在决策节点、而非全流程自动化**）与"sandbox + 高可用 + 权限边界"的思路一脉相承，是本场很亮的一个回答。
