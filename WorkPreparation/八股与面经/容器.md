# Dockers、Containerd与虚拟机的区别与优劣势？

最根本的区别在于**虚拟化的层级**。

## 1. 虚拟机 (VM)

虚拟机是通过 **Hypervisor**（如 KVM, VMware）在物理硬件上模拟出完整的硬件环境。

- **内核：** 每个 VM 都有自己独立的 **Guest OS（客户操作系统内核）**。
- **隔离性：** 强隔离。即便一个 VM 崩溃或被攻破，也不会直接威胁到宿主机或其他 VM。
- **开销：** 沉重。启动需要数分钟，占用 GB 级的磁盘和内存空间。

## 2. 容器 (Containers)

容器是宿主机操作系统上的一个**特殊进程**，通过 Linux 内核的 `Namespace`（空间隔离）和 `Cgroups`（资源限制）实现。

- **内核：** 所有容器**共用宿主机的内核**。
- **隔离性：** 弱隔离。虽然进程间看不见，但逻辑上仍在同一个内核运行。
- **开销：** 极轻。秒级启动，占用 MB 级空间，几乎没有性能损耗。

> - **Docker：** 是一个完整的软件产品线（包括镜像构建、API、命令行工具、网络、卷管理等）。它像是一个**精装修的样板房**，进去就能住。
> - **Containerd：** 是从 Docker 中剥离出来的**底层容器运行时**。它只负责容器的生命周期管理（拉取镜像、启动/停止容器）。它更像是一块**地基**。
>
> **现状：** 在 Kubernetes (K8s) 环境中，为了提高效率，现在大多跳过 Docker 直接调用 Containerd。

| **维度**       | **虚拟机 (VM)**                         | **Docker / Containerd**                     |
| -------------- | --------------------------------------- | ------------------------------------------- |
| **隔离性**     | **极高**（硬件级隔离，更安全）          | **中等**（内核级隔离，共用内核）            |
| **启动速度**   | 分钟级                                  | 秒级                                        |
| **资源利用率** | 低（由于 Guest OS 的冗余）              | **极高**（几乎等同于原生进程）              |
| **系统支持**   | 可以运行不同内核（如 Linux 宿主跑 Win） | **必须相同内核**（Linux 只能跑 Linux 容器） |
| **移植性**     | 较差（镜像体积大，受硬件模拟限制）      | **极佳**（Build once, run anywhere）        |

**选虚拟机 (VM) 的场景：**

- 需要运行不同操作系统的任务（如在 Linux 服务器上跑 Windows 应用）。
- 多租户云环境，对**安全性**要求极高，防止“容器逃逸”。
- 需要对硬件进行深度模拟或直接分配。

**选 Docker / Containerd 的场景：**

- **微服务架构**：需要快速扩缩容。
- **CI/CD 流水线**：频繁的构建、测试和发布。
- **高密度部署**：在有限的硬件上运行成百上千个应用。

# Dockers、Containerd使用Cgroup、Namespace的方式？

## 1. Namespace：解决“你在哪”的问题（环境隔离）

Namespace（命名空间）负责把全局的系统资源划分成一个个独立的“小房间”。

- **PID Namespace：** 容器里的进程以为自己是 1 号进程（PID 1），但实际上在宿主机上它可能只是 PID 9527。
- **Net Namespace：** 给容器分配独立的虚拟网卡、IP 地址和路由表。
- **Mount Namespace：** 让容器拥有独立的根文件系统（RootFS），看不到宿主机的磁盘目录。
- **UTS Namespace：** 让容器有独立的主机名（Hostname）。
- **IPC / User Namespace：** 隔离进程间通信资源和用户 ID/组 ID。

**操作流程：** 当 Containerd 启动一个容器时，它会调用内核的 `clone()` 或 `unshare()` 系统调用，并带上相关的标志位（如 `CLONE_NEWPID`）。内核收到指令后，会为该进程创建一个新的视图，使其只能看到自己 Namespace 里的资源。

> * Docker/Containerd 是如何利用它实现隔离的？
>
>   当你想启动一个容器时，Containerd 实际上执行了以下“三板斧”：
>
>   1. 创建（Clone/Unshare）
>
>      Containerd 调用 `clone()` 系统调用创建新进程。这时会传入一系列标志位，告诉内核：“给这个新进程分配一套全新的 Namespace ID，不要用父进程的。”
>
>      内核会为这个新进程生成一组全新的 ID。
>
>   2. 挂载（Pivot_root）
>
>      虽然有了 PID 和网络隔离，但容器进程默认还是能看到宿主机的根目录。
>
>      Containerd 会利用 **Mount Namespace**，配合 `pivot_root` 命令，把容器镜像的内容（RootFS）挂载为该进程的根目录 `/`。
>
>      从此，该进程执行 `ls /` 时，看到的只是镜像里的文件，宿主机的 `/etc/shadow` 等敏感文件被挡在了“视距”之外。
>
>   3. 限制与收尾
>
>      将该进程的 PID 写入对应的 **Cgroups** 配置文件以限制资源
>
>      关闭不必要的文件描述符。
>
> * Namespace 文件的“玄机”：为什么容器关了，网络还在？
>
>   你可能会问：如果容器进程退出了，这些 Namespace 文件（ID）会自动消失吗？
>
>   - **默认情况：** 是的，引用计数归零，内核销毁该 Namespace。
>   - **持久化技巧：** 有时候我们需要在没有容器进程的情况下保留网络（比如 K8s 的 Pause 容器）。
>   - **做法：** 我们可以把 `/proc/[pid]/ns/net` 这个文件 **“挂载（bind mount）”** 到宿主机的另一个地方。只要这个挂载点存在，这个 Namespace ID 就会一直保留。这就是为什么有些网络插件能预先创建好网络环境，等容器启动后再塞进去。

## 2. Cgroups：解决“你能用多少”的问题（资源限制）

Cgroups（Control Groups）负责给进程带上“紧箍咒”，防止某个容器耗尽宿主机的所有资源。

- **CPU 子系统：** 限制容器的 CPU 使用率（例如只允许使用 0.5 核）。
- **Memory 子系统：** 限制容器的内存上限（超过后会触发 OOM Kill）。
- **Blkio 子系统：** 限制磁盘读写的吞吐量（IOPS）。
- **Devices 子系统：** 控制容器能访问哪些硬件设备（如 GPU）。

**操作流程：**

1. Linux 内核将 Cgroups 暴露为一个虚拟文件系统（通常挂载在 `/sys/fs/cgroup/`）。
2. Docker/Containerd 会在目录下创建一个子目录（例如 `/sys/fs/cgroup/cpu/docker/<container_id>`）。
3. 将容器进程的 PID 写入该目录下的 `tasks` 文件。
4. 将限制值（如 `cpu.shares`）写入对应的配置文件。内核随后就会根据这些文件实时管控该 PID 的资源消耗。

# 容器是如何实现的？

要透彻理解容器的实现，首先要打破一个误区：**容器不是一个实体的“盒子”，而是一组被限制了权限和资源的“特殊进程”。**

在 Linux 底层，容器的实现依赖于三大核心技术：**Namespace（空间隔离）**、**Cgroups（资源限制）** 和 **UnionFS（联合文件系统）**。我们可以把这三者形象地比喻为：**障眼法、紧箍咒和幻术文件夹。**

------

## 1. Namespace：障眼法（隔离视角）

**Namespace** 是 Linux 内核用来隔离系统资源的方式。它让容器进程产生一种“我正独占整台机器”的错觉。

- **PID Namespace**：让容器拥有独立的进程树。容器内的第一个进程 PID 为 1，它看不到宿主机的其他进程。
- **Net Namespace**：让容器拥有独立的网卡、IP 地址和路由表。
- **Mount Namespace**：让容器拥有独立的挂载点，使其文件系统与宿主机隔离。
- **UTS Namespace**：让容器拥有独立的主机名（Hostname）。

## 2. Cgroups：紧箍咒（配额控制）

如果 Namespace 只是让进程“看不见”外部，那么 **Cgroups (Control Groups)** 则是限制进程“不能乱动”外部资源。

- **作用**：防止某个容器进程因为代码 Bug 或恶意攻击，耗尽宿主机的 CPU、内存或带宽。
- **实现**：内核在 `/sys/fs/cgroup` 目录下维护一组文件。当你限制一个容器只能用 512MB 内存时，Docker 会把该容器的进程 PID 写入对应的 `memory.limit_in_bytes` 文件中，内核就会据此强制执行限额。

## 3. UnionFS：幻术文件夹（分层镜像）

容器之所以能实现“秒级启动”，关键在于它的镜像存储方案——**UnionFS（联合文件系统，如 Overlay2）**。

- **分层结构**：容器镜像是由多个“只读层”叠加而成的。底层是基础操作系统（如 Ubuntu），上层是你的应用（如 Nginx）。
- **Copy-on-Write (写时复制)**：
  - 所有的镜像层都是**只读**的。
  - 当你启动容器时，系统会在最顶层加一个薄薄的**可读写层**。
  - 如果你修改了文件，系统会先把只读层的文件拷贝到可写层再修改。
- **优势**：多个容器可以共享同一个底层的只读镜像层，极大地节省了磁盘空间。

## 4. 容器运行时的协调者：Containerd 与 runc

当你输入 `docker run` 时，背后发生了一场接力赛：

1. **Docker/Containerd**：作为“大管家”，负责拉取镜像、准备根文件系统（RootFS）。
2. **runc**：作为“执行者”，是一个轻量级的命令行工具。它调用内核的 `clone()` 或 `unshare()` 系统调用来创建 Namespace，并配置 Cgroups。
3. **结果**：进程启动，被关进了由 Namespace 和 Cgroups 编织的“牢笼”里，容器诞生了。

# 一个容器就是一个进程，这么说有问题吗？

准确的表述应该是：**一个容器的本质是一个（或一组）受约束的进程及其运行环境。**

## 1. 为什么说“一个容器就是一个进程”？（宏观角度）

当你运行 `docker run nginx` 时，宿主机操作系统内核确实只是启动了一个新的进程。

- **生命周期绑定：** 容器的生命周期与它内部的 **PID 1 进程**（主进程）紧紧绑定。如果这个主进程结束了，容器也就自动停止（Exited）。
- **资源实体：** 在宿主机上执行 `ps -ef`，你可以直接看到容器里的 Nginx 进程。对内核来说，它就是一个分配了资源、由调度器管理的普通进程，只是它被戴上了 Namespace 和 Cgroups 的“枷锁”。

## 2. 为什么这种说法“有问题”？（微观角度）

容器并不总是“一个”进程，它通常包含以下结构：

### A. 进程组（Process Group）

一个容器里可以运行多个进程。例如，你在 Nginx 容器里执行 `docker exec -it <id> sh`，这时容器内就有了两个进程：Nginx 和 Shell。它们共享同一套 Namespace 和 Cgroups。

### B. 容器运行时（Runtime Artifacts）

除了业务进程本身，容器还包含了一些**非进程的静态实体**：

- **RootFS（根文件系统）：** 镜像解压后的目录，为进程提供所需的库文件、配置和二进制程序。
- **隔离环境（Namespace 句柄）：** 即使进程退出了，如果 Namespace 被挂载保留（如 K8s 的某些场景），这个“环境”依然存在。

## 3. 容器与普通进程的“分水岭”

如果说容器只是进程，那它和你在命令行跑一个 `./my-app` 有什么区别？区别在于**“进程的视图”**。

- **普通进程：** 看到的是宿主机的全部。它能看到所有的网卡、所有的文件、所有的其他进程。
- **容器进程：** 被 **Namespace** 剥夺了全局视野。它以为自己运行在独立的机器上，有自己的 IP、独立的文件根目录和独有的 PID 树。

## 4. 架构上的“守护进程”：containerd-shim

在实际运行中，每一个容器进程旁边其实都有一个“小跟班”：**containerd-shim**。

- 它是一个非常轻量的进程，作用是作为容器内进程的父进程。
- **意义：** 这样即使 Docker 守护进程（Daemon）重启了，容器进程也不会因为失去父进程而被内核回收，保证了容器的稳定性。

# 容器和镜像的区别在于？

简单来说，容器与镜像的关系就像是**“程序”与“进程”**，或者**“图纸”与“建筑”**。

在 Docker 的世界里，镜像（Image）是**静态的只读模板**，而容器（Container）是**动态的运行实例**。

| **维度**   | **镜像 (Image)**               | **容器 (Container)**                 |
| ---------- | ------------------------------ | ------------------------------------ |
| **状态**   | 静态、保存在磁盘上的文件       | 动态、运行在内存中的进程             |
| **可写性** | **完全只读**                   | **可读可写**（带有一个临时的可写层） |
| **内容**   | 操作系统、依赖库、应用程序代码 | 运行中的程序、环境变量、用户数据     |
| **类比**   | 游戏安装包 / 菜谱              | 运行中的游戏 / 正在炒的那盘菜        |

* 存储结构：联合文件系统 (UnionFS)

  这是理解两者区别的技术核心。容器实际上是在镜像的基础上，“套”了一层可以修改的皮。

  1. 镜像：多层只读 (Read-Only Layers)

     当你构建镜像时，每一条指令（如 `INSTALL`）都会生成一个**只读层**。这些层是固化在磁盘上的，多个容器可以共享同一个镜像的这些只读层，这也是容器节省空间的原因。

  2. 容器：可写层 (Writable Layer / Container Layer)

     当你启动容器时，容器运行时会在镜像的最顶层挂载一个薄薄的**可写层**。

     - **写时复制 (CoW)**：如果你在容器里修改了一个镜像里的文件，系统会先把文件从只读层拷贝到可写层，然后在可写层进行修改。
     - **短暂性**：一旦容器被删除，这个可写层也会随之消失。镜像本身毫发无损。
