# 如果网络发生丢包的情况，你会如何检查故障来源？
# 详细说明一下访问一个网站时，操作系统和网络底层都会有哪些操作？（从DNS解析到不同网络层之间的数据是如何传输的）
这是一个极为经典且宏大的问题。要把访问网站的过程讲透，我们需要跨透**用户空间（应用程序）**、**内核空间（操作系统网络协议栈）**以及**物理硬件（网卡与线缆）**这三个维度的壁垒。

既然你希望了解到底层操作，我们跳过浏览器渲染的细节，直接聚焦于**操作系统机制**和**网络协议的数据流转**。

整个过程可以划分为以下几个核心阶段：

### 第一阶段：应用层准备与 DNS 解析 (User Space -> Kernel Space)

当你在浏览器中输入 `https://www.example.com` 并按下回车时，一切从用户空间的应用程序开始。

**1. URL 解析与 Socket 创建**

- 浏览器首先解析 URL，提取出协议（HTTPS）、域名（[www.example.com](https://www.example.com/)）和默认端口（443）。
    
- 浏览器调用操作系统的 Socket API（如 `socket()` 系统调用），请求内核分配一个套接字描述符（File Descriptor）。此时，操作系统会为这个连接在内核态分配内存结构。
    

**2. DNS 解析 (将域名翻译为 IP)**

网络层只认 IP 地址，所以浏览器必须先进行 DNS 查询：

- **本地缓存检查：** 浏览器缓存 -> 操作系统 DNS 缓存 -> 本地 `hosts` 文件。
    
- **发起系统调用：** 如果都没命中，浏览器会调用 OS 的 `getaddrinfo()` 等函数，将解析任务交给操作系统的 DNS 解析器（Resolver）。
    
- **UDP 报文发送：** 操作系统构造一个 DNS 查询报文，目标地址是网卡配置的本地 DNS 服务器（如 114.114.114.114 或 8.8.8.8），目标端口是 UDP 53。
    
- **递归与迭代查询：** 本地 DNS 服务器如果没有缓存，会依次向根域名服务器、顶级域名服务器（TLD）、权威域名服务器发起查询，最终拿到 `www.example.com` 的真实 IP 地址并返回给你的操作系统。
    

---

### 第二阶段：传输层与网络层的封装 (Kernel Space)

拿到目标 IP 后，操作系统内核的网络协议栈（如 Linux 的 Netfilter/TCP/IP 栈）开始接管数据的封装工作。在 Linux 中，数据包在内核中通常以 `sk_buff`（Socket Buffer）的数据结构存在并流转。

**1. 传输层 (TCP) - 建立连接与分段**

- **三次握手：** 因为是 HTTPS（基于 TCP），OS 必须先建立 TCP 连接。内核会分配一个本地的临时端口（如 54321），向目标 IP 的 443 端口发送一个 `SYN` 报文。经历 `SYN -> SYN+ACK -> ACK` 后，TCP 连接在内核层面建立。
    
- **数据封装：** 浏览器将加密后的 HTTP 请求数据写入 Socket，内核将其复制到 TCP 发送缓冲区。如果数据过大，TCP 会根据 MSS（最大报文段长度）将其切片。
    
- **加 TCP 头：** 内核为每个切片添加 TCP 头部，包含源端口、目的端口、序列号、确认号等。
    

**2. 网络层 (IP) - 路由与寻址**

- **路由决策：** 内核查询操作系统的路由表（`ip route`）。它将目标 IP 与本地子网掩码进行按位与运算，判断目标 IP 是在局域网内，还是需要走默认网关（路由器）。通常访问外网都是走默认网关。
    
- **加 IP 头：** 内核在 TCP 报文外层加上 IP 头部，包含源 IP（本机 IP）、目的 IP（目标服务器 IP）、TTL（生存时间）等。
    

---

### 第三阶段：数据链路层与硬件发送 (Kernel Space -> Hardware)

数据包（Packet）现在已经完全成型，但它还需要被转换为电信号或光信号才能离开机器。

**1. ARP 解析 (获取下一跳的 MAC 地址)**

- IP 头部虽然有目标 IP，但在物理网络（以太网）中传输，网卡只认 MAC 地址。
    
- 操作系统需要知道**默认网关（路由器）**的 MAC 地址。它会先查本地的 ARP 缓存表（`arp -a`）。
    
- 如果没有，内核会构造一个 ARP 广播报文：“谁是 [网关 IP]？请把你的 MAC 地址告诉我。”网关收到后单播回复其 MAC 地址。
    

**2. 数据链路层 (MAC) - 帧封装**

- 内核在 IP 数据包外部加上以太网帧（Frame）头部，包含源 MAC 地址（本机网卡）、目的 MAC 地址（网关网卡），以及帧尾的 FCS（循环冗余校验码）。
    

**3. 操作系统与网卡驱动的交互 (核心底层操作)**

- **Ring Buffer：** 封装好的以太网帧被放入系统内存中的一个环形缓冲区（Tx Ring Buffer）。
    
- **通知网卡：** 操作系统通过写网卡的硬件寄存器，通知网卡（NIC）：“有新数据准备好了”。
    
- **DMA 拷贝：** 网卡利用 DMA（直接内存访问）技术，不需要 CPU 介入，直接将主存中 Ring Buffer 里的数据帧拷贝到网卡的内部缓存中。
    
- **电/光信号转换：** 网卡的 PHY 芯片将数字信号转换成物理线缆上的高低电平（双绞线）或光脉冲（光纤），发送出去。
    

---

### 第四阶段：网络流转与目标端接收

**1. 路由器的接力**

- 数据帧到达你家里的路由器。路由器网卡接收信号，通过硬件中断通知路由器内核。
    
- 路由器剥离 MAC 头部，查看 IP 头部，发现目的 IP 不是自己。
    
- 路由器查自己的路由表（通常是利用 BGP/OSPF 等协议学习到的），决定下一跳去哪里。
    
- 路由器重新封装新的源 MAC 和目的 MAC，将 TTL 减 1，发往下一个节点。这个过程可能跨越十几台运营商的路由器，直到抵达目标服务器所在的数据中心。
    

**2. 目标服务器接收 (自下而上解析)**

- **硬件中断与 NAPI：** 目标服务器的网卡收到光/电信号，存入自身缓存，通过 DMA 写入服务器内存的 Rx Ring Buffer。随后，网卡向 CPU 发起**硬中断**。为了避免高并发下中断风暴，现代 Linux 会触发**软中断（NET_RX_SOFTIRQ）**，让内核线程以轮询的方式批量从 Ring Buffer 读取数据（NAPI 机制）。
    
- **逐层解包：** 内核网络栈将数据结构从以太网帧剥离（去 MAC 头），交给网络层处理（去 IP 头），再交给传输层处理（去 TCP 头，并通过序列号重组乱序的包）。
    
- **应用层读取：** 最终，目标服务器内核将完整的 HTTP 请求数据放入目标进程（如 Nginx 或 Node.js）绑定的 Socket 接收缓冲区，唤醒应用程序去处理。

   不同数据交换的方式和特点

   1. 电路交换：**有建立链接，拆除链接的过程，发送方和接收方之间建立一条 物理链路，一旦链路建成被使用者单独使用，适合长时间连续数据传输。**

   2. 报文交换：不要求在两个通信节点之间建立连接，**发送的信息被组织成报文，在网络中经过多次存储转发到达目的结点，没有建链拆链的时间，但是有通信中的转发延迟，而且对转发结点的存储空间要求较高**

   3. 分组交换：**数据报有固定的长度，交换结点只要在内存中开辟相对较小的缓冲区即可。**分组交换又分为数据报和虚电路。

      数据报类似于报文交换，**每个分组携带完整地址信息，每个分组都要进行路由，不同分组经过的路径可能不同，道道目的地的顺序可能与发送顺序不同，目标主机对分组重排序。**

      虚电路类似电路交换**，有建链和拆链过程，要求在发送端和接收端之间建立一条逻辑链接，各分组沿同一通路传输**

     > 本题：
     >
     > 在幅移键控（ASK）中，信号的速率（也称为波特率）是指每秒传输的信号元素的数量。**ASK所需的带宽通常是信号速率的两倍，即最大带宽是 ( 2S )**。这是因为在ASK中，一个信号元素可以包含一个比特的信息，而要准确地传输这些信号元素，就需要足够的频率范围来避免信号之间的干扰。
     >
     > [简单来说，如果你有一个每秒传输 ( S ) 个信号元素的系统，那么理论上你需要最多 ( 2S ) 的带宽来确保这些信号元素不会相互干扰。这个带宽的计算基于最理想的情况，实际应用中可能需要更多的带宽来补偿信号失真、噪声等因素](https://www.rfwireless-world.com/Terminology/ASK-vs-FSK-vs-PSK.html)。
     >
     > 同理，对于FSK、PSK：
     >
     > 对于频移键控（FSK）和相移键控（PSK），带宽需求与ASK有所不同。
     >
     > [**FSK**的带宽需求是 ( 2Rb + (f1-f2) )，其中 ( Rb ) 是比特率，( f1 ) 和 ( f2 ) 是代表二进制1和0的两个不同频率](https://www.rfwireless-world.com/Terminology/ASK-vs-FSK-vs-PSK.html)。FSK通常需要比ASK更宽的带宽，因为它涉及到传输两个不同的频率。
     >
     > [**PSK**的带宽需求则取决于符号编码和脉冲形状，因为这两者共同决定了功率谱密度（PSD）。对于PSK和矩形脉冲（无滤波器应用），PSD将呈现 ( \text{sinc}^2 ) 形状，这看起来像是一系列不同振幅的“山丘”或“瓣叶”](https://www.rfwireless-world.com/Terminology/ASK-vs-FSK-vs-PSK.html)。PSK通常比FSK更有效地使用带宽，因为它可以在相同的频率下传输两个不同的相位。
     >
     > [总的来说，FSK和PSK的带宽需求与ASK不同，它们各自有不同的优势和适用场景。FSK在抗噪声方面表现更好，但需要更宽的带宽。而PSK在带宽和功率消耗方面更为高效，但对噪声和干扰更敏感，且需要更复杂的调制和解调技术](https://medium.com/@divyanshu.chore/fsk-vs-psk-a-comparison-of-digital-modulation-techniques-74f94caf731d)。

   * T1载波使用了TDM多路复用技术，其24路语音信道的总数据速率是：**1.544M**
   
     > T1载波系统利用时分多路复用（TDM）技术，**将24个独立的语音信道整合到一个单一的数字信号中。每个语音信道都以64kbps的速率传输数据，这是因为每个信道都是通过8000次/秒的采样率来编码的，每个采样被编码成8位的数字（即1字节）**。
     >
     > 为了同步和控制信号的传输，除了这24个信道外，还需要额外的比特来进行帧同步。具体来说，每个TDM帧包含了24个8位的语音数据加上一个用于帧同步的额外比特。由于帧率是8000帧/秒，所以总的数据速率就是 ( 1.544Mbps )，这样计算如下：
     >
     > $8000 \text{ frames/sec} \times (24 \text{ channels/frame} \times 8 \text{ bits/channel} + 1 \text{ framing bit/frame}) = 1,544,000 \text{ bits/sec} $
     >
     > [因此，T1载波的总数据速率是1.544Mbps，这包括了24个语音信道的数据以及额外的控制和同步信号](https://inetdaemon.com/tutorials/telecom/t-carrier/T1/)[1](https://inetdaemon.com/tutorials/telecom/t-carrier/T1/)[2](https://www.technologyuk.net/telecommunications/communication-technologies/plesiochronous-digital-hierarchy.shtml)[3](https://www.dialogic.com/~/media/products/docs/appnotes/11171-t1-intro-plan-config-an.pdf)[4](http://pld.cs.luc.edu/telecom/mnotes/tcarrier_sonet.html)。

     * 量化：是对采样点的值进行分级量化，尽量增大量化等级，提高量化精度；量化尽量采用2的次幂级，便于编码

   > [标准以太网使用的是**1-持续的CSMA/CD**](https://geek-docs.com/network/network-ask-answer/the-difference-between-1-persistent-p-persistent-and-non-persistent-csma.html)。这种方法在信道空闲时能够快速发送数据，适用于以太网这种低延迟和高带宽的环境。非持续的CSMA/CD则更适用于负载较轻和传输延迟较高的网络环境。
   >
   > * 1持续的CSMA/CD：
   >   - **当信道空闲时，节点会立即发送数据。**
   >   - **如果信道忙碌，节点会持续监听直到信道变为空闲。**
   >   - 这种方法可能会导致较多的碰撞，因为多个节点可能同时发现信道空闲并尝试发送数据。
   > * 非持续的CSMA/CD：
   >   - 当信道空闲时，节点也会发送数据，**但如果信道忙碌，它不会持续监听。**
   >   - 相反，节点会等待一个随机的时间间隔后再次检查信道是否空闲。
   >   - 这种方法减少了碰撞的可能性，但可能会降低网络的效率。
   > * 注意，之前学过的1坚持CSMA、非坚持CSMA、p坚持CSMA都是CSMA这个方法的一种策略，后面的CSMA/CD、CSMA/CA都是CSMA的子方案。

   > X.25是一种早期的网络协议标准，由国际电信联盟（ITU-T）提出，主要用于在公共数据网络上实现分组交换通信。它定义了数据终端设备（DTE）和数据电路终结设备（DCE）之间的接口，包括物理层、数据链路层和网络层的标准
   >
   > X.25协议的体系结构分为三层：
   >
   > 1. **物理层**：规定了DTE和DCE之间的物理连接标准。物理层协议为X.21、X.21bis、V系列
   > 2. **数据链路层**：使用高级数据链路控制（HDLC）的子集，即链路访问程序平衡（LAPB）协议，确保数据可靠传输。

   >
   > X.25协议适用于误码率较高的通信环境，提供了可靠的数据传输服务，但由于其较高的时延和协议复杂性，随着技术的发展，已逐渐被更现代的网络协议所取代。它在20世纪70年代至90年代被广泛使用，尤其是在构建早期的广域网（WAN）中发挥了重要作用。如今，尽管X.25协议不再是主流，但它在网络通信历史中仍占有一席之地。

   * 死锁主要有：**直接死锁和重装死锁**
   
     > 计算机网络中的死锁：
     >
     > [计算机网络中的死锁是指网络中的一组设备或节点由于资源竞争和相互依赖导致的一种僵局状态。在这种状态下，每个设备或节点都在等待其他设备或节点释放资源，但没有一个设备或节点愿意首先放弃自己占有的资源，从而导致整个系统无法继续进行任何进一步的操作](https://bing.com/search?q=计算机网络中的死锁是什么？)。
     >
     > 在计算机网络中，直接死锁和重装死锁是两种不同的死锁情况。
     >
     > [**直接死锁**通常发生在两个节点之间，当两个节点尝试相互发送数据时，但每个节点都没有足够的缓冲区来接收对方的数据。这种情况下，每个节点都在等待对方先释放资源，从而导致了死锁](https://blog.csdn.net/weixin_55323026/article/details/117755730)[1](https://blog.csdn.net/weixin_55323026/article/details/117755730)。
     >
     > [**重装死锁**可能发生在一组节点之间，例如，节点A想要向节点B发送数据，节点B想要向节点C发送数据，而节点C又想要向节点A发送数据。如果此时每个节点都没有空闲的缓冲区来接收新的数据，那么这些节点就会陷入一个循环等待的状态，这种情况被称为重装死锁](https://blog.csdn.net/weixin_55323026/article/details/117755730)[1](https://blog.csdn.net/weixin_55323026/article/details/117755730)。
     >
     > 这两种死锁都是由于资源分配不当和通信协议设计不足导致的，解决这些问题通常需要改进网络协议和资源管理策略。在设计网络系统时，应该考虑这些潜在的死锁情况，并采取措施预防它们的发生。例如，可以通过设置适当的缓冲区大小、使用死锁预防算法或者引入超时机制来避免死锁的发生。

* CRC-8的错位检测：

  - **所有单比特错误**：CRC-8可以检测出所有单比特错误，因为任何单一比特的变化都会导致计算出的CRC值发生变化。

  - **所有奇数比特错误**：如果CRC多项式包含偶数个项（即二进制表示中有偶数个1），则可以检测出所有奇数比特的错误。

  - **长度为8比特的突发错误**：CRC-8可以检测出长度不超过8比特的突发错误。

  - **长度超过8比特的突发错误**：CRC-8可以以一定的概率检测出长度超过8比特的突发错误，但这个概率会随着错误长度的增加而减小。

    对于超出8比特的错误，CRC-8的检测概率计算相对复杂，因为它涉及到多项式的特性和数据的特定模式。通常，CRC的检测概率可以通过分析多项式的汉明距离（Hamming Distance）来估计。汉明距离是指至少需要改变多少个比特才能使得两个有效的数据块有相同的CRC值。

    对于超过8比特的错误，CRC-8的检测概率通常是 $ (2^{n-1} - 1) / 2^n $，其中 ( n ) 是CRC的位数。这意味着对于CRC-8，错误检测的概率大约是 $ (2^7 - 1) / 2^8 = 127/256 $ 或大约为49.61%。这个概率表示对于任意超过8比特的错误，CRC-8有大约49.61%的概率能够检测到错误。

  - 对于偶数比特错误:

    CRC（循环冗余校验）通过使用特定的多项式来生成一个校验值，这个校验值是数据的一个短的“余数”。如果数据在传输或存储过程中发生变化，接收方重新计算的CRC值将与发送方的CRC值不匹配，从而检测到错误。

    [对于偶数比特错误的检测，CRC的能力取决于所使用的多项式。如果多项式包含偶数个项（即二进制表示中有偶数个1），CRC可以检测出所有奇数比特错误，因为任何奇数比特的变化都会导致CRC值的变化。然而，当总数为偶数的比特错误发生时，这些错误可能会相互抵消，导致CRC值不变，从而无法被检测出](https://www.csus.edu/indiv/p/pangj/166/f/d8/Handout_CRC Error Detection.pdf)[1](https://www.csus.edu/indiv/p/pangj/166/f/d8/Handout_CRC Error Detection.pdf)。

    因此，虽然CRC非常擅长检测单个错误和突发错误，但它并不总是能够检测出所有偶数比特错误。这是CRC的一个已知限制，设计CRC系统时需要考虑这一点。为了提高错误检测的能力，通常会选择一个能够提供所需错误检测特性的多项式，并且可能会结合其他错误检测机制来弥补CRC的这一限制。
