# Q1：你所在的部门职责范围 / 运维 Scope 是什么？对应到你的 SRE Agent，它的边界在哪？

> **面试官的问题：** 「这个基础设施部门……你认为的范围是什么？」随后进一步解释：「如果不清晰你所在这个部门的职责范围，那你所做的这个运维的事情，它的边界范围其实就不太清晰。」
>
> 他希望你说明：你所在的部门希望你运维的范围包括哪些？硬件层面、物理机、系统资源、网络、中间件、操作系统……还是「除了应用之外都属于基础设施」？
>
> **话术思路：** 不要先说「因为涉及保密所以不方便说」，而是直接给出**职责粒度**；并学会从「运维职责边界」反向解释 Agent 的功能范围。

## 这道题其实在考什么？

表面上是在问「你们部门到底管什么？」，但结合上下文，面试官真正关心的是：

> **你的 SRE Agent 到底应该解决什么范围的问题？**

因为如果连「人」的运维职责 Scope 都没有定义清楚，那么 **Agent 应该运维什么 → Agent 的能力边界 → Agent 的价值** 这几件事也就都不清楚了。

## 当时我的回答（复盘）

第一次回答有点紧张，担心涉及公司保密，所以没有直接说清楚。后来重新回答，核心是：

- 运维部门主要针对**千问事业部业务应用的底层运维**；
- 我所在的质量小组主要负责：
  - 中间件；
  - GPU 模型水位；
  - GPU 与推理服务指标；
  - RPS 等指标；
  - 水位控制与质量保障；
- 整个 SRE Agent 的平台覆盖范围比较广，可以从 **操作系统 → K8s → 中间件 → 业务应用**；
- 但**底层硬件管理不属于我们团队**，由云平台相关团队负责。

## 更合适的回答方式

不先说「涉及保密不方便说」，而是直接给职责粒度：

> 我们团队主要负责千问事业部业务应用相关的基础设施和运行质量保障。
>
> 从范围上来说，主要覆盖操作系统、Kubernetes、中间件，以及业务应用运行过程中相关的指标和水位控制。我们质量小组当时比较关注中间件、GPU 以及推理服务相关的指标，比如 GPU 水位、RPS 等，并负责对应的质量保障。
>
> 但底层物理硬件并不属于我们团队的直接运维范围，硬件和云资源底层的管理由对应的云平台团队负责。
>
> 所以如果对应到我做的 SRE Agent，它的运维 Scope 主要也是在我们团队实际负责的这一层——从 Kubernetes、操作系统、中间件一直到业务应用相关的运行状态和指标，而不是去覆盖最底层的物理硬件。

## 要记住的思维方式：SRE Scope → Agent Scope

面试官其实是在帮我建立一个 **SRE Scope → Agent Scope** 的思维方式：

```
团队负责什么
    ↓
哪些故障属于团队职责
    ↓
Agent 应该覆盖哪些层
    ↓
哪些问题应该交给其他团队
```

所以以后再被问「你的 Agent 为什么要做这个功能？」时，都可以反过来从**运维职责边界**去解释，而不是只从技术实现角度解释。

# Q2：这个 Agent 是开源 Agent 二开的？为什么当初选择 Hermes？

> **面试官的问题：** 「这个 Agent 当时……这个项目是开源 Agent 二开的？」确认项目来源后继续问：「你大概了解为什么当初选了爱马仕（Hermes）？」
>
> **话术思路：** 这一题考的不是「Hermes 是什么」，而是——**你是否理解一个 Agent 平台为什么采用「二开」而不是「自研」**。所以回答要围绕一个典型的工程选型问题：**自研 vs 复用成熟框架**，并从开发成本、上线周期、已有能力复用、二次开发成本、团队规模、业务需求这几个维度展开。

## 当时我的回答（复盘）

- 我加入项目时，项目已经在开发迭代；
- 项目确实是基于开源 Agent **Hermes** 做二次开发；
- Hermes 的最初选型我没有直接参与；
- 我了解到当时大概还有另外一个 Agent 平台方案；
- 如果完全自研 Agent，团队投入成本比较大；
- 当时整个 SRE Agent 团队大约十个人，而且每个人还有自己的业务运营和质量保障工作；
- 因此最终选择了相对成熟、比较重型的 Hermes，然后在它基础上二开，以满足尽快上线的需求。

## 更好的表达方式（很重要）

原来的回答是「这个选型我不知道，我没有参加」——事实没问题，但面试表达上比较被动。更好的说法是：

> **「最初决策我没有参与，但我后来了解了当时的背景，并且从工程约束上可以理解这个选择。」**

这两句话差别很大：前者是在说「我不知道」，后者是在说「我没有参与决策，但我能理解这个决策」。而这恰恰是三面比较容易考察的东西：**你不一定亲自做过决策，但要能理解技术决策背后的约束和 Trade-off。**

## 建议的完整回答

> 我加入这个项目的时候，Hermes 的最初选型其实已经完成了，所以这部分决策我并不是直接参与者。
>
> 但从我后来了解到的情况来看，当时主要是在成熟的 Agent 平台和自主搭建之间做取舍。
>
> 一方面，如果完全自研 Agent 平台，需要自己解决 Agent 的基础能力，包括模型调用、工具调用、任务编排、状态管理以及运行环境等，整体开发成本比较高。
>
> 另一方面，当时整个 SRE Agent 团队规模并不大，大概十个人左右，而且每个人还有自己的业务运营和质量保障工作，所以团队没有太多资源从零开始搭建一套完整的 Agent 平台；同时当时项目又有比较明确的上线需求。
>
> 所以最终选择了 Hermes 作为基础框架，在已有能力的基础上进行二次开发。这样可以把团队的主要精力放在 SRE 场景本身，比如工具接入、运维能力以及 Agent 的业务逻辑，而不是重新建设 Agent 的基础设施。
>
> 所以如果让我总结这个选型，本质上是一个工程上的取舍：**在团队规模、开发成本和上线周期的约束下，复用一个成熟的 Agent 框架，比完全自研更符合当时的项目目标。**

## 注意边界

可以用的是「团队规模有限、需要尽快上线、完全自研成本较高、最终选择 Hermes 二开」这条口径。至于 Hermes 具体有哪些能力，如果实际项目代码/源码里没有验证过，就不要在面试里凭空扩展。

# Q3：沙箱的保障和构建——你这样做就能保证它高可用吗？

> **面试官的问题（连续追问）：** 「这个的话主要就是那个沙箱的保障和构建？」→「我听下来有点懵……你这样做就能保证它能高可用？」→「切换的过程里面说应该复制一些数据或者一些信息过去？」→「所以你做的工作就是在需要切的时候，在那边新创建一个，新沙箱的时候在那个新的地方能找到，对不对？」
>
> **话术思路：** 面试官质疑的是「你说两个集群切换，就叫高可用了吗？」。不能只回答「我们有两个集群，所以高可用」，要讲清楚 **故障域隔离 + 状态外置 + 故障切换 + 恢复机制**；同时把 **平台高可用 ≠ 我负责的 Sandbox 使用质量保障** 这条边界说明白。

## 我实际负责的架构与边界

我负责的并不是**沙箱平台本身的高可用**，而是保证 SRE Agent 使用沙箱时，在沙箱发生故障的情况下能够快速恢复、尽量不影响用户使用。

```
                    SRE Agent / Hermes
                           │
                    Agent 运行平台
                           │
              ┌────────────┴────────────┐
              │                         │
          沙箱集群 A                  沙箱集群 B
           （南）                     （北）
              │                         │
              └────────────┬────────────┘
                           │
                      云对象存储
```

每个员工的目录结构：

```
个人账号
   │
   ├── 云对象存储：个人 Workspace
   │      ├── Skills
   │      ├── MCP 配置
   │      ├── 工作文件
   │      └── 手册
   │
   └── 独立 Sandbox（使用上述 Workspace）
```

沙箱本身还有一个很重要的约束：**生命周期只有 7 天，7 天后无论是否使用都会销毁重建。**

把整条链路按职责拆成四层（面试讲 Sandbox 相关问题时非常好用）：

| 层次 | 核心职责 | 关键词 |
| --- | --- | --- |
| **Agent Layer**（Hermes Agent / LLM / Agent Loop / Tool Planning） | 理解任务、分析、规划、选择工具、决定下一步 | **决策** |
| **Sandbox Layer**（Sandbox Cluster / Shell / CLI / Python） | 实际执行 Agent 产生的命令、脚本、工具操作；提供隔离、资源限制与权限边界 | **执行 + 隔离** |
| **External Resource**（Kubernetes / 内部服务与 API） | Agent 最终要操作的真实基础设施 | **被操作对象** |
| **Object Storage**（Workspace / Skills / MCP Config / 用户文件） | 保存需要长期保留的用户状态与工作空间 | **持久化** |

其中一个很重要的理解是：

> **Agent Layer 不等同于执行环境，Sandbox Layer 才是实际执行环境。**

所以整条链路可以概括为：用户请求 → Agent 理解 / 分析 / 决策 → 生成执行动作 → Sandbox 隔离执行 → 访问 K8s / 外部资源 → 结果返回 Agent → Agent 根据结果继续分析。而 Object Storage 是**旁路的持久化层**，把 Workspace / Config / Files 注入或恢复到 Sandbox。这样 Sandbox 就可以是**临时的、可销毁的计算环境**，而不是用户状态的唯一存储位置。

## 高可用方案到底是什么？

**第一层：双集群。** 沙箱平台当时有两个集群，一南一北；正常情况下使用其中一个，如果一个集群发生故障，就切换到另外一个集群。

**第二层：数据和计算分离（这才是真正重要的部分）。** 沙箱并不是数据的唯一存储位置，沙箱中的数据会同步到**云对象存储**。所以发生切换的时候：

```
旧 Sandbox
    ↓
发生故障
    ↓
切换到另一个 Sandbox 集群
    ↓
重新创建 Sandbox
    ↓
从对象存储恢复个人 Workspace
```

因此不需要在两个 Sandbox 之间做实时数据复制——这一点是这道题最值得讲清楚的地方。

## 这道题真正考什么？

面试官质疑的是「你说两个集群切换，就叫高可用了吗？」。完整的逻辑应该是：

```
两个沙箱集群
    ↓  避免单一集群成为唯一故障域
用户数据不依赖单个 Sandbox
    ↓  数据持久化到对象存储
故障后重新创建 Sandbox
    ↓
恢复用户工作环境
```

## 完整容灾路径：不只是「南 → 北」

我实际补充的细节是：容灾**不是简单的两级切换，而是三级降级**。

```
正常：Sandbox 南集群
      ↓ 集群故障
      Sandbox 北集群（Workspace 从对象存储恢复，用户感知尽量小）
      ↓ 集群故障
      Agent Container 本地执行（最终降级）
```

- **第一层（正常）**：`Agent → Sandbox → External Resource`。具备用户之间的执行环境隔离、Sandbox 级别的权限控制、独立的执行资源、用户授权机制、相对独立的故障域。
- **第二层（南 → 北切换）**：链路不变，只是从 `Sandbox-A` 切到 `Sandbox-B`；因为用户 Workspace 在 Object Storage，新 Sandbox 恢复 Workspace 后即可继续执行。
- **第三层（南北都故障）**：已经无法维持完整的 Sandbox 隔离模型，只能降级为 **Agent 容器本地执行**（`Agent → Agent Container → 直接执行 → External Resource`）。代价有两点：
  - **隔离能力下降**：原本是 `User A → Sandbox A`、`User B → Sandbox B`，降级后多个用户可能共用同一个 Agent Container；
  - **权限边界下降**：原本 `User → 授权 → Sandbox → CLI / Tool → External Resource` 的授权链被弱化，用户级隔离与授权边界不再由 Sandbox 承载。

**表述口径：** 这个降级方案本质上不是「Sandbox 挂了也没关系」，而是——

> **以降低执行隔离和权限控制能力为代价，换取 Agent 的基本执行能力仍然可用。**

如果面试官继续追问「那南北都挂了怎么办」，就用这条 **Graceful Degradation** 的 Trade-off 回答。

## 更适合面试的回答

> 我这里需要先区分一下，我负责的并不是沙箱平台本身的高可用，而是保证 SRE Agent 使用沙箱时，在沙箱发生故障的情况下能够快速恢复，尽量不影响用户使用。
>
> 当时沙箱平台本身有两个集群，一南一北，所以我们在两个集群上都有部署。正常情况下使用其中一个集群，如果这个集群出现故障，就切换到另外一个集群。
>
> 这里比较关键的是，我们没有把用户数据只放在 Sandbox 本身，而是把 Sandbox 中的个人工作空间同步到云对象存储。这样 Sandbox 本身实际上是相对临时的计算环境，数据和计算是解耦的。
>
> 所以发生故障之后，不需要把旧 Sandbox 里的数据再复制到新的 Sandbox，而是可以直接在另一个集群重新创建 Sandbox，然后重新挂载或者注入用户在对象存储里的 Workspace，包括 Skills、MCP 配置和个人文件。
>
> 因此我当时做的更多是 Sandbox 这一层的使用质量保障，而不是建设底层沙箱平台的高可用能力。平台本身的高可用由沙箱平台团队负责，我们主要保证的是：当 Sandbox 出现故障时能够发现、切换并快速恢复用户的 Agent 使用环境。

## 要记住的 SRE 思维

> **「计算可以是临时的，但状态不能和单个计算实例强绑定。」**

- **计算环境**：临时，可以销毁、重建；
- **用户状态**：放到对象存储，独立于 Sandbox；
- **故障恢复**：换集群 + 重建 Sandbox + 恢复状态。

**一句话记忆（把这一整题串起来）：**

> **Agent 负责决策，Sandbox 负责隔离执行，External Resource 是实际操作对象，Object Storage 保存持久化状态；Sandbox 故障时先南北切换，南北都不可用时降级到 Agent Container 本地执行，代价是用户隔离与权限控制能力下降。**

这样就把 **HA → Failover → State Recovery → Graceful Degradation**，以及**降级后的安全边界变化**串成了一条线，比只说「双集群保证高可用」完整得多。

另外，面试官还问了**「谁负责高可用」**这个边界问题，所以一定要把 **平台高可用 ≠ 我负责的 Sandbox 使用质量保障** 说清楚。否则很容易被继续追问「你凭什么保证平台本身两个集群都可用？」——我实际能负责的是**故障发现、切换和恢复用户环境**，而不是整个底层沙箱平台的 HA。

# Agent 相较于传统算法的优势：SRE 场景下的边界

### 核心结论

在 SRE 场景中，Agent 不是用来全面替代传统算法或自动化工作流的。传统算法、工作流平台和 Agent 更适合承担不同类型的任务：

- **监控与算法**：负责故障感知、异常检测、指标预测、特征分析和根因排序等确定性较强的任务；
- **自动化工作流**：负责稳定、固定、可审计的流程编排；
- **Agent**：负责复杂故障场景下的任务分解、工具选择、上下文整合和多轮探索，并将不同能力串成面向 SRE 的诊断流程。

因此，Agent 的优势并不只是“可以编排工作流”或“可以整合多源信息”，因为自动化平台和传统算法同样可以做到这些事情。更准确的区别在于：Agent 能够根据当前故障上下文和中间结果，动态决定下一步需要获取什么信息、调用什么工具，以及是否需要重新验证之前的判断。

### 与自动化工作流的区别

对于固定流程，例如“CPU 超过阈值后查询 Pod 状态、查询节点信息并生成告警卡片”，自动化工作流通常更稳定、可控、成本也更低，没有必要引入 Agent。

Agent 更适合处理流程分支多、故障信息不完整、下一步动作依赖前一步结果的场景。例如接口成功率下降后：

1. 先检查近期是否存在发布或配置变更；
2. 如果存在变更，进一步检查实例状态和配置差异；
3. 如果不存在变更，再检查依赖服务、网络和 Trace；
4. 如果证据仍然不足，再扩大时间窗口或补充采集其他信息；
5. 最后综合证据给出根因判断和恢复建议。

这类流程可以由传统工作流实现，但需要提前枚举大量分支；而 Agent 可以根据中间结果动态选择下一步，减少人工预先编排所有异常路径的工作量。对于稳定、关键、风险高的操作，仍然应该使用固定工作流、审批机制或人工确认进行约束。

### 与根因分析算法的区别

根因分析算法并不只能给出一个结论，也可以处理指标、日志、Trace、变更记录等多源信息，并输出特征、证据、因果链和解释结果。因此不应表述为“算法只能给结果，Agent 才能做过程分析”。

更准确的说法是：根因分析算法擅长在问题边界、输入数据和分析目标相对明确时，进行高效且稳定的专业判断；Agent 则可以调用这些算法，并负责在更开放的故障场景中决定何时调用、调用哪些数据、如何补充上下文，以及如何把结果与知识库、运维手册和后续流程结合起来。

### 更适合面试的回答

> 我认为 Agent 并不是全面替代传统算法或自动化工作流，而是适合承担不同的职责。监控和算法在故障感知、异常检测、指标预测以及根因排序等确定性较强的任务上更稳定；自动化工作流则适合编排固定、可审计的流程。
>
> Agent 的价值主要体现在复杂故障处理过程中：它可以结合当前上下文和中间结果，动态决定下一步需要查询哪些指标、日志、Trace、变更记录或知识库。如果现有信息不足，还可以继续调用工具或补充采集，再综合算法结果形成诊断结论和恢复建议。传统工作流也能实现这类流程，但通常需要提前枚举大量分支。
>
> 所以在 SRE 场景中，更合理的是三者结合：监控负责触发，算法负责专业分析，工作流负责稳定流程，Agent 负责复杂任务的动态编排、上下文整合和人机协同。对于高风险的写操作，最终仍然需要审批或人工确认。

### 需要避免的表述

- 不要说“算法无法处理多源信息”，这不准确；
- 不要说“算法只能给结论，Agent 才能解释过程”，算法同样可以输出证据和解释；
- 不要说“Agent 一定比工作流更好”，固定流程通常更适合工作流；
- 不要把 Agent 的优势泛化成“更智能”，应具体说成**动态决策、开放式探索、上下文整合和跨工具协同**。

# System Prompt 优化：简洁面试版

### 面试问题

**System Prompt 优化是怎么做的？如何证明优化有效？**

### 推荐回答

> 当时 Agent 被多人使用，模型调用成本较高，同时线上 session 中出现了重复环境检查、工具失败后反复重试等问题。
>
> 我先把业务人员和运营人员真实使用过的问题及处理路径沉淀成评测 case，并将线上已经被业务认可的回复和执行路径作为标准答案。在保持模型、Harness 和 case 不变的前提下，评测时只调整 System Prompt，比较任务完成率、稳定性、响应时间、Token 消耗、用户友好性和工具调用有效率。
>
> 评测发现，不同模型在相同 Harness 下存在不同的行为问题，因此我们针对性增加了跳过冗余检查、限制失败重试次数等规则。实验阶段 Token 消耗约下降 50%，冗余工具调用约下降 33%；上线后输入 Token 约下降 18%，输出 Token 约下降 57%，冗余工具调用约下降 33%，同时任务效果和用户体验没有明显下降。
>
> 所以这次优化的重点不是单纯缩短 Prompt，而是通过真实业务 case 发现模型行为问题，再通过受控评测验证 System Prompt 中每条规则是否真正有效。

### 这道题的核心逻辑

**真实问题 → 真实 case → 只调整 System Prompt 的受控实验 → 针对性优化 → 线上验证**

### 口径注意

评测对照实验中只调整 **System Prompt**；模型、Harness 和评测 case 等条件保持不变。不要把 Skills 的变化表述成这次实验的调整变量。

# 为什么从算法转向 AI

## 面试问题

**之前一直做算法，为什么后来转向 AI？**

## 原始回答

> 我逐渐发现自己对 AI 很感兴趣，但不希望单纯只做 AI，而是想把 AI 和 SRE 等具体领域结合起来，解决实际问题。

## 推荐回答

> 我之前做的算法工作让我积累了数据分析、异常检测和根因定位方面的经验，但我逐渐意识到，单个算法通常只解决一个局部问题，实际业务还需要数据采集、信息整合、流程编排和结果落地。因此我开始关注 Agent，希望把模型能力和已有的算法能力结合起来，解决更完整的问题。
>
> 我选择 SRE 作为结合场景，是因为它既有明确的业务痛点，也有比较清晰的反馈闭环。例如故障定位是否准确、建议是否可执行、恢复后指标是否改善，都可以被验证。因此我希望从运维场景入手，先理解真实流程和痛点，再用 AI、算法和自动化能力共同提升 SRE 效率，最终发展为 AI 与具体领域结合的工程方向。

## 核心记忆句

> **从解决单点算法问题，转向解决完整业务流程；从单纯做 AI，转向 AI 与 SRE 场景结合。**
