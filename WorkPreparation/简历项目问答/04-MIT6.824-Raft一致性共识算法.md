# 1. 角色状态与初始化 (`Make`)

系统启动时，每个节点通过 `Make` 函数进行初始化：

- **初始状态**：所有节点起步均为 `FOLLOWER` (状态 0)。
- **关键数据结构**：
  - `CurrentTerm`: 当前任期，初始化为 0。
  - `VotedFor`: 记录当前任期投票给谁，初始化为 -1。
  - `Log`: 日志条目切片，索引从 1 开始（`Log[0]` 作为占位符）。
  - `CommitIndex` & `LastApplied`: 追踪已提交和已应用到状态机的日志进度。
- **后台协程**：启动 `ticker` 协程负责状态切换和超时检查，启动 `applier` 协程负责向状态机提交日志。

# 2. 核心状态机循环 (`ticker`)

这是 Raft 的“心脏”，负责驱动节点在不同角色间转换：

- **选举超时 (Election Timeout)**：代码中设置了基础时间（如 300ms）加上基于节点 ID 的偏移（`me * SERVER_TIMEOUT`）和随机抖动。
- **状态转换逻辑**：
  - **Follower**：如果在超时时间内未收到 Leader 的心跳或 Candidate 的投票请求，则转变为 `CANDIDATE`。
  - **Candidate**：发起选举（`startElection`）。
  - **Leader**：定期发送心跳（`LeaderSendHeartBeat`），频率远高于选举超时。

# 3. 领导者选举流程 (`RequestVote`)

当节点进入 `CANDIDATE` 状态：

1. **发起请求**：自增 `CurrentTerm`，给自己投票，并并行（goroutine）向其他所有节点发送 `RequestVote` RPC。
2. **投票规则 (安全性约束)**：
   - **任期检查**：请求者的任期必须大于等于接收者的任期。
   - **日志完整性检查**：接收者会检查请求者的日志是否“至少一样新”。如果请求者的最后一条日志任期更高，或者任期相同但日志更长，才投赞成票。
3. **赢得选举**：如果获得超过半数（`votes > len(rf.peers)/2`）的选票，立即转为 `LEADER`。
4. **退位**：如果在选举过程中发现更高任期的请求或心跳，立即转回 `FOLLOWER`。

# 4. 日志复制与心跳 (`AppendEntries`)

一旦成为 Leader，通过此 RPC 维持权威并同步日志：

- **心跳机制**：Leader 定期发送不带日志条目的 `AppendEntries` 以阻止其他节点发起选举。
- **日志同步**：
  1. Leader 为每个 Follower 维护 `nextIndex`（下一条要发送的日志索引）。
  2. **一致性检查**：Follower 接收到请求后，会检查 `PrevLogIndex` 和 `PrevLogTerm` 是否匹配。如果不匹配，返回 `false`，Leader 会递减 `nextIndex` 并重试。
  3. **冲突处理**：Follower 如果发现已存在的条目与新条目冲突（索引相同但任期不同），会删除冲突条目及其后的所有日志。
- **提交进度更新**：当 Leader 发现某条日志已复制到半数以上节点，则更新自身的 `commitIndex`。

# 5. 日志应用与持久化 (`applier` & `persist`)

这是确保系统最终一致性的关键：

- **日志应用 (`applier`)**：
  - 这是一个持续运行的循环。
  - 当 `rf.CommitIndex > rf.LastApplied` 时，将 `LastApplied` 之后到 `CommitIndex` 的日志包装成 `ApplyMsg` 发送到 `applyCh`。
- **持久化 (`persist`)**：
  - 每当 `CurrentTerm`、`VotedFor` 或 `Log` 发生变化时，调用 `persist()` 将状态写入磁盘/内存。
  - **重启恢复**：`readPersist()` 负责在节点崩溃重启后恢复这些关键变量，确保选举安全性不被破坏（例如不会在同一任期投两次票）。

# 6. 并发控制与同步机制

你的代码中体现了典型的 Go 并发模式：

- **互斥锁 (`rf.mu`)**：几乎在所有修改或读取共享状态的地方都使用了 `Lock/Unlock`，防止数据竞态。
- **条件变量 (`sync.Cond`)**：虽然在提供的代码片段中主要看到了 `ticker` 的循环，但在成熟的实现中（如 `applier`），通常会配合 `sync.Cond` 来唤醒正在等待新日志提交的协程。
- **上下文管理 (`context`)**：在 RPC 调用中引入了 Context 机制，增强了对超时和取消的控制能力。

# 7. 实现中的关键细节 (基于代码注释)

- **调试开关**：通过 `EnableDebug` 及各类子开关（`LeaderElectionDebug` 等）实现了精细化的日志追踪。
- **索引 1 开始**：日志切片初始化时添加了一个空元素，简化了 `PrevLogIndex` 的边界逻辑处理。
- **重置计时器**：在收到合法心跳、成功给他人投票或转换状态时，会重置选举计时器。
